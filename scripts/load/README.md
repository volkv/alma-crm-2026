# Нагрузочный прогон

Здесь лежит всё, чем меряются требования `N1` (отклик не дольше секунды), `N6`
(пятьдесят одновременных пользователей) и `N7` (десять одновременных отчётов).
Результаты последнего прогона и выводы — в [`docs/performance.md`](../../docs/performance.md).

## Что здесь

| Файл               | Что это                                                                           |
| ------------------ | --------------------------------------------------------------------------------- |
| `run.sh`           | Весь прогон одной командой: стенд, набор, сценарии, уборка                        |
| `compose.load.yml` | Третье наложение Compose: стенд в своём проекте и на своих портах                 |
| `load.env.example` | Образец переменных стенда; `load.env` рядом с ним заполняется на месте            |
| `session.js`       | Вход через каталог учётных записей — тот же путь, что проходит браузер            |
| `metrics.js`       | Что считается: операции требования `N1` и виды запроса                            |
| `browse.js`        | Сценарий «пятьдесят пользователей»                                                |
| `reports.js`       | Сценарий «десять одновременных отчётов»                                           |
| `cache.js`         | Замер кэша повторного открытия — карточки и экрана отчёта (`F13`)                 |
| `fixture.ts`       | Список карточек для сценария: где стоит запись и куда с этой стадии можно шагнуть |

k6 в репозитории нет и быть не может: это не пакет npm, а отдельный бинарь.
`run.sh` запускает его контейнером `grafana/k6` в сети хоста — приложение стенда
опубликовано на 127.0.0.1, и из своей сети контейнер до него не дотянулся бы.

## Порядок

Сначала — свой файл окружения. В репозитории его нет: он несёт ключ шифрования
контактов, пароли каталога учётных записей и хранилища, а напечатанные в
репозитории они не защищают ничего. Значения генерируются один раз на машину:

```bash
cp scripts/load/load.env.example scripts/load/load.env
for key in POSTGRES_PASSWORD REDIS_PASSWORD OIDC_CLIENT_SECRET KEYCLOAK_ADMIN_PASSWORD \
	S3_SECRET_KEY EXCHANGE_SECRET MOCK_CONTROL_TOKEN SEED_DEMO_PASSWORD; do
	sed -i "s|^$key=$|$key=$(openssl rand -hex 24)|" scripts/load/load.env
done
sed -i "s|^PII_ENCRYPTION_KEY=$|PII_ENCRYPTION_KEY=$(openssl rand -base64 32)|" scripts/load/load.env
```

Пустых значений после этого остаться не должно у всех, кроме `SMTP_*` и
`EXCHANGE_API_KEY_*`: почты и обмена на нагрузочном стенде нет. Тем же паролем,
что попал в `SEED_DEMO_PASSWORD`, входит и сценарий k6 — `run.sh` читает его
оттуда, а не хранит у себя.

```bash
scripts/load/run.sh up       # стенд и нагрузочный набор
scripts/load/run.sh probe    # проба: 5 VU, 30 с
scripts/load/run.sh cache    # замер кэша повторного открытия
scripts/load/run.sh browse   # только сценарий пользователей (VUS, DURATION)
scripts/load/run.sh reports  # только сценарий отчётов
scripts/load/run.sh full     # полный прогон обоих сценариев
scripts/load/run.sh down     # погасить стенд вместе с томами
```

Параметры задаются переменными окружения: `VUS`, `DURATION`, `REPORT_VUS`,
`REPORT_DURATION`, `PAIRS`, `REPORT_PAIRS`, `OUT` (куда складывать результаты),
`BASE_URL`. Лестница нагрузки — это `browse` с разными `VUS` и своим `OUT` на
каждую ступень: сводка k6 пишется в файл по имени сценария и иначе затёрлась бы.

Кроме сводки каждый прогон оставляет рядом сырые точки
(`<сценарий>-raw.json.gz`). Сводка считает метрики сценария целиком, и на один
вопрос она не отвечает: переход по процессу и комментарий лежат в ней одной
метрикой, потому что для требования это одна операция — отправка формы. Разложить
прогон по шагам сценария:

```bash
scripts/load/run.sh breakdown <OUT>/browse-raw.json.gz
```

## Три вещи, которые ломают прогон

1. **Стенд поднимается под своим именем проекта — `lct-load`.** Тот же стек под
   именем разработки пересоздал бы контейнеры, которыми в это время пользуется
   прогон e2e, и снёс бы его базу. Имя проекта задаётся в `run.sh` и менять его
   без причины не надо.
2. **Каталог учётных записей защищается от частых входов.** Два входа одной
   записью внутри секунды он считает подбором и запирает запись на минуту.
   Полсотни VU входят тремя записями, поэтому они расходятся по времени
   (`sleep((__VU - 1) * 0.5)` перед входом), а на случай запертой записи в
   `session.js` есть повтор. Ослаблять настройки каталога ради прогона нельзя:
   мерить надо систему, какая она есть.
3. **Счётчик начала входа живёт пятнадцать минут.** Второй прогон подряд упёрся
   бы в него, а не в производительность, поэтому `run.sh` перед каждым
   сценарием чистит ключи `login_ip:*` в Redis стенда.

## Почему сценарию нужна фикстура

k6 не отрисовывает страницу и не открывает диалогов, а перевести карточку на
следующую стадию нельзя, не зная, где она стоит и куда с этой стадии ведёт шаг
вперёд. Эти идентификаторы человек в интерфейсе получает нажатием, а сценарий —
из `fixture.ts`: скрипт читает базу стенда (и ничего в ней не меняет) и печатает
JSON со списком карточек, списком «куда шагнуть» и списком записей с самой
длинной историей.

Список «куда шагнуть» неоднородный, и это свойство процесса: до подписания
соглашения шаг вперёд требует только решения человека, на подписании —
утверждённой отметки по документу дела, после — результата и подтверждения
данными. Переводить карточку, которой по процессу переходить нельзя, значило бы
мерить скорость отказа, поэтому такие записи остаются только в чтении. Каждому
VU достаётся свой кусок списка: стадия — это состояние, и второй переход по той
же карточке пошёл бы уже с другой стадии.

Отсюда и размер списка: из 2600 действующих карточек набора шагнуть вперёд
можно с 1292 — это те, что стоят на четырёх первых стадиях процесса. Сколько
переходов достаётся одному VU, считает сам сценарий; когда кусок кончается, шаг
остаётся комментарием, и в разбивке по шагам это видно отдельной строкой.
