# Нагрузочный прогон

Здесь лежит всё, чем меряются требования `N1` (отклик не дольше секунды), `N6`
(пятьдесят одновременных пользователей) и `N7` (десять одновременных отчётов).
Результаты последнего прогона и выводы — в [`docs/performance.md`](../../docs/performance.md).

## Что здесь

| Файл               | Что это                                                                       |
| ------------------ | ----------------------------------------------------------------------------- |
| `run.sh`           | Весь прогон одной командой: стенд, набор, сценарии, уборка                    |
| `compose.load.yml` | Третье наложение Compose: стенд в своём проекте и на своих портах             |
| `load.env.example` | Образец переменных стенда; `load.env` рядом с ним заполняется на месте        |
| `session.js`       | Вход через каталог учётных записей — тот же путь, что проходит браузер        |
| `metrics.js`       | Что считается: операции, доля ответов дольше секунды, виды запроса, изменения |
| `browse.js`        | Сценарий «пятьдесят пользователей»                                            |
| `reports.js`       | Сценарий «десять одновременных отчётов»                                       |
| `cache.js`         | Замер кэша повторного открытия — карточки и экрана отчёта (`F13`)             |
| `fixture.ts`       | Данные под прогон: команда, её области, свежий пул переходов, сверка с базой  |

Сам нагрузочный набор — объём и команда из двадцати КАМов и трёх руководителей —
заливает сид (`scripts/seed/load.ts`, [`docs/seeds.md`](../../docs/seeds.md)).

k6 в репозитории нет и быть не может: это не пакет npm, а отдельный бинарь.
`run.sh` запускает его контейнером `grafana/k6` в сети хоста — приложение стенда
опубликовано на 127.0.0.1, и из своей сети контейнер до него не дотянулся бы.

## Порядок

Сначала — свой файл окружения. В репозитории его нет: он несёт ключ шифрования
контактов, пароли каталога учётных записей и хранилища, а напечатанные в
репозитории они не защищают ничего. Значения генерируются один раз на машину:

```bash
cp scripts/load/load.env.example scripts/load/load.env
for key in POSTGRES_PASSWORD REDIS_PASSWORD OIDC_CLIENT_SECRET KEYCLOAK_ADMIN_PASSWORD \
	S3_SECRET_KEY EXCHANGE_SECRET MOCK_CONTROL_TOKEN SEED_DEMO_PASSWORD; do
	sed -i "s|^$key=$|$key=$(openssl rand -hex 24)|" scripts/load/load.env
done
sed -i "s|^PII_ENCRYPTION_KEY=$|PII_ENCRYPTION_KEY=$(openssl rand -base64 32)|" scripts/load/load.env
```

Пустых значений после этого остаться не должно у всех, кроме `SMTP_*` и
`EXCHANGE_API_KEY_*`: почты и обмена на нагрузочном стенде нет. Тем же паролем,
что попал в `SEED_DEMO_PASSWORD`, входит и сценарий k6 — `run.sh` читает его
оттуда, а не хранит у себя.

```bash
scripts/load/run.sh up       # стенд, нагрузочный набор, команда в каталоге
scripts/load/run.sh probe    # дымовой прогон: 5 VU, 1 мин, со сверкой
scripts/load/run.sh cache    # замер кэша повторного открытия
scripts/load/run.sh browse   # только сценарий пользователей (VUS, DURATION)
scripts/load/run.sh reports  # только сценарий отчётов
scripts/load/run.sh full     # полный прогон обоих сценариев
scripts/load/run.sh down     # погасить стенд вместе с томами
```

Параметры задаются переменными окружения: `VUS`, `DURATION`, `REPORT_VUS`,
`REPORT_DURATION`, `PAIRS`, `REPORT_PAIRS`, `OUT` (куда складывать результаты),
`BASE_URL`. Лестница нагрузки — это `browse` с разными `VUS` и своим `OUT` на
каждую ступень: сводка k6 пишется в файл по имени сценария и иначе затёрлась бы.

Кроме сводки каждый прогон оставляет рядом сырые точки
(`<сценарий>-raw.json.gz`). Разложить прогон по шагам сценария, включая вход и
подсказку выбора, которых в сводке нет отдельными метриками:

```bash
scripts/load/run.sh breakdown <OUT>/browse-raw.json.gz
```

Вторая таблица разбивки — `Server-Timing` по операциям: сколько ответ ждал базу
(`db`) и сколько работало приложение (`app`). Когда операция не держит секунду,
она отвечает, во что упёрлись; разница с временем операции — очередь до начала
обслуживания.

Код выхода `probe` и `browse`: 99 — не выдержан порог k6, 1 — сверка с базой не
сошлась (или k6 не оставил сводки). Сверка идёт и после красного порога: числа
несдавшего прогона тоже надо проверить.

## Четыре вещи, которые ломают прогон

1. **Стенд поднимается под своим именем проекта — `lct-load`.** Тот же стек под
   именем разработки пересоздал бы контейнеры, которыми в это время пользуется
   прогон e2e, и снёс бы его базу. Имя проекта задаётся в `run.sh` и менять его
   без причины не надо.
2. **Каталог учётных записей защищается от частых входов.** Два входа одной
   записью внутри секунды он считает подбором и запирает запись на минуту.
   Полсотни VU входят двадцатью тремя записями, по два-три VU на запись,
   поэтому они расходятся по времени (`sleep((__VU - 1) * 0.5)` перед входом),
   а на случай запертой записи в `session.js` есть повтор. Ослаблять настройки каталога ради прогона нельзя:
   мерить надо систему, какая она есть.
3. **Счётчик начала входа живёт пятнадцать минут.** Второй прогон подряд упёрся
   бы в него, а не в производительность, поэтому `run.sh` перед каждым
   сценарием чистит ключи `login_ip:*` в Redis стенда.

4. **Прокси из окружения.** Стенд стоит на петле, а `HTTP_PROXY` машины до
   него не дотянется. Обращения `run.sh` к каталогу идут мимо прокси явно, k6
   работает в контейнере, и прокси машины у него нет.

## Кто входит

Двадцать КАМов (`load-kam-01` … `load-kam-20`) и три руководителя
(`load-lead-1` … `load-lead-3`). Каждый вуз набора закреплён за одним КАМом, КАМы
подчинены руководителям по кругу. Сид заводит их в базе CRM, а `run.sh up` — в
каталоге, через его административный API: с той же почтой, подтверждённой
почтой, ролью realm и паролем из `SEED_DEMO_PASSWORD`. Повторный `up` записи не
пересоздаёт. Новая запись каталога — это новый субъект, и CRM не связала бы её
со строкой, уже связанной первым входом. `up` только выставляет пароль и роль
заново.

VU раздаются записям по кругу. Всё, что VU открывает, `fixture.ts` берёт из
области его записи: у КАМа — его портфель, у руководителя — портфели его КАМов.
Карточку чужого портфеля сервер отдал бы как «не найдено», и прогон мерил бы
отказ.

## Почему переходам нужен свой пул

k6 не отрисовывает страницу и не открывает диалогов, а перевести запись на
следующую стадию нельзя, не зная, где она стоит и куда с этой стадии ведёт шаг
вперёд. Эти идентификаторы человек получает нажатием, а сценарий — из
фикстуры.

Переход меняет состояние. Записи набора после одного-двух шагов упираются в
подписание, где шаг вперёд ждёт утверждённого документа, а после него —
результата и подтверждения. Прежний сценарий так и вычерпывал набор от ступени
к ступени. Поэтому `probe` и `browse` перед каждым прогоном заводят **свежий
пул** под свой ключ прогона:

```bash
node scripts/load/fixture.ts --run <ключ> --vus <V> --per-vu <N>
```

- на каждую запись команды — `ceil(V / 23) × N` взаимодействий. Их ведёт сам
  сотрудник, вуз взят из его области, стадия — одна из тех, с которых шаг
  вперёд ничего не требует, чек-лист закрыт;
- `N = длительность / 4 + 1`: проход VU длится не меньше четырёх секунд (четыре
  паузы по секунде), и пула хватает на весь прогон. Если он всё-таки кончится,
  проход считается в `pool_exhausted`, а на ней стоит порог «ноль»;
- пул записи делится между её VU поровну, одну запись дважды не переводят.

Пул остаётся в базе. Ступени, которые надо сравнивать между собой, снимаются на
свежем стенде: `down`, `up`, одна ступень.

## Сверка с базой

Засчитать изменение по статусу ответа нельзя: отказ формы (`fail(409, …)`) в
ответе `use:enhance` приходит с HTTP 200 и `type: "failure"`. Поэтому сценарий
отправляет формы так же, как страница (`x-sveltekit-action: true`), и считает
изменение состоявшимся только при `type: "success"` (`applied_transition`,
`applied_comment`).

Этого мало, если ошибётся сам сценарий, поэтому после k6 `run.sh` сверяется с
базой: `fixture.ts --verify <ключ>` считает закрытые записи стадий пула (одна на
переход) и комментарии с ключом прогона в тексте. Расхождение с числами k6
печатается как `РАСХОДИТСЯ`, и `run.sh` завершается с ошибкой.
