# Начальные данные

Сид заполняет пустую базу тем, без чего систему нельзя ни показать, ни начать
использовать: каталогом прав и ролей, учётными записями и демонстрационным
справочником. Код — в `scripts/seed/`, запуск — `pnpm run db:seed`.

## Что заливается

| Набор              | Строк | Что это                                                                          |
| ------------------ | ----- | -------------------------------------------------------------------------------- |
| `permissions`      | 26    | Каталог прав из `$lib/server/rbac/permissions`                                   |
| `roles`            | 3     | Администратор, менеджер, наблюдатель                                             |
| `role_permissions` | 52    | Права ролей по тому же каталогу                                                  |
| `users`            | 5–6   | Три демонстрационные записи, два сотрудника и, если задан пароль, администратор  |
| `organizations`    | 25    | 12 вузов, 4 колледжа, 2 школы, 6 компаний-заказчиков, 1 организация-оператор     |
| `sites`            | 15    | Кампусы, филиалы, кафедры и лаборатории у восьми учебных заведений               |
| `people`           | 40    | Контакты: ректоры, проректоры, деканы, завкафедрами, преподаватели, координаторы |

| `programs`         | 10    | Программы уровней `bachelor`, `master`, `spo`, `school`, `dpo`                   |
| `program_versions` | 14    | По версии на программу, у четырёх — по две                                       |
| `products`         | 8     | Продукты с поставщиками из компаний-заказчиков                                   |
| `stat_snapshots`   | 3     | Две подтверждённые выгрузки за соседние учебные годы и одна непринятая           |
| `stat_rows`        | 96    | Их строки; в непринятой выгрузке три строки не разобрались                       |
| `stage_routes`     | 1     | Демонстрационный маршрут из 14 стадий (`ensureDemoRoute`)                        |
| `interactions`     | 30    | Взаимодействия на стадиях маршрута — см. «Взаимодействия»                        |

Данные полностью синтетические. Ни одна организация, площадка, фамилия, почта
или телефон не принадлежит настоящему лицу: наименования собраны из
географических и отраслевых слов, почта — на `example.org` и `example.com`,
телефоны — из диапазона `+7 900 000-00-NN`. ИНН, КПП и ОГРН выдуманы, но
проходят контрольные суммы: иначе форма организации отвергла бы собственные
демонстрационные данные.

Заливка идёт в два приёма, и это видно в `seedAll` (`scripts/seed/run.ts`).
Сначала одной транзакцией пишутся права, учётные записи, справочники и маршрут:
половина справочника без ролей — это не «частично получилось», а сломанный
стенд. После её фиксации заливаются взаимодействия — иначе никак: их историю
пишет сам движок стадий, а каждая его команда открывает собственную транзакцию
и незафиксированных справочников не увидит.

Отсюда требование к окружению: сид ходит в базу тем же подключением, что и
приложение (`getDb()`), поэтому ему нужны все переменные из `.env.example`, а не
только `DATABASE_URL`.

## Запуск

```bash
pnpm run db:migrate          # сид работает по уже применённой схеме
SEED_DEMO_PASSWORD='…' pnpm run db:seed
```

Трём взаимодействиям сид собирает соглашение по шаблону, а это конвертация в
PDF через Gotenberg. Служба поднимается вместе с остальным окружением
(`docker compose up -d gotenberg`); если её нет, сид пишет об этом в лог и
заливает всё остальное. Это единственное место, где ошибка не останавливает
заливку: стенд без трёх документов показать можно, а установка на машине без
Gotenberg не должна падать на сиде.

`SEED_DEMO_PASSWORD` — общий пароль демонстрационных учётных записей.
Переменная нужна только сиду, в `src/lib/server/config.ts` её нет: сервер про
неё ничего не знает и без неё стартует. Значение для локальной работы уже лежит
в `.env.example`. Пароль проверяется по политике по умолчанию (12 символов, три
класса символов) — короткий пароль сид не примет.

`SEED_STAFF_ADMIN_PASSWORD` — пароль администратора стенда, единственная
необязательная переменная сида; о ней — раздел «Администратор стенда» ниже.

## Запуск в контейнере

Контейнер приложения сам применяет миграции и сам заливает данные — но только
на демонстрационном стенде:

```dockerfile
CMD ["sh", "-c", "node scripts/migrate.ts && node scripts/seed/index.ts --if-demo && exec node build/index.js"]
```

Флаг `--if-demo` означает «залей, если `DEMO_MODE=true`»; при любом другом
значении сид пишет в лог строку о том, что данных не будет, и выходит с нулевым
кодом. Так один и тот же образ годится и для публичного стенда, и для установки
у заказчика, где демонстрационные вузы никому не нужны.

Ошибка на любом шаге останавливает контейнер: приложение не должно подниматься
на наполовину подготовленной базе.

## Почему повторный запуск безопасен

У каждой сидируемой строки идентификатор известен заранее: это UUID версии 5 от
константного пространства имён и ключа набора (`scripts/seed/ids.ts`). Отсюда
два следствия.

**Повторный сид ничего не дублирует.** Вставка идёт с
`on conflict (id) do nothing`: строка, которая уже есть, просто пропускается.

**Повторный сид ничего не затирает.** Переименовали организацию на стенде,
поправили должность, убрали заметку — правка останется. Исключение одно:
каталог прав и ролей приводится к тому, что записано в коде
(`seedRolesAndPermissions`), потому что отозванное в коде право не должно
оставаться выданным в базе.

То же касается учётных записей: пароль, роль и имя уже заведённой записи —
дело администратора стенда. Сменить `SEED_DEMO_PASSWORD` и перезапустить
контейнер недостаточно, чтобы поменять пароль демонстрации: сначала нужно
удалить сами записи. Исключение одно — сам администратор стенда, см. одноимённый
раздел ниже: его пароль сид как раз обязан возвращать к значению переменной.

Ссылки между наборами расставляются теми же вычисляемыми идентификаторами,
поэтому сид не читает из базы ничего, что только что записал.

## Взаимодействия

Тридцать записей на разных стадиях маршрута — то, ради чего стенд вообще можно
открыть и показать. Данные лежат в `scripts/seed/interactions.ts` явным списком,
как и справочники, и ссылаются на те же ключи организаций, людей, программ и
продуктов.

| Что                                   | Сколько |
| ------------------------------------- | ------- |
| Взаимодействий                        | 30      |
| Завершённых (весь маршрут пройден)    | 5       |
| Просроченных по текущей стадии        | 4       |
| На паузе «ждём вуз»                   | 3       |
| С открытой помехой (одна блокирующая) | 2       |
| С закрытым чек-листом текущей стадии  | 6       |
| С комментариями                       | 8       |
| С собранным соглашением (DOCX + PDF)  | 3       |
| С возвратом стадии в истории          | 1       |
| С передачей другому менеджеру         | 3       |

Больше всего записей на ранних и исполнительских стадиях: так выглядит живая
воронка — контактов много, до занятий доходят единицы. У каждой записи три
стороны (учебное заведение, компания-заказчик, оператор), контакт вуза, одна-три
программы, ответственный менеджер. У трёх ответственный по ходу дела сменился —
`setResponsible` пишет об этом в историю плана, и вкладка «Правки плана» на
стенде не пустая.

**Историю пишет движок, а не сид.** Набор зовёт те же команды, что и карточка:
`advanceStage`, `confirmStage`, `pauseStage`, `raiseBlocker`, `addComment`,
`setResponsible`, `completeInteraction`. Разложить записи стадий прямо в таблицу было бы вдвое
короче и вдвое хуже: слепки стадий, отметки чек-листа, закрытие пауз и события
журнала — это правила движка, и вторая их реализация в сиде однажды разойдётся
с первой.

**Время правится после.** Движок ставит `now()` — и правильно делает, команду
отдают сейчас. Но демонстрации нужна запись, которая идёт третий месяц, а
параметр «а на самом деле это было в мае» в командах движка не понадобился бы
никогда и никому, кроме сида. Поэтому сид, дописав историю, одной транзакцией
двигает `stage_entries.entered_at` и `left_at`, начало паузы, время помехи и
комментариев и `interactions.last_activity_at`. Сроки, просрочку и паузы
пересчитывает представление `stage_entry_status` — числа сид не подставляет.

**Просрочка — следствие данных, а не флаг.** В наборе у записи сказано, сколько
дней назад она вошла в стадию; просроченной её делает норматив стадии. Поэтому
счётчик просроченных в `INTERACTION_SEED_SIZES` вычисляется из тех же данных, а
тест сверяет его с тем, что насчитала база.

**Идентификаторы — вычисляемые, как у справочников.** Взаимодействие заводится
не через `createInteraction`: сервис выдаёт записи случайный идентификатор, а
повторный сид узнаёт свои строки только по `seedId('interaction', <ключ>)`. Всё
остальное — стороны, программы, продукты, первая стадия и событие журнала —
делается в той же транзакции, что и вставка, поэтому записи без стадии не
существует даже мгновение.

**Повторный запуск не пересоздаёт историю.** Если взаимодействие с таким
идентификатором уже есть, сид его пропускает целиком: досоздать историю нельзя,
а переписать заново — значит стереть работу, проделанную на стенде руками.

## Журнал действий пишется только за взаимодействия

У справочников автора нет: строки вставляются напрямую, за ними не стоит ни
пользователя, ни запроса, и подходящего типа события в словаре
`AUDIT_EVENT_TYPES` для «залили справочник» тоже нет. Факт заливки виден в логе
контейнера, этого достаточно.

С взаимодействиями иначе: их ведёт движок, а он пишет журнал сам. События
приезжают с источником `system` и с автором — тем сотрудником, от чьего имени
набор отдаёт команду. Назвать автором систему было бы неправдой: у комментария
и у отметки подтверждения есть человек, и на демонстрации он должен быть виден
и в карточке, и в журнале.

## Демонстрационные учётные записи

| Почта                        | Имя                | Роль          |
| ---------------------------- | ------------------ | ------------- |
| `admin@demo.lct-crm.local`   | Администратор Демо | Администратор |
| `manager@demo.lct-crm.local` | Менеджер Демо      | Менеджер      |
| `viewer@demo.lct-crm.local`  | Наблюдатель Демо   | Наблюдатель   |

У всех трёх `users.is_demo = true`, поэтому при `DEMO_MODE=true` на странице
входа появляются кнопки «Войти как …» — пароль для них не нужен. Пароль
пригодится, если нужно войти обычной формой.

Кроме них заводятся два сотрудника (`a.veresova@example.org`,
`p.zotov@example.org`) с ролью менеджера. Они нужны, чтобы списки владельцев и
авторов не состояли из одного «Менеджера Демо». Войти под ними нельзя: в
`password_hash` лежит хеш случайной строки, которой никто не видел.

## Администратор стенда

При `DEMO_MODE=true` демонстрационная сессия не получает прав на пользователей,
ключи доступа, настройки, маршруты, интеграции и уничтожение персональных
данных — какой бы ролью ни вошли (`auth.md`, «Демо-сессия — это граница, а не
значок»). Обезличивание в этом списке не ради полноты: оно необратимо, а сид
стёртые имена не возвращает — он не затирает правок, сделанных на стенде. Учёт
согласий и сроков демонстрации при этом оставлен: его записи переигрываются.
Значит, на публичном стенде управлять системой может только обычная учётная
запись оператора, а завести её изнутри демонстрации невозможно: раздел
пользователей демонстрации ей не принадлежит. Поэтому её заводит сид — и только
если ему дали пароль:

```bash
SEED_DEMO_PASSWORD='…' SEED_STAFF_ADMIN_PASSWORD='…' pnpm run db:seed
```

| Почта                       | Имя                  | Роль          |
| --------------------------- | -------------------- | ------------- |
| `admin@staff.lct-crm.local` | Администратор стенда | Администратор |

`is_demo = false`, поэтому кнопки «Войти как …» у неё нет и ограничения
демонстрации на неё не распространяются: входят обычной формой по паролю.

Переменная не задана — записи нет вовсе, и сид пишет об этом строку в лог.
Установка у заказчика, где администратора заводят руками, ничего лишнего не
получает.

Это **единственная запись, чей пароль сид переписывает**. Общее правило —
«пароль заведённой записи дело администратора стенда» — здесь не работает:
поменять пароль этой учётной записи может только она сама, и если он забыт или
стенд поднимают заново, вернуть доступ больше нечем. Обратная сторона: пароль,
изменённый в интерфейсе, вернётся к значению переменной при следующем запуске
сида — то есть при каждом перезапуске контейнера. Пароль проверяется по той же
политике, что и заведённый руками.

## Как добавить набор

1. Данные — отдельным модулем в `scripts/seed/`, рядом с `directory.ts`.
   Функция принимает `tx` и ничего не знает ни про подключение, ни про
   окружение: это забота `run.ts`.
2. Идентификаторы — только через `seedId(<набор>, <ключ>)`. Новый набор
   добавляется в тип `SeedKind`.
3. Каждая строка перед вставкой проходит контракт из `$lib/contracts/**` —
   тот же, что валидирует форму. Сид не имеет права положить в базу то, чего не
   примет интерфейс.
4. Вставка — `on conflict (<первичный ключ>) do nothing`.
5. Вызов — в `seedAll` (`scripts/seed/run.ts`), после наборов, на которые
   ссылается новый.
6. Ожидаемое число строк — в счётчик набора (`DIRECTORY_SEED_SIZES` и ему
   подобные), чтобы тест заметил молча не вставившуюся строку.

## Почему у сида свой резолвер импортов

Сид пользуется схемой базы, контрактами и хешированием паролей из `src/lib`, но
запускается обычным процессом Node, а не через Vite. Vite понимает две вещи,
которых в Node нет: специи SvelteKit (`$lib/…`, `$env/dynamic/private`) и импорт
без расширения. Оба правила объявлены в `scripts/seed/aliases.ts` синхронными
хуками модулей и ставятся из `scripts/seed/index.ts` до первого такого импорта.

Это дешевле, чем собирать ради сида второй бандл, и честнее, чем держать рядом
со скриптом копию схемы, которая однажды разойдётся с настоящей. Плата —
`src/lib` лежит в образе рядом со сборкой (`Dockerfile`).

## Проверка

`tests/integration/seed/seed.test.ts` поднимает PostgreSQL в testcontainers и
проверяет на настоящей базе: количества строк по наборам, неизменность
идентификаторов при повторном запуске, что ручная правка переживает повторный
сид, что под демонстрационной записью можно войти паролем из окружения и что
все ИНН проходят контрольную сумму и не повторяются. По данным об обучении — что
коды программ, записанные в строках снимков, есть в справочнике: строка снимка
показывается такой, какой пришла из файла, и код, которого в справочнике нет,
читается как ошибка загрузки. По администратору стенда — что без переменной
записи нет, что с переменной под ней входят, что повторный запуск переписывает её
пароль и что негодный пароль сид отвергает до записи.

По взаимодействиям сверяются числа из `INTERACTION_SEED_SIZES` с тем, что
насчитала база: открытая запись стадии ровно одна у каждого незакрытого
взаимодействия и ни одной у завершённых, просроченных четыре, на паузе три, у
завершённых пройден весь маршрут. Повторный сид не добавляет ни одной записи
стадии.

Этими же данными работает e2e: `e2e/global-setup.ts` заливает их тем же сидом —
и тем же сидом заводит себе администратора стенда, передавая
`SEED_STAFF_ADMIN_PASSWORD`, — а `e2e/demo-pass.test.ts` проходит по ним
сквозной сценарий демонстрации.
