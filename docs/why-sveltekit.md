# Почему SvelteKit, а не React

Техническое задание называет Kotlin, Python, Node.js и React. На Q&A 2026-09-16 заказчик разрешил
другой набор — при условии **развёрнутого обоснования**: «мы владеем этим языком» за обоснование не
считается. Этот документ и есть такое обоснование.

Серверная платформа и база взяты из перечня задания: **Node.js 24** и **PostgreSQL 17**. Разошлись
мы с ним в одном пункте — интерфейсе: вместо React стоит **Svelte 5 в режиме runes** и
**SvelteKit 2**. Ниже — почему это решение продукта, а не привычка.

## Коротко

| Требование задания                                  | Чем отвечает выбор                                                                           |
| --------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `N1` — отклик интерфейса не дольше секунды          | страница приходит собранной с сервера; браузеру не нужен второй круг за данными              |
| `N2` — страница не перезагружается при смене данных | формы с прогрессивным улучшением и клиентская навигация — штатное поведение, а не надстройка |
| `R2` — все методы в Swagger UI                      | схема OpenAPI собирается из тех же контрактов Zod, что проверяют формы                       |
| `X4` — удобство на десктопе и на телефоне           | одна разметка и один стиль на оба размера, проверенные прогоном на 390 и 1280                |
| `R3` — отдельный самостоятельный сервис             | интерфейс и API — одно приложение и один процесс, а не два развёртывания                     |

## Один процесс вместо двух

React в паре с серверным API — это два развёртывания: отдельная сборка интерфейса и отдельный
сервис данных. У них своя пара контрактов, своя пара конфигураций, свой CORS и своя аутентификация
между собой.

В SvelteKit страница, форма и эндпоинт живут в одном приложении и зовут **одни и те же сервисы** с
одним и тем же контекстом прав (`docs/architecture.md`). Права проверяются один раз и одинаково —
и для страницы, и для `/api/v1`. Развёртывание — один контейнер (`R3`), и на демонстрации это
видно: `docker compose up` поднимает продукт целиком.

## Отклик: страница приходит готовой

Загрузчик `+page.server.ts` выполняется на сервере и отдаёт браузеру уже собранный HTML вместе с
данными. Классический одностраничный интерфейс сначала грузит бандл, потом просит у API данные,
потом рисует — то есть тратит два обращения там, где хватает одного.

Для требования `N1` это значит, что счёт идёт на время **одного** ответа сервера, а его видно
целиком: каждый ответ несёт заголовок `Server-Timing` с временем ожидания базы
(`docs/performance.md`). Замер показал, что узкое место — база, а не приложение: в любом измеренном
ответе `db;dur` занимает от 70 до 95 % времени. Это и есть довод в пользу выбора — цена самого
интерфейсного слоя в измеренных числах пренебрежимо мала. Конкретные числа и условия замера — в
[`performance.md`](performance.md); здесь их не дублируем, чтобы они не разошлись.

Размер бандла — то же самое рассуждение с другой стороны: у Svelte нет рантайма виртуального DOM,
компилятор превращает компонент в прямые операции над узлами. Цифры по весу сборки мы не мерили и
поэтому их не называем — см. [`performance.md`](performance.md) о том, что измерено, а что нет.

## Формы не перезагружают страницу, и это поведение по умолчанию

Form action — это обычная HTML-форма с обработчиком на сервере: браузер отправляет её сам, а
директива `use:enhance` перехватывает отправку, и страница обновляется без перезагрузки. Это и есть
`N2` — штатное поведение фреймворка, а не отдельная функция, которую пришлось бы писать.

Оговорка: **обходиться совсем без JavaScript продукт не обещает.** Выпадающие списки, поля даты и
выбор файла у нас свои, а не браузерные (`docs/development.md`, «Один контрол на задачу»), и без
скриптов они не работают. Выигрыш здесь не в отказоустойчивости к выключенному JS, а в том, что
отправка формы, её отказ и обновление данных на экране — один механизм на все десятки форм.

Для CRM это важнее, чем кажется: у продукта десятки форм (переход по стадии, пауза, помеха,
комментарий, загрузка файла, отметка документа, правка справочника), и каждая из них в SPA
означала бы свой обработчик состояния запроса, своей обработки ошибки и своего отката.

Проверка правил при этом **не удваивается**: схема Zod одна, и её читают и браузер, и сервер
(`sveltekit-superforms`). Подробности — [`development.md`](development.md), раздел «Формы».

## Один язык и один контракт

Весь код — TypeScript: сервисы, загрузчики, компоненты, тесты, скрипты сида и съёмки, имитаторы
систем заказчика. Контракты — Zod-схемы в `src/lib/contracts/`, и каждая работает в трёх местах
сразу:

1. проверяет форму в браузере и на сервере;
2. проверяет тело и параметры запроса к `/api/v1`;
3. **становится** описанием операции в OpenAPI 3.1 (`@asteasolutions/zod-to-openapi`).

Отсюда свойство, ради которого это и сделано: Swagger UI не может разойтись с поведением, потому
что собран из того же объекта, который запрос и проверяет. Требование `R2` закрывается по
построению, а не дисциплиной.

То же и с типами базы: схема Drizzle объявлена на TypeScript, и выборка возвращает типизированную
строку. Один язык от таблицы до кнопки означает, что переименование поля ломает сборку, а не
страницу у пользователя.

## Телефон и рабочий экран

Интерфейс рассчитан на две ширины — 390 и 1280. Правила вёрстки и токены темы —
[`design.md`](design.md).

Своей заслуги фреймворка здесь меньше, чем в остальных пунктах: так же можно сделать и на React.
Пункт стоит в списке потому, что требование `X4` есть, и ответ на него — одна разметка на оба
размера, а не отдельная мобильная версия.

## Чем платим

Честный список, без которого обоснование неполно:

- **Рынок разработчиков меньше.** React знают больше людей, и найти на поддержку человека со
  Svelte 5 труднее. Ответ: серверная часть — обычный TypeScript и SQL, и её читает любой
  бэкендер; специфика Svelte живёт в компонентах.
- **Runes — новая модель.** Svelte 5 не совместим по синтаксису со Svelte 4, и статьи в сети чаще
  описывают старый. Ответ: шпаргалка по runes и грабли — в [`development.md`](development.md),
  а `svelte-check` ловит старый синтаксис на гейте.
- **Экосистема компонентов беднее.** Готовых библиотек под Svelte меньше, чем под React. Ответ:
  примитивы (shadcn-svelte поверх bits-ui) завендорены в репозиторий — они наши файлы, и правятся
  как наш код.
- **Серверный рендеринг — это сервер.** Страница считается на каждое открытие, и нагрузка ложится
  на Node и базу, а не на браузер. Ответ: кэш чтений с явными областями и поколениями
  (`src/lib/server/cache/`, `docs/performance.md`).

## Карта кода для читателя с React

| React / Next.js                      | Здесь                                                             |
| ------------------------------------ | ----------------------------------------------------------------- |
| страница маршрута                    | `src/routes/<путь>/+page.svelte`                                  |
| `getServerSideProps` / server loader | `+page.server.ts`, функция `load`                                 |
| обработчик формы / server action     | `+page.server.ts`, объект `actions`                               |
| API route                            | `src/routes/api/v1/**/+server.ts`                                 |
| `_app` / корневой layout             | `src/routes/+layout.svelte`, `(app)/+layout.svelte`               |
| middleware                           | `src/hooks.server.ts` и `src/lib/server/hooks/*`                  |
| `useState`                           | `let x = $state(...)`                                             |
| `useMemo` / производное значение     | `const y = $derived(...)`                                         |
| `useEffect`                          | `$effect(...)` — нужен редко: производные считаются сами          |
| props компонента                     | `let { a, b } = $props()`                                         |
| `children`                           | сниппеты: `{@render children?.()}`                                |
| CSS-in-JS / CSS-модули               | Tailwind 4 с токенами темы в `src/app.css`, без `tailwind.config` |

Две вещи, которые сбивают чаще всего:

- **`$state` — не хук.** Ограничения «только на верхнем уровне компонента» у него нет, списка
  зависимостей — тоже: `$derived` пересчитывается сам по тому, что прочитал.
- **Файл с суффиксом `.server.ts` в браузер не попадает вовсе.** Это не соглашение, а граница
  сборки: секрет, случайно прочитанный в таком файле, наружу не уедет — но и `window` там нет.

и [`architecture.md`](architecture.md) (путь запроса и карта модулей).
