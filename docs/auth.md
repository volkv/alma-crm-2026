# Аутентификация и доступ

Кто перед системой, решает **внешний каталог учётных записей** — Keycloak, realm `lct`. Приложение
своих паролей не хранит и никогда не спрашивает: оно отправляет человека в каталог, проверяет его
ответ и заводит собственную серверную сессию. Что человек может делать — решают права роли
(`docs/access-matrix.md`), какие записи он при этом видит — область доступа.

Разделение простое: **каталог отвечает на вопрос «кто это», приложение — на вопрос «что ему
можно»**. Роль приходит утверждением токена и приводится к нему при каждом входе; иерархия
сотрудников и назначения на вузы живут только у нас — это операционные данные CRM, и каталог о них
ничего не знает.

## Вход: Authorization Code + PKCE

Библиотека — `oauth4webapi`: одна прямая зависимость, ноль транзитивных, и каждая проверка протокола
остаётся именованным вызовом в нашем коде, а не спрятана внутри обёртки.

| Шаг | Что происходит                                                                                                                                     | Где                                 |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------- |
| 1   | `POST /login` заводит `state`, `nonce` и проверочный код PKCE, кладёт их в Redis и отдаёт браузеру случайную ручку в cookie `lct_login` (10 минут) | `auth/flow.ts`                      |
| 2   | Браузер уходит на адрес авторизации realm с `code_challenge=S256`                                                                                  | `auth/oidc.ts::authorizationUrl`    |
| 3   | Каталог спрашивает имя входа и пароль, штатным `crm-admin` и `crm-lead` — ещё и одноразовый код (раздел «Второй фактор»)                           | Keycloak                            |
| 4   | Возврат на `GET /login/callback?code=…&state=…`; запись захода читается из Redis **и сразу удаляется** (`getdel`)                                  | `auth/flow.ts::takeFlow`            |
| 5   | Сверяется `state`, код меняется на токены, id-токен проверяется по ключам realm (JWKS): подпись, `iss`, `aud`, `nonce`, сроки                      | `auth/oidc.ts::exchangeCode`        |
| 6   | Роли realm отображаются на нашу роль, запись находится или заводится, открывается сессия                                                           | `auth/roles.ts`, `auth/identity.ts` |

Ни одна из проверок пятого шага не сокращается: каждая отвечает на свой вопрос — «токен ли это
нашего каталога», «нам ли он выдан», «наш ли это заход», — и снятая поодиночке ни одна не заметна,
пока её не используют.

**Что именно проверяется у id-токена.** `iss`, `aud`, `nonce`, `exp`/`iat`/`nbf` и наличие `sub`
читает обмен кода (`processAuthorizationCodeResponse`); **подпись** проверяется следом отдельным
вызовом `validateApplicationLevelSignature` по ключам realm из `jwks_uri`. Двумя вызовами, потому
что в `oauth4webapi` разбор утверждений и проверка подписи разнесены: первый к ключам realm не
ходит вовсе, и токен с верными утверждениями, подписанный чужим ключом, без второго вызова прошёл
бы насквозь. Ключи realm скачиваются один раз на процесс и обновляются сами, когда проверке
встречается незнакомый `kid`.

**Ограничение: до Keycloak внутри стека идёт HTTP.** Спецификация (OIDC Core 3.1.3.7, п. 6)
разрешает не проверять подпись id-токена, полученного прямо с token endpoint, — но только когда
канал до него защищён TLS. В `docker-compose.prod.yml` приложение ходит к каталогу по внутреннему
адресу сети стека без шифрования, поэтому условие не выполняется, и проверка подписи — не
формальность, а единственное, что отличает ответ каталога от ответа того, кто занял его адрес
внутри сети. Полностью вопрос закрывает TLS до каталога; проверка подписи — эшелон: она ловит
подмену одного из двух ответов и ошибку настройки, но не заменяет защищённый транспорт. Снаружи
стенд стоит за nginx с TLS (`docs/deployment.md`), и позиция для такой подмены требует уже
захваченного контейнера.

**Запись захода одноразовая.** `getdel` читает и удаляет одним действием, поэтому второй возврат с
тем же кодом сверять уже не с чем, — а повторно предъявленный код и есть его перехват.

**Адрес возврата собирается из `ORIGIN`, а не из `event.url`.** За обратным прокси в запросе стоит
внутренний адрес, и каталог отверг бы такой `redirect_uri` как незарегистрированный. `ORIGIN` —
единственное место, где сказано, как приложение видно снаружи.

**Публичный адрес каталога и адрес для сервера — разные вещи.** Каталог называет себя одним именем:
им он подписывается в `iss`, его же выдаёт в метаданных и по нему идёт браузер. Это
`OIDC_PUBLIC_URL` (основание) и `OIDC_ISSUER_URL` (realm целиком), и `KC_HOSTNAME` у Keycloak обязан
совпадать с ними — иначе `iss` «плавает» между опубликованным портом и именем контейнера, и токен не
проходит собственную проверку.

Сервер до этого адреса может и не доставать: в стеке приложение и каталог стоят в одной сети, где
опубликованный порт — чужой адрес. Тогда развёртывание задаёт необязательную `OIDC_INTERNAL_URL`, и
**серверные** запросы — метаданные, ключи подписи, обмен кода — уходят туда заменой публичного
основания на внутреннее (`rebaseEndpoint`). Адрес авторизации и адрес выхода не переносятся: по ним
идёт браузер. Проверка `iss` и `aud` остаётся по публичному имени: подменять то, чем токен подписан,
нельзя ни при каких удобствах. Что `OIDC_ISSUER_URL` начинается с `OIDC_PUBLIC_URL`, проверяет
конфигурация при старте.

## Второй фактор

Одноразовый код (TOTP) спрашивает каталог, а не приложение: приложение получает id-токен уже после
того, как Keycloak проверил и пароль, и код, и само второго фактора не видит и не проверяет.

| Кто                                            | Второй фактор                                                   |
| ---------------------------------------------- | --------------------------------------------------------------- |
| штатный `crm-admin` или `crm-lead`             | обязателен; не настроен — настройка на первом же входе          |
| `crm-user`                                     | по желанию: настроил сам — спрашивается на каждом входе         |
| демонстрационные записи стенда (группа `demo`) | не спрашивается никогда — задокументированное исключение стенда |

Устройство потока, исключение и проверка — `keycloak/README.md`, «Второй фактор». Почему
исключение есть и почему оно безопасно только на стенде — раздел «Демо-режим» ниже и
`docs/security.md`, «Принятые решения демонстрационного стенда». В промышленной установке
демонстрационных записей нет вовсе (`docker-compose.production.yml`), и исключать некого.

Потерял телефон — код сбрасывает администратор каталога (консоль Keycloak, «Учётные данные» →
удалить OTP); следующий вход снова начинается с настройки. Приложение в этом не участвует.

## Роли realm

| Роль realm  | Наша роль |
| ----------- | --------- |
| `crm-admin` | `admin`   |
| `crm-lead`  | `lead`    |
| `crm-user`  | `manager` |

Правила отображения (`auth/roles.ts`):

1. **Несколько ролей** — берётся старшая по порядку `admin` > `lead` > `manager`. Realm вправе
   выдать обе: руководитель, который ведёт свои вузы сам, — законная пара ролей, и отказ выглядел бы
   как поломка каталога.
2. **Незнакомая роль realm игнорируется.** Набор ролей сужается вместе с кодом, а не вместе с
   содержимым realm, — так же, как устроено чтение прав в `loadRolePermissions`.
3. **Ни одной известной роли** — вход отклоняется страницей «Доступ в систему вам не назначен»,
   событие журнала `auth.login` с исходом `denied`. Локальная запись при этом не заводится:
   пользователь без роли нам не сотрудник.

Роли `service` в realm нет и быть не может: машинный субъект не входит (`docs/access-matrix.md`,
раздел 1).

## Кем человек становится в системе

Ключ идентичности — `sub` токена в колонке `users.external_subject` (уникальная, допускает пустое
значение). Порядок (`auth/identity.ts`):

1. запись с этим `sub` есть — входит она;
2. `sub` неизвестен, но в токене есть **подтверждённая** почта, и такая почта уже числится за
   записью без внешнего субъекта, — записи проставляется `sub`, и человек входит **со своим прежним
   портфелем**. Без этого шага у каждого заведённого пользователя появился бы двойник, а его
   взаимодействия, назначения, ключи и след в журнале остались бы за записью, в которую уже никто не
   войдёт;
3. ни `sub`, ни подтверждённой почты не нашлось — заводится новая запись;
4. **неподтверждённая почта в связывании не участвует**: чужой адрес в токене иначе отдавал бы
   чужой портфель.

При каждом следующем входе почта, имя и роль приводятся к тому, что в токене: источник истины о
человеке — каталог. Иерархия (`manager_user_id`) и назначения на вузы источником истины в каталоге
**не** являются — их ведёт администратор в `/settings/users` и на карточке вуза.

**Машинный субъект не входит никогда.** Запись с ролью `service` не проходит вход ни при каких
утверждениях токена, даже если её почта совпала с почтой из токена: её права принадлежат ключам
обмена, и отдать их живому человеку значило бы отдать ему чужую систему.

## Деактивация

Учётная запись не удаляется никогда — на неё ссылаются журнал, назначения и взаимодействия.

| Что случилось                     | Что происходит                                                                   |
| --------------------------------- | -------------------------------------------------------------------------------- |
| Роль отозвали в realm             | следующий вход отклонён, запись помечается `is_active = false`, её сессии гаснут |
| Роль сменили в realm              | роль приводится к токену, сессии владельца гаснут — область была другой          |
| Администратор выключил запись     | сессии гаснут немедленно; вход закрыт до включения обратно                       |
| Администратор сменил руководителя | гаснут сессии и подчинённого, и обоих руководителей: у всех изменилась область   |

**Каталог перезавели.** Переимпорт realm, перенос установки, поднятый заново контейнер без тома —
и `sub` у тех же людей становится другим. Вход по новому субъекту запись не узнаёт, а связаться по
почте не может: связывание принимает только запись **без** субъекта, и ослаблять это правило
нельзя — иначе чужой адрес в токене отдавал бы чужой портфель. Человек получает отказ «ваша почта
уже числится за другой учётной записью системы», а в журнале остаётся `auth.login` с исходом
`denied`.

Решение остаётся за человеком: администратор нажимает «Отвязать» в `/settings/users`
(`users.manage`, событие `users.updated` с `changedFields: ['externalSubject']`), и следующий вход
связывает запись заново по подтверждённой почте — вместе со всем портфелем, назначениями и следом
в журнале. Сессии владельца при отвязке гаснут: связь, по которой они открыты, больше не та.

## Сессии

Сессия — своя, серверная. Cookie `lct_session` хранит только идентификатор — 256 случайных бит, — а
всё остальное лежит в Redis, поэтому сессию можно погасить с сервера. Подписывать такой cookie нечем
и незачем: подделать идентификатор, которого нет в Redis, бесполезно, а угадать его нельзя.

- `httpOnly`, `sameSite=lax`, `secure` при `https` в `ORIGIN`;
- срок по бездействию — настройка `session_idle_minutes` (по умолчанию 30 минут);
- предельный срок — `session_absolute_hours` (по умолчанию 12 часов), от него не спасает активность;
- продление не чаще раза в минуту: чаще дёргать Redis незачем;
- срок cookie переставляется тем же продлением, что и ключ в Redis: окно скользящее с обеих сторон.
  Пока срок ставился один раз при входе, браузер выбрасывал cookie через `session_idle_minutes`
  после входа независимо от работы человека, а продлённая сессия оставалась в Redis без того, чем
  её предъявить. Новый срок берётся с учётом остатка до предельного, поэтому cookie его не
  переживает;
- индекс `user_sessions:<id>` — множество сессий пользователя; по нему их гасят все разом;
- в записи сессии лежит id-токен того входа, которым она открыта: он нужен выходу и наружу не выходит.

Права и имя в сессии не хранятся: пользователь собирается из базы на каждый запрос
(`loadSessionUser`). Иначе снятое право продолжало бы действовать до конца рабочего дня.

## Область доступа

Область считается при сборке пользователя — то есть на каждом запросе — и оттуда копируется в
`ActorContext`:

```
scope(admin)   = всё
scope(lead)    = он сам ∪ подчинённые* по users.manager_user_id
scope(manager) = он сам
scope(service) = всё, но только на эндпоинтах обмена
```

Замыкание подчинённых считается рекурсивным CTE с ограничением глубины и встроенной защитой от
цикла (`cycle … set … using path`): проверка `users_manager_not_self` ловит только петлю длиной
один, а пару «A руководит B, B руководит A» база допускает.

Область — это множество **людей**, а не организаций: какие вузы видны, решают действующие
назначения, читаемые подзапросом в момент выборки. Поэтому переназначение действует немедленно и во
всех каналах сразу. Подробно — `docs/access-matrix.md`, разделы 1 и 2.

## Защита маршрутов

| Группа маршрутов | Кто пускает                       | Что происходит без сессии       |
| ---------------- | --------------------------------- | ------------------------------- |
| `(app)/**`       | хук `guard`                       | 303 на `/login?next=<куда шёл>` |
| `(auth)/**`      | никто: сюда и приходят без сессии | —                               |
| `/api/v1/**`     | ключ доступа, модуль API          | 401 в конверте JSON             |
| `/logout`        | только POST                       | 303 на `/login`                 |

Право на раздел проверяют загрузчики и сервисы: хук отвечает только на вопрос «есть ли тут
кто-нибудь». Перенаправление именно бросается, а не собирается ответом: у брошенного есть три разных
вида — заголовок `location`, конверт JSON для клиентского маршрутизатора и ещё один для формы через
`use:enhance`, — и выбирает между ними SvelteKit.

`next` не берётся на веру: `safeNextPath` принимает только путь внутри приложения — ни адреса с
протоколом, ни `//host`, ни `/\host`, ни управляющих символов.

## Лимит заходов с адреса

Пароли проверяет каталог, и подбор — его забота (`keycloak/README.md`, «Сроки и лимиты»: 30 неудач
закрывают учётную запись realm на минуту, и дольше минуты пауза не растёт — умолчание Keycloak в
четверть часа на общем стенде закрывало бы вход всем зрителям сразу, `docs/security.md`).

За нами остаётся то, чего каталог за нас не сделает: каждое нажатие «Войти» заводит в Redis запись с
состоянием, `nonce` и проверочным кодом PKCE. Без потолка анонимный поток нажатий забил бы Redis, не
назвавшись вовсе. Поэтому хук `rate-limit` считает заходы по адресу: 30 за 15 минут, на
демонстрационном стенде — в пять раз больше (десятки зрителей приходят из-за одного NAT). Исчерпав
окно, POST разворачивается обратно на страницу входа, и она объясняет словами, сколько ждать
(`auth/start-limit.ts`).

## Выход

`POST /logout` гасит **обе** сессии: нашу — в Redis, чтобы украденный идентификатор не пережил
нажатие, и сессию каталога — перенаправлением на его адрес выхода с подсказкой `id_token_hint`. Без
второго шага следующий вход каталог пропустил бы молча, по своей ещё живой куке, и человек на общем
компьютере оказался бы в чужой учётной записи, не увидев формы.

Только POST: выход меняет состояние, поэтому его нельзя получить по ссылке — ни предзагрузкой
браузера, ни картинкой на чужом сайте. Каталог недоступен — наша сессия всё равно погашена, и
человек видит страницу входа, а не ошибку.

`/settings/profile` гасит **все** наши сессии владельца, не трогая каталог: это средство от открытой
вкладки на чужой машине.

## Демо-режим

`DEMO_MODE=true` означает ровно две вещи: страница входа показывает карточку с именами
демонстрационных учётных записей, а сид заливает синтетические данные.

**Пароль на карточке.** Стенд публичный, и пароль его демонстрационных записей публичный тоже: он
написан и в `README.md`, и на самой карточке входа. Приложение его при этом по-прежнему не знает —
пароль живёт в realm, — а на экран попадает отдельной переменной окружения `DEMO_PASSWORD_HINT`,
которую читает загрузчик страницы входа. Разделение намеренное: показать чужой пароль — это решение
развёртывания, и оно принимается явным действием, а не выводится из того, что каталог рядом. Нет
переменной — карточка просто не называет пароль; есть, но испорчена (пробелы, длиннее 128
символов) — страница падает, а не показывает пустую строку вместо пароля
(`$lib/server/auth/demo-password.ts`). Границу демонстрации держат права, а не знание пароля, — и
штатный администратор стенда входит своей записью со своим паролем, которого нет нигде, и со
вторым фактором.

**Второго фактора у демонстрационных записей нет.** Общий пароль набирают десятки зрителей, и
код, привязанный к одному телефону, закрыл бы показ всем остальным. Исключение задаёт группа
каталога `demo`, а не режим приложения: в неё входят ровно три демонстрационные записи
(`keycloak/demo-users.json`), и установка без демо этого файла не импортирует.

Рядом с паролем стоит кнопка, которая кладёт его в буфер обмена: набирают-то его не здесь, а в форме
каталога, куда уводит «Войти», и перенабор по памяти посреди показа стоит дороже кнопки. Закрытый
настройками браузера буфер (и незащищённый адрес, где его не существует вовсе) карточка называет
словами и советует выделить пароль руками — молчаливой кнопки, после которой в форму нечего
вставить, здесь быть не должно.

**Демо-сессия — это граница, а не значок.** Запись с `is_demo` при включённом режиме не получает
одного права, какой бы ролью ни вошла (`DEMO_DENIED_PERMISSIONS` в `$lib/server/rbac`):

| Право                           | Почему                                                                   |
| ------------------------------- | ------------------------------------------------------------------------ |
| `integrations.manage_endpoints` | в поле адреса посетитель уводит запросы сервера стенда на указанный узел |

Всё остальное демонстрации остаётся: правка процесса, журнал обмена, настройки стенда, выгрузка
журнала, учёт согласий, управление учётными записями, выпуск ключей, обезличивание. Раздел,
закрытый от посетителя, читается им как раздел, которого в продукте нет.

Держится это не на доверии к посетителю, а на том, что стенд возвращается к эталону раз в сутки и
сброс доводит до эталона ровно те строки, которые эти права правят: выключенную или перевешенную
учётную запись возвращает сид (`restoreSeededAccounts`), выпущенный ключ уезжает вместе с таблицей
`api_keys`, обезличенные люди заливаются заново. Вычтенным остаётся только адрес — и не потому, что по
нему уводят запросы сервера: куда система ходит, проверяет `outboundAddressIssue`, дважды — при
сохранении и при отправке. Дело в том, что адреса и токены подключений живут в `app_settings`, а её
сброс не чистит и чистить не может: там же настройки самого стенда. Подменённый приёмник подписки и
адрес системы обучения остались бы подменены и после показа. Открыть право можно вместе со сбросом
ключей интеграций до эталона — до тех пор оно вычтено.

Граница проходит по правам, а не по интерфейсу, и ставится в одном месте — `loadSessionUser`, через
которое собирается действующее лицо и для браузера, и для ключа доступа: спрятанной кнопки хватает
ровно настолько, насколько её хватает от `curl`.

Что ещё меняет режим:

- демонстрационную запись нельзя выключить: ею входят все, кто открыл стенд, а включить обратно
  оттуда же будет некому;
- стенд сбрасывается к эталонному набору — кнопкой администратора или по расписанию, настройка
  `demo_reset_schedule` (`docs/admin.md`); полоса демо-режима называет час;
- журнал огрубляет адреса и клиентов для таких сессий;
- лимит заходов с адреса поднимается впятеро;
- `/settings/profile` не даёт завершить сессии общей учётной записи;
- штатному администратору стенда остаётся всё, что отняли у демонстрации.

Вне демо-режима столбец `is_demo` ни на что не влияет: это обычная учётная запись.

## Настройки и переменные окружения

| Что                      | Где                                                |
| ------------------------ | -------------------------------------------------- |
| `session_idle_minutes`   | `/settings/general`                                |
| `session_absolute_hours` | `/settings/general`                                |
| `login_banner`           | `/settings/general`                                |
| `demo_reset_schedule`    | `/settings/general`; сброс стенда по часам сервера |
| `DEMO_PASSWORD_HINT`     | окружение; общий пароль стенда на карточке входа   |
| `OIDC_ISSUER_URL`        | окружение; адрес realm, он же `iss` токенов        |
| `OIDC_PUBLIC_URL`        | окружение; адрес каталога для браузера             |
| `OIDC_CLIENT_ID`         | окружение; клиент realm                            |
| `OIDC_CLIENT_SECRET`     | окружение; секрет конфиденциального клиента        |

Политик пароля, блокировки и второго фактора в настройках нет: правила к паролю задаются в realm
(`passwordPolicy`, `keycloak/README.md`), второй фактор — потоком входа realm `browser-otp`.

## Как позвать сервис из загрузчика или действия

```ts
import { actorFromEvent } from '$lib/server/actor';
import { requirePermission } from '$lib/server/rbac';

export const load = async (event) => {
	const ctx = actorFromEvent(event);
	requirePermission(ctx, 'organizations.read');

	return { organizations: await listOrganizations(ctx, query) };
};
```

Контекст собирает транспорт, сервис принимает `(ctx, input)` и сам подмешивает область в условие
выборки. Сервис не смотрит в `locals`, не читает заголовки и не решает, кто перед ним, — тогда одно
и то же действие ведёт себя одинаково из браузера, из API и из скрипта.

## Что пишется в журнал

| Событие              | Когда                                                                           |
| -------------------- | ------------------------------------------------------------------------------- |
| `auth.login`         | удачный вход; `denied` — отказ без роли, выключенной записи, машинному субъекту |
| `auth.logout`        | выход и «завершить все сессии»                                                  |
| `users.created`      | запись заведена первым входом                                                   |
| `users.updated`      | запись связана с каталогом; смена руководителя                                  |
| `users.role_changed` | каталог сменил роль                                                             |
| `users.deactivated`  | роль отозвана в каталоге или запись выключена администратором                   |
| `users.activated`    | запись включена обратно                                                         |

Отказ по праву пишется формой `requirePermission(ctx, key, denial)` — той же, что используется
везде. Отказы транспорта публичного API (401 и 429 безымянному вызывающему) пишутся агрегированно,
одной строкой в минуту на адрес: иначе перебор ключей забивал бы журнал.
