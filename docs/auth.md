# Аутентификация и доступ

Кто вошёл, как это проверяется на каждом запросе и что защищает форму входа. Права и область
доступа описаны отдельно — в `data-model.md`, раздел «Права и область доступа».

## Пароли

`@node-rs/argon2`, алгоритм argon2id с параметрами по умолчанию библиотеки: 19 МиБ памяти, два
прохода, один поток. Параметры записаны в самой строке хеша, поэтому их можно поднять, не трогая
уже сохранённые пароли. В базе лежит только хеш (`users.password_hash`), наружу он не выходит
никогда.

Требования к паролю задаёт настройка `password_policy` (`minLength`, `minClasses`), а проверяет
`validatePassword(policy, password)` из `$lib/server/auth/password`: длина и число классов символов
из четырёх — строчные буквы, прописные, цифры, всё остальное. Классы считаются по свойствам
Юникода, поэтому кириллица работает так же, как латиница. Функция возвращает список претензий
по-русски; ошибку из них делает тот, кто вызвал.

Проверка пароля несуществующего пользователя всё равно считает argon2 — по фиктивному хешу.
Иначе по времени ответа перебором узнают, какие адреса заведены в системе.

## Сессии

Cookie `lct_session` хранит только идентификатор: 32 случайных байта в base64url. Всё остальное —
в Redis:

| Ключ                     | Что в нём                                                    |
| ------------------------ | ------------------------------------------------------------ |
| `session:<id>`           | JSON: `userId`, `createdAt`, `lastSeenAt`, `ip`, `userAgent` |
| `user_sessions:<userId>` | множество идентификаторов сессий этого пользователя          |

Cookie — `httpOnly`, `sameSite=lax`, `path=/`; `secure` включается, когда `ORIGIN` начинается с
`https://` (на http-происхождении такая cookie была бы невидима для самого приложения). Подписывать
её нечем и незачем: подделать идентификатор, которого нет в Redis, бесполезно, а угадать 256 бит
нельзя.

Два срока жизни, оба из настроек:

- `session_idle_minutes` — бездействие. Это TTL ключа в Redis, то есть срок соблюдается сам собой.
  Активность продлевает сессию, но не чаще раза в минуту: писать в Redis на каждый запрос незачем.
- `session_absolute_hours` — предельный срок от `createdAt`, сколько бы активности ни было. Проверяется
  при чтении сессии; просроченная удаляется вместе с записью в множестве пользователя.

`revokeAllSessions(userId)` гасит все сессии разом — при смене пароля и при деактивации
пользователя. И то и другое должно действовать немедленно, а не со следующего входа.

Пользователь запроса (`SessionUser`) собирается из базы **на каждый запрос**, а не хранится в
сессии: роль, права и признак активности меняются без участия владельца сессии. Права роли берутся
из `loadRolePermissions` с кэшем на процесс.

## Защита маршрутов

Три хука в `src/lib/server/hooks`, порядок задан в `src/hooks.server.ts`:

- `session` — читает cookie, продлевает сессию, кладёт `locals.user`. Cookie, которая больше ни во
  что не разрешается, сбрасывается тут же — заголовком на самом ответе: ответ гвардии собран в
  хуке, и отложенные в `event.cookies` до него не доходят.
- `guard` — всё под `(app)` требует сессии. Без неё — `303` на `/login?next=<путь>`, собранный
  хуком (`hookRedirect`), а не брошенный `redirect()`: иначе на ответе не оказалось бы ни
  заголовков безопасности, ни `x-request-id`. Маршрут `/api/v1` не трогает: там ключи и ответы в
  JSON, это забота модуля API. Несуществующий маршрут (`route.id === null`) не перенаправляется —
  404 не должен зависеть от того, вошёл ли кто-то.
- `rate-limit` — считает POST на маршруты `(auth)`; исчерпавший лимит POST разворачивает обратно на
  страницу, с которой он пришёл, — она и объясняет отказ.

Правило — группа маршрутов, а не список путей: страница, добавленная в `(app)`, защищена тем, что
она в `(app)`. Права на конкретное действие проверяют загрузчики и сервисы (`requirePermission`),
это отдельный вопрос от «вошёл ли вообще».

`next` из адреса проверяет `safeNextPath`: принимается только путь внутри приложения. `//evil.example`
браузер понимает как адрес с протоколом текущей страницы, `https://…` — как чужой сайт; и то и
другое заменяется на `/`.

## Блокировка перебора

Два счётчика в Redis, каждый про своё.

**По паре «учётная запись и адрес»** — `login_fail:<почта>:<адрес>`. Настройка `lockout_policy`:
после `attempts` неудач вход в эту учётную запись **с этого адреса** закрыт, пока живёт ключ, а
живёт он `minutes` минут с **последней** неудачи. Пара, а не одна учётная запись: иначе чужой
перебор запирал бы владельца снаружи — достаточно было бы стучаться в его почту наугад. Удачный
вход счётчик снимает. Отказ по блокировке не доходит до проверки пароля и пишет в журнал
`auth.locked` с исходом `denied`.

**По адресу** — `login_ip:<адрес>`: не больше 30 POST на маршруты `(auth)` за 15 минут, окно
фиксированное от первой попытки. Считаются только POST: открыть страницу входа бесплатно.

Удачный вход счётчик адреса **снимает**. Он считает перебор, а вошедший ничего не перебирал: без
этого класс или жюри за одним NAT — для счётчика это один адрес — выбирает общий лимит обычной
работой и упирается в отказ ни за что. Подбора это не открывает: чтобы снять адресный счётчик,
нужен верный пароль, а счётчик по паре «учётная запись и адрес» живёт отдельно и от удачного входа
в **чужую** запись не сбрасывается.

При `DEMO_MODE=true` порог адреса вместо 30 равен 150 (`ADDRESS_ATTEMPT_LIMIT` ×5): стенд смотрят
десятками из-за одного адреса. Порог остаётся константой в `$lib/server/auth/lockout`, а не
настройкой: настройки правит администратор из интерфейса, а демонстрация этого права и не имеет.

Отказ по адресу — не голый 429: хук `rate-limit` разворачивает POST обратно на ту же страницу входа
(303, с сохранением `next`), а её загрузчик спрашивает `addressLimitState` и вместо формы и кнопок
показывает «Слишком много входов с этого адреса. Попробуйте через N минут». Код ответа человеку
ничего не объясняет, а ждать ему всё равно придётся — и он должен знать сколько.

Адрес берётся из `event.getClientAddress()`. За обратным прокси adapter-node читает его из
заголовка, названного в `ADDRESS_HEADER` (в `docker-compose.prod.yml` — `X-Forwarded-For`), с
глубиной `XFF_DEPTH`. Флаг `TRUST_PROXY` говорит приложению, что оно стоит за прокси. Включать его,
когда приложение доступно напрямую, нельзя: клиент сам выберет себе адрес — и для журнала, и для
счётчиков.

Отказы намеренно неразличимы: «нет такого пользователя», «пароль не подошёл» и «учётная запись
выключена» дают один текст «Неверная почта или пароль». Иначе форма входа превращается в справочник
заведённых адресов.

## Демо-режим

`DEMO_MODE=true` включает на странице входа блок с кнопками «Войти как …» — по одной на роль, для
которой в базе есть учётная запись с `users.is_demo = true`. Вход по такой кнопке проходит без
пароля. При `DEMO_MODE=false` действия `?/demo` для приложения не существует — 404, кнопок на
странице нет, а запись с `is_demo` становится обычной учётной записью.

### Демо-сессия — это граница, а не значок

Сессия считается демонстрационной, если открыта на записи с `is_demo` при включённом режиме —
**кнопкой или паролем, безразлично**: учётная запись от способа входа общей быть не перестаёт.
Признак живёт в `SessionUser.isDemo`, а собирается он в `loadSessionUser` — там же, где права.
Одно место на оба входа: и на браузерную сессию, и на ключ доступа, владельцем которого числится
демонстрационная запись.

Такая сессия не получает пяти прав, какой бы ролью ни вошли (`demoSessionPermissions` в
`$lib/server/rbac`):

| Право              | Почему                                                                       |
| ------------------ | ---------------------------------------------------------------------------- |
| `users.manage`     | Заведённый администратор переживает демонстрацию и пускает в систему дальше  |
| `api_keys.manage`  | Выпущенный ключ — то же самое, только без формы входа                        |
| `settings.write`   | Баннер, сроки сессий и политики — общие; правка меняет стенд для всех        |
| `stages.configure` | Маршруты и стадии — устройство процесса, а не данные, которые показывают     |
| `audit.export`     | Выгрузка уносит адреса, клиентов и историю действий всех, кто заходил раньше |

Вычитание — по правам, а не по разметке: `can()` читают и загрузчики страниц, и сервисы, и публичный
API, поэтому спрятанной кнопки хватило бы ровно настолько, насколько её хватает от `curl`. Разделы
настроек пропадают из меню сами — оно собирается из тех же прав.

Читать журнал демонстрация может (`audit.read` остаётся): это часть того, что показывают. Но адрес
и строка клиента в нём — настоящие, их оставил живой посетитель, поэтому демо-сессии они приходят
огрублёнными: адрес до первых двух октетов (`198.51.*.*`), клиент до семейства браузера
(`Chrome`, `Firefox`, …) или «скрыто». Маскирует `maskAuditEvent` из `$lib/contracts/audit`,
вызывает — загрузчик `/audit`.

Демонстрационную запись **нельзя выключить**, пока режим включён (`deactivateUser` отвечает
`ConflictError`, кнопки в списке пользователей у такой строки нет). Ею входят все, кто открыл стенд,
а включить её обратно было бы некому: кнопка «Войти как …» исчезает вместе с записью, а раздел
пользователей самой демонстрации не принадлежит.

Отсюда следует, что на стенде с `DEMO_MODE=true` управлять пользователями, ключами и настройками
может только **не** демонстрационная учётная запись — обычная запись оператора, входящая по паролю.
Завести её изнутри демонстрации невозможно, поэтому её заводит сид, и только когда ему дали пароль:
`SEED_STAFF_ADMIN_PASSWORD` — `admin@staff.lct-crm.local`, «Администратор стенда», роль
администратора, `is_demo = false` (`scripts/seed/users.ts`, подробно — `seeds.md`). Тем же способом
и с тем же паролем получает своего администратора прогон e2e (`e2e/global-setup.ts`, `STAFF_ADMIN`).

### Что ещё меняет режим

Демонстрационными записями пользуются десятки незнакомых друг с другом людей, поэтому при включённом
демо-режиме блокировка по паре «учётная запись и адрес» на них не действует: чужая опечатка не
должна закрывать вход остальным. Лимит по адресу остаётся, но поднят впятеро — он защищает не
учётную запись, а систему.

В оболочке приложения при `DEMO_MODE` висит полоса «Демо-режим: данные синтетические»: флаг едет в
`AppShell` из `(app)/+layout.server.ts`.

## Настройки, которые всё это меняют

Все — из `app_settings` через `getSetting`, значения по умолчанию в `$lib/server/settings`:
`login_banner` (заголовок и текст над формой входа), `session_idle_minutes`,
`session_absolute_hours`, `password_policy`, `lockout_policy`.

## Как позвать сервис из загрузчика или действия

`ActorContext` собирает транспорт, а не сервис:

```ts
import { actorFromEvent } from '$lib/server/actor';
import { toActionFailure } from '$lib/server/http';

export const actions = {
	deactivate: async (event) => {
		const ctx = actorFromEvent(event);

		try {
			await deactivateUser(ctx, event.params.id);
		} catch (error) {
			// ValidationError → 400, ForbiddenError → 403, NotFoundError → 404,
			// ConflictError → 409. Незнакомая ошибка летит дальше и станет 500.
			return toActionFailure(error);
		}

		redirect(303, resolve('/settings/users'));
	}
};
```

В `+page.server.ts` под `(app)` `locals.user` уже не `null` — до загрузчика отработал `guard`.
Проверять право всё равно надо: вошёл — не значит «можно».

## Что пишется в журнал

`auth.login` (успех; у демонстрационной сессии с `details.demo` — признак берётся у самой сессии, а
не у способа входа), `auth.login_failed` (неудача), `auth.locked` (отказ по блокировке),
`auth.logout`, `auth.password_changed`, `users.created`, `users.activated`, `users.deactivated`,
`audit.exported` (в том числе с исходом `denied`, когда выгрузку запросили без права на неё).
Неудача и отказ пишутся отдельным соединением — транзакция вокруг них обычно откатывается, а знать о
попытке нужно именно тогда. Почты в подробностях нет: в неизменяемый журнал персональные данные не
попадают, там только `userId`.

## Выход

POST на `/logout` (форма в меню учётной записи). Не ссылка: выход меняет состояние, поэтому его не
должны уметь дёргать предзагрузка браузера или картинка на чужом сайте. Сессия гасится в Redis, а не
только в cookie.
