# Отклик и нагрузка

Три требования задания говорят про скорость: отклик интерфейса не дольше
секунды (`N1`), пятьдесят одновременных пользователей (`N6`), десять
одновременных отчётов (`N7`).

Это **второй замер**. Первый (2026-09-18, днём, коммит `ee28304`) показал, что
отчёт за учебный год стоит секунду и всё это время занимает база; по его выводам
экран отчёта переписан на агрегаты в SQL, добавлены индексы окна стадий и кэш
списков фильтров и действующей редакции процесса (`5c75e7b`). Здесь — числа
после этих правок, рядом со старыми, и честный ответ, что они дали.

**Все числа сняты 2026-09-18 вечером** на сборке рабочего дерева на коммите
`d476b2d` (`edc070d` плюс переименование переменной на странице направлений — на
измеряемые пути оно не влияет). Колонка «до» — тот же документ прошлой редакции,
прогон на `ee28304`.

Между двумя замерами в те же экраны приехало и новое — и это важно для чтения
таблиц: `d476b2d` не равен «`ee28304` плюс оптимизация». На карточку
добавились договоры и позиции лицензий, в отчёт — drill-down, воронка по
пространствам, колонка программ и подписи значений на диаграммах, на стадию
подписания — проверка отметки по документу. Часть разницы в числах — цена этих
возможностей, и разделить её замером нечем.

## Как мерили

Методика та же, что в первом замере: тот же стенд, тот же набор, те же сценарии
и тот же порог в сценарии k6. Что в ней изменилось намеренно — отдельным
списком ниже.

### Стенд

Отдельный стек в своём проекте Compose (`lct-load`), поднятый производственным
наложением: тот же образ приложения, тот же режим `production`, те же потолки
памяти. Стек не пересекается ни портами, ни томами со стеком разработки —
иначе замер шёл бы по базе, которую в это же время меняет прогон e2e.

| Что             | Значение                                                       |
| --------------- | -------------------------------------------------------------- |
| Машина          | AMD Ryzen AI 7 350, 8 ядер / 16 потоков, 30 ГиБ памяти, Linux  |
| Docker          | 29.8.1                                                         |
| k6              | v2.2.0, контейнером `grafana/k6` в сети хоста                  |
| Приложение      | образ проекта, Node 24, `adapter-node`, потолок памяти 512 МиБ |
| PostgreSQL      | 17-alpine, потолок памяти 1 ГиБ                                |
| Redis           | 8-alpine, потолок 128 МиБ                                      |
| Gotenberg       | 8, потолок 768 МиБ                                             |
| Каталог записей | Keycloak 26.7.4, потолок 768 МиБ                               |
| Дата прогона    | 2026-09-18, 19:56–20:19                                        |

### Данные

Нагрузочный набор (`node scripts/seed/index.ts --load`,
[`seeds.md`](seeds.md)): 300 вузов, 3000 взаимодействий, 16 500 записей стадий,
22 800 комментариев, 17 100 правок плана — ровно тот же, что в первом замере,
без единой правки. Все вузы ведёт один КАМ, поэтому подзапрос области доступа
считается по трёмстам действующим назначениям, а не по трём.

Статистика таблиц к началу прогона собрана: автоанализ прошёл по всем семи
таблицам набора через минуту после заливки, за три минуты до первого сценария.
Мерить в окне, пока PostgreSQL ещё не посчитал статистику, значит мерить планы
запросов, которых в работающей системе не бывает.

### Чем мерили

`Server-Timing` на каждом ответе приложения — три числа: `db` (сколько запрос
ждал базу), `app` (сколько осталось приложению), `total`. Это не отладочный
режим и не переключатель: заголовок стоит на каждом ответе всегда, в том числе
на стенде, и по нему видно, где время, без профилировщика и без доступа к
машине.

Сценарии k6 — в `scripts/load/`: `browse.js` (рабочий круг сотрудника:
список → карточка → переход по процессу с комментарием → смена фильтра отчёта,
три роли сразу), `reports.js` (десять человек одновременно просят отчёт за год
и забирают его файлом), `cache.js` (стоимость повторного открытия). Вход в
систему настоящий — код авторизации с PKCE через форму каталога учётных
записей; он происходит один раз на VU и в измеряемые операции не входит.

### Что в методике изменилось с первого замера

1. **PDF меряется за тот же учебный год, что и XLSX.** В первом замере у него
   был свой, укороченный период: выгрузка отказывалась собирать больше двух
   тысяч строк. Отказ снят, PDF всегда сводка, и мерить его на квартале больше
   незачем. Строку «PDF» в таблице `N7` поэтому **нельзя** читать как «стало
   хуже»: это другой объём работы.
2. **Ступеней нагрузки стало четыре** — 5, 15, 30 и 50 VU. Тридцать добавлены
   затем, чтобы ответить не «держится или нет», а «до скольких пользователей».
3. **Пятьдесят прогнаны дважды** — на менее и на более занятой машине. Обе
   строки в таблице: одна показывает систему, другая — цену соседей по машине.
4. **Разбивка по шагам сценария.** Каждый прогон, кроме сводки, оставляет сырые
   точки (`<сценарий>-raw.json.gz`), и `run.sh breakdown` раскладывает их по
   меткам запроса. Это понадобилось, потому что в метрике «переход по процессу»
   лежат два разных шага — сам переход и комментарий, когда переходить уже
   нечему.
5. **Замер кэша охватывает и экран отчёта**, не только карточку: списки
   фильтров и действующая редакция процесса теперь тоже лежат в Redis.

### Чем сценарий отличается от прошлого раза не по своей воле

**Переходов в наборе стало меньше, и они кончаются.** Стадия подписания
требует теперь утверждённой отметки по документу дела, поэтому карточки,
стоящие на ней, из списка «куда шагнуть» выпали: из 2600 действующих карточек
шагнуть вперёд можно с 1292, а не с 1615. Хуже того, каждый прогон эти карточки
тратит — переведённая карточка уходит на стадию, с которой шагнуть уже нельзя.
По ступеням лестницы это видно: 1266 → 1210 → 892 → 46 → 16 доступных
переходов. Поэтому в первых трёх прогонах шаг «переход» — действительно переход
(на пятидесяти VU: 846 переходов и 67 комментариев), а в четвёртом и пятом —
почти целиком комментарий. В таблицах это помечено, а для чтения годятся
строки первых трёх ступеней и первого прохода пятидесяти.

### Фоновая нагрузка: граница этого замера

Машина общая: в то же время на ней шли сборки и прогоны тестов этого проекта
(в том числе в контейнерах) и работали контейнеры соседних. Средняя загрузка по
ступеням — из `uptime` до и после каждого прогона:

| Ступень                      | load average до | load average после |
| ---------------------------- | --------------- | ------------------ |
| 5 VU, 1 мин                  | 2,85            | 3,07               |
| 15 VU, 2 мин                 | 3,07            | 5,85               |
| 50 VU, 4 мин (первый проход) | 5,85            | 20,13              |
| 10 отчётов, 2 мин            | 20,13           | 13,81              |
| Кэш, 1 VU                    | 13,81           | 2,21               |
| 30 VU, 3 мин                 | 2,05            | 21,14              |
| 50 VU, 4 мин (второй проход) | 21,14           | 26,73              |

Часть этих чисел — сам прогон: пятьдесят VU k6 рядом со стендом на одной машине
поднимают загрузку до двадцати сами по себе. Но не вся: во втором проходе
пятидесяти к ним прибавились чужие тесты, и это видно по числам — он хуже
первого по всем операциям. Отдельного нагрузочного стенда у команды нет,
поэтому **числа на 30 и 50 VU — это «не хуже, чем»**, а не точная величина.
Числа на 5 и 15 VU и однопользовательский замер кэша этим искажены
незначительно.

Дальше — четыре ступени. В каждой таблице `p50 / p95 / max`, слева прошлый
замер (`ee28304`), справа этот (`d476b2d`).

### Что это значит

**`N6` выполняется.** Пятьдесят одновременных пользователей система
обслуживает без единого отказа: очередь не рвётся, соединения к базе не
кончаются, память приложения остаётся в пределах 274 МиБ из 512. Пропускная
способность — 4865 запросов за четыре минуты, 19,5 запроса в секунду.

**`N1` по списку, карточке и переходу выполняется на пятнадцати пользователях и
упирается в границу на тридцати.** Прошлый замер проходил границу так же на
пятнадцати, но впритык (p95 377–411 мс); теперь на пятнадцати запас
пятикратный, а промах случается только на тридцати и только десятыми долями
(1079 и 1147 мс при пороге 1000). На пятидесяти требование не выполняется:
девяносто пятая доля открытия списка 2,0 с, карточки 2,7 с.

**Отчёт за учебный год не укладывается в секунду ни при какой нагрузке.** У
одного пользователя он стоит 0,92 с, и 0,90 с из них — ожидание базы (замер
`Server-Timing`, раздел `F13`). Это не деградация под нагрузкой, а цена одной
выборки.

**Где именно время на пятидесяти.** `docker stats` во время прогона: PostgreSQL
берёт до 1356 % процессора (13,5 ядра из шестнадцати) и упирается в свой потолок
памяти в 1 ГиБ, приложение — до 172 % (1,7 ядра) и 274 МиБ из 512. Второй
экземпляр приложения тут не поможет: занята база.

## N7: десять одновременных отчётов

Полный прогон: 10 VU, 2 минуты, 117 проходов, 528 запросов, **ни одной ошибки**.
Пауз между запросами в этом сценарии нет намеренно: десять одновременных
выгрузок — не поведение человека, а худший случай, ради которого требование и
написано.

| Что                          | До: p50 / p95 / max   | После: p50 / p95 / max |
| ---------------------------- | --------------------- | ---------------------- |
| Экран отчёта за учебный год  | 2038 / 2559 / 3021 мс | 2088 / 2528 / 2854 мс  |
| Выгрузка XLSX за учебный год | 3176 / 4002 / 4265 мс | 2575 / 3252 / 3584 мс  |
| Выгрузка JSON за учебный год | 2189 / 2585 / 3016 мс | 2273 / 3041 / 3546 мс  |
| Выгрузка PDF за учебный год  | **отказ по объёму**   | 3484 / 4080 / 6059 мс  |

**`N7` выполняется целиком** — в отличие от прошлого замера, где оставалась
незакрытой часть «pdf за большой период». Тогда выгрузка в PDF отказывалась
собирать больше двух тысяч строк, а в годовом срезе портфеля их три тысячи.
Теперь PDF всегда сводка: условия выборки, итоги, числа воронки и динамики
таблицами и первые 500 строк с пометкой «показаны первые 500 из 3028; полная
таблица — в XLSX и JSON». Десять человек одновременно получают такой файл за
3,5 с в середине и 4,1 с на девяносто пятой доле.

Из них около секунды — сборка самого PDF: Gotenberg отработал 120 запросов,
все двухсотые, p50 1118 мс, p95 1684 мс, файл в среднем 541 КиБ. Остальное —
выборка и сборка страницы на печать.

Выгрузка XLSX стала быстрее на пятую часть (p95 4002 → 3252 мс) — это тот самый
случай, где правка отчёта видна прямо: сборка книги берёт набор строк целиком, и
дешевле стала именно выборка.

Секунды здесь нет и не обещано: `N1` говорит про отклик интерфейса, а выгрузка
за год — это файл, который собирают и ждут. Ориентир продукта — до десяти
секунд на выгрузку в пределах порогов объёма ([`reports.md`](reports.md)), и он
выдержан с запасом втрое.

## F13: кэш повторного открытия

Кэш живёт в Redis; область доступа — в ключе, поколение — для обесценивания,
короткий срок жизни. Что кэшируется: общая половина карточки, лента
комментариев и история правок плана, подбор из справочника для форм, списки
фильтров отчёта и действующая редакция процесса.

Сорок пар «холодное открытие — повторное» по карточкам и три по экрану отчёта,
один пользователь, числа из `Server-Timing`:

| Что                               | До: первое / повторное | После: первое / повторное |
| --------------------------------- | ---------------------- | ------------------------- |
| Обычная карточка (4 комментария)  | 75,4 → 67,0 мс (−11 %) | 65,9 → 66,5 мс (0 %)      |
| Долгая карточка (40 комментариев) | 76,3 → 71,0 мс (−7 %)  | 69,5 → 68,4 мс (−2 %)     |
| Экран отчёта за год               | не мерилось            | 924,6 → 889,9 мс (−4 %)   |

Первое открытие карточки стало дешевле само по себе — 65,9 мс против 75,4, —
а **разница между первым и повторным исчезла**. Объяснение простое и
неприятное: кэш карточки покрывает три чтения из девяти, а за время вехи
карточка обросла тем, что в кэш не попадает, — договорами и позициями лицензий,
слепком доказательства исполнения стадии, отметками по документам. Ожидание базы
у повторного открытия — 52,6 мс из 66,5, и это те самые чтения, которых кэш не
касается. Как средство от нагрузки он по-прежнему работает (запросов к базе
меньше), но как ускоритель одного открытия — уже нет.

Экран отчёта: повторное открытие дешевле на 35 мс — столько стоят семь выборок
списков фильтров и чтение действующей редакции. На фоне 900 мс самой выборки это
4 %, и ждать большего было неоткуда: кэш снимает справочники, а не отчёт.

Холод для отчёта приходится ждать: поколение этих записей не зависит от данных
отчёта, обесценивает их запись в справочник, публикация редакции или срок жизни
(30 и 60 секунд). Поэтому пар всего три и перед каждой сценарий молчит 65
секунд.

**Чего в кэше нет: контактов людей.** Стороны карточки читаются из базы каждый
раз, потому что сериализатор контактов не только маскирует их по правам, но и
оставляет след просмотра персональных данных, — ответ из Redis этот след
потерял бы. Проверено тестом: два открытия карточки дают два события
`people.pii_viewed`.

## Что дала каждая оптимизация

Правка `5c75e7b` была из шести частей. Что по замеру видно про каждую:

1. **Экран отчёта не читает всю выборку.** Итоги, воронка, динамика и разрезы
   считаются агрегирующими запросами по тем же условиям `where`, что у таблицы
   (`reports/aggregate.ts`), а признаки строки — только для показанных
   пятидесяти. До правки шесть боковых выборок считались на каждую из трёх
   тысяч строк годового отчёта. **Что видно:** выгрузка XLSX, которая берёт
   набор целиком, стала быстрее на пятую часть; экран отчёта у одного
   пользователя — не изменился (0,91 → 0,92 с). Значит, дорога не сборка
   признаков, а сама выборка по окну стадий.
2. **Подзапросы на основную сторону взаимодействия сведены в один боковой
   join** (`reports/conditions.ts`): было четыре подзапроса на строку, стало
   одно соединение на выборку. Отдельным числом не измеряется, входит в
   предыдущий пункт.
3. **Индексы под выборку отчёта** — миграция `drizzle/0013_report_window_indexes.sql`:
   окно записи на момент среза, диапазон ухода со стадии, вычитание пауз. **Что
   видно:** ожидание базы у годового отчёта осталось прежним (875 → 904 мс), то
   есть индексы сняли не главную часть работы. Что именно ест эти 0,9 с, надо
   смотреть планом запроса — это первый пункт списка «что дальше».
4. **Кэш списков фильтров отчёта** (семь выборок на каждое открытие раздела) —
   **что видно:** 35 мс на повторном открытии, 4 % от времени экрана.
5. **Кэш действующей редакции процесса** (`cache/process.ts`) — её читают
   карточка, список и доска. **Что видно:** это, по всей видимости, и есть
   источник главного выигрыша замера — падение p95 списка, карточки и перехода
   вдвое с лишним на пятнадцати пользователях. «По всей видимости» — потому что
   правки ехали одним коммитом, и отделить вклад одного кэша от вклада другого
   этот замер не может.
6. **PDF отчёта не отказывает по объёму** — **что видно:** годовой отчёт в PDF
   собирается за 3,5 с и требование `N7` закрыто целиком.

Чего правка **не** трогала: сборку карточки (девять чтений подряд) и число
экземпляров приложения.

## Что делать дальше

По порядку убывания эффекта — это выводы замера, а не план работ.

1. **План запроса годового отчёта.** Замер закрыл вопрос «кто виноват»: не
   сборка признаков строк и не приложение, а сама выборка — 0,90 с ожидания
   базы из 0,92 с ответа. Следующий шаг не «оптимизировать отчёт», а прочитать
   `explain (analyze, buffers)` среза и движения на этом наборе и посмотреть,
   что стоит дороже всего: окно `stage_entries`, вычитание пауз или подзапрос
   области доступа.
2. **Второй экземпляр приложения не нужен.** На пятидесяти пользователях
   приложение занимает 1,7 ядра, база — 13,5. Всё, что дешевле делать в базе,
   уже там; дальше помогает не второй Node, а меньше работы для PostgreSQL.
3. **Карточка собирается девятью чтениями подряд**, и кэш покрывает три из них.
   Раз разница между первым и повторным открытием исчезла, кэш карточки в
   нынешнем виде ничего не ускоряет — либо расширять его на состояние стадии и
   сводку «что могу сейчас», либо признать, что его смысл только в снятии
   запросов под нагрузкой.
4. **Область доступа считается подзапросом на каждой выборке.** На трёхстах
   действующих назначениях это заметно; отдельным замером вклад не выделен, но
   это единственное условие, которое одинаково стоит в списке, карточке и
   отчёте.

## Чего не измеряли и почему

- **Отдельный стенд.** Всё мерилось на машине разработчика, где в это же время
  работали и другие контейнеры, и сам k6. Числа на 30 и 50 VU поэтому
  пессимистичны и показывают «не хуже, чем».
- **Сеть.** Всё в пределах петли: ни задержки канала, ни обратного прокси, ни
  TLS в числах нет. На стенде за nginx к каждому ответу прибавится время прокси.
- **Долгий прогон.** Каждый сценарий длится минуты, а не часы: утечек памяти,
  распухания таблиц и деградации плана запросов такой замер не покажет.
- **Трудозатраты и самостоятельный проход новых пользователей** — это не
  нагрузка, а наблюдение за людьми; в матрице требований эти строки остаются со
  статусом «не проверено».

## Как повторить

Перед первым прогоном на машине — свой `scripts/load/load.env`: в репозитории
его нет (ключ шифрования контактов и пароли стенда), значения генерируются по
[`scripts/load/README.md`](../scripts/load/README.md). Без файла `run.sh`
останавливается и говорит, что скопировать.

```bash
# 1. Поднять нагрузочный стек и залить набор (свой проект Compose, свои порты)
scripts/load/run.sh up

# 2. Короткая проба — проверить, что сценарий жив (5 VU, 30 с)
scripts/load/run.sh probe

# 3. Лестница нагрузки: своя папка результатов на каждую ступень
OUT=/tmp/vu5 VUS=5 DURATION=1m scripts/load/run.sh browse
OUT=/tmp/vu15 VUS=15 DURATION=2m scripts/load/run.sh browse
OUT=/tmp/vu30 VUS=30 DURATION=3m scripts/load/run.sh browse
OUT=/tmp/vu50 VUS=50 DURATION=4m scripts/load/run.sh browse

# 4. Десять одновременных отчётов и замер кэша
OUT=/tmp/rep REPORT_VUS=10 REPORT_DURATION=2m scripts/load/run.sh reports
OUT=/tmp/cache PAIRS=40 REPORT_PAIRS=3 scripts/load/run.sh cache

# 5. Разложить прогон по шагам сценария
scripts/load/run.sh breakdown /tmp/vu50/browse-raw.json.gz

# 6. Погасить стек вместе с его томами
scripts/load/run.sh down
```

Лестницу надо проходить **на свежем наборе**: каждый прогон тратит доступные
переходы, и к четвёртой ступени их не остаётся (см. «Чем сценарий отличается от
прошлого раза не по своей воле»). Если нужны сравнимые между собой ступени —
`down -v`, `up` и одна ступень за заливку.

Стек поднимается командой

```bash
docker compose -p lct-load --env-file scripts/load/load.env \
  -f docker-compose.yml -f docker-compose.prod.yml -f scripts/load/compose.load.yml \
  up -d --build
```

и слушает 127.0.0.1:3100 (приложение) и 127.0.0.1:3180 (каталог учётных
записей). Подробности — [`scripts/load/README.md`](../scripts/load/README.md).

Одиночный замер без k6 — тем же `Server-Timing`:

```bash
curl -sI -b cookies.txt 'http://localhost:3100/reports?mode=slice&from=2026-09-01&to=2027-08-31' \
  | grep -i server-timing
# server-timing: db;dur=904.0, app;dur=20.6, total;dur=924.6
```
