# Отклик и нагрузка

Три требования задания говорят про скорость: отклик интерфейса не дольше
секунды (`N1`), пятьдесят одновременных пользователей (`N6`), десять
одновременных отчётов (`N7`). До этого замера они стояли в матрице требований со
статусом «не проверено», и это был честный статус: индексы, представление срока
стадии и кэш дашборда в системе были, а числа не мерил никто.

Здесь — числа. Что именно мерили, на чём, что получилось и где требование не
выполняется.

## Коротко

| Требование                          | Что получилось                                                                                                                                                                                           |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `N1` — отклик не дольше секунды     | Выполняется до **15 одновременных пользователей** по списку, карточке и переходу. На пятидесяти — нет. Отчёт за учебный год не укладывается в секунду **ни при какой нагрузке**: он один стоит 0,9–1,1 с |
| `N6` — пятьдесят пользователей      | Система **держит**: 984 прохода за четыре минуты, ни одной ошибки. Но отвечает медленно: p95 списка 2,7 с, карточки 2,9 с                                                                                |
| `N7` — десять одновременных отчётов | **Держит**: ни одной ошибки за две минуты. XLSX за учебный год — p95 4,0 с; PDF за год не собирается вовсе — у формата потолок 2000 строк, и это отказ по замыслу, а не сбой                             |
| `F13` — кэш повторного открытия     | Повторное открытие карточки дешевле первого на **11 %** по общему времени и на **15 %** по времени в базе. Кэш подбора из справочника на этом объёме — в пределах шума                                   |

Вывод одной строкой: **узкое место — база, а не приложение.** В любом
измеренном ответе `db;dur` занимает от 70 до 95 % времени, а сам Node
простаивает. Что с этим делать — в разделе «Что делать дальше».

## Как мерили

### Стенд

Отдельный стек в своём проекте Compose (`lct-load`), поднятый производственным
наложением: тот же образ приложения, тот же режим `production`, те же потолки
памяти. Стек не пересекается ни портами, ни томами со стеком разработки —
иначе замер шёл бы по базе, которую в это же время меняет прогон e2e.

| Что             | Значение                                                       |
| --------------- | -------------------------------------------------------------- |
| Машина          | AMD Ryzen AI 7 350, 8 ядер / 16 потоков, 30 ГиБ памяти, Linux  |
| Docker          | 29.8.1                                                         |
| k6              | v2.2.0, контейнером `grafana/k6` в сети хоста                  |
| Приложение      | образ проекта, Node 24, `adapter-node`, потолок памяти 512 МиБ |
| PostgreSQL      | 17-alpine, потолок памяти 1 ГиБ                                |
| Redis           | 8-alpine, потолок 128 МиБ                                      |
| Gotenberg       | 8, потолок 768 МиБ                                             |
| Каталог записей | Keycloak 26.7.4, потолок 768 МиБ                               |
| Дата прогона    | 2026-09-18                                                     |

### Данные

Нагрузочный набор (`node scripts/seed/index.ts --load`,
[`seeds.md`](seeds.md)): 300 вузов, 3000 взаимодействий, 16 500 записей стадий,
22 800 комментариев, 17 100 правок плана. Все вузы ведёт один КАМ, поэтому
подзапрос области доступа считается по трёмстам действующим назначениям, а не по
трём.

### Чем мерили

`Server-Timing` на каждом ответе приложения — три числа: `db` (сколько запрос
ждал базу), `app` (сколько осталось приложению), `total`. Это не отладочный
режим и не переключатель: заголовок стоит на каждом ответе всегда, в том числе
на стенде, и по нему видно, где время, без профилировщика и без доступа к
машине. Внутренностей он не раскрывает — ни текстов запросов, ни их количества,
ни имён сервисов.

Сценарии k6 — в `scripts/load/`:

- **`browse.js`** — рабочий круг сотрудника: список взаимодействий → карточка →
  переход по процессу с комментарием → смена фильтра отчёта, с паузой в секунду
  между шагами. Работают три роли сразу — КАМ, руководитель, администратор, —
  потому что область доступа считается подзапросом на каждой выборке и у
  администратора он вырождается в «всё»;
- **`reports.js`** — десять человек одновременно просят отчёт за учебный год и
  забирают его файлом: экран, XLSX, PDF, JSON;
- **`cache.js`** — стоимость повторного открытия карточки: одна и та же
  карточка открывается дважды подряд, числа берутся из `Server-Timing`.

Вход в систему настоящий: приложение паролей не хранит, поэтому сценарий
проходит тот же путь, что и браузер, — код авторизации с PKCE через форму
каталога учётных записей. `direct grants` у клиента выключены намеренно, и
включать их ради замера нельзя: мерить надо систему, какая она есть. Вход
происходит один раз на VU и в измеряемые операции не входит.

## N1 и N6: пятьдесят пользователей

Полный прогон: 50 VU, 4 минуты, 984 прохода, 5220 запросов, **ни одной ошибки**
(`http_req_failed 0 %`). Для сравнения рядом — тот же сценарий на 15 и на 5 VU.

Порог `N1` стоит в самом сценарии (`thresholds` k6) на девяносто пятой доле, а
не на среднем: секунда обещана человеку, который открыл экран.

| Операция                   | 5 VU: p50 / p95 / max                                | 15 VU: p50 / p95 / max                              | 50 VU: p50 / p95 / max       |
| -------------------------- | ---------------------------------------------------- | --------------------------------------------------- | ---------------------------- |
| Открытие списка            | 72 / 119 / 130 мс                                    | 138 / 377 / 830 мс                                  | 1300 / 2709 / 5433 мс        |
| Открытие карточки          | 73 / 96 / 107 мс                                     | 161 / 396 / 963 мс                                  | 1348 / 2908 / 5974 мс        |
| Переход по процессу        | 82 / 107 / 110 мс                                    | 185 / 411 / 700 мс                                  | 1617 / 3050 / 6021 мс        |
| Смена фильтра отчёта (год) | 790 / 977 / 982 мс                                   | 1456 / 1867 / 2187 мс                               | 2416 / 4037 / 6819 мс        |
| **Порог `N1` ≤ 1 с (p95)** | список, карточка, переход — **да**; отчёт — на грани | список, карточка, переход — **да**; отчёт — **нет** | **нет** ни по одной операции |

Доля ошибок по видам запроса — на всех трёх уровнях нагрузки нули:

| Вид запроса                               | 50 VU: p50 / p95 | Доля ошибок |
| ----------------------------------------- | ---------------- | ----------- |
| SSR-страницы (список, карточка, отчёт)    | 1750 / 3452 мс   | 0 %         |
| Отправка форм (переход, комментарий)      | 1617 / 3050 мс   | 0 %         |
| JSON-ответы приложения (подсказка выбора) | 543 / 1727 мс    | 0 %         |

Что это значит. **`N6` выполняется**: пятьдесят одновременных пользователей
система обслуживает без единой ошибки и без отказов — очередь не рвётся,
соединения к базе не кончаются, память приложения остаётся в пределах 234 МиБ из 512. **`N1` при этом не выполняется**: на пятидесяти пользователях девяносто
пятая доля времени открытия — почти три секунды.

Ограничение замера, о котором нельзя умолчать: **k6 работал на той же машине,
что и стенд**, и на 50 VU он сам съедает заметную долю процессора. Отдельного
нагрузочного стенда у команды нет, поэтому числа на 50 VU — это «не хуже, чем»,
а не точная величина. Числа на 5 и 15 VU этим искажены незначительно.

## N7: десять одновременных отчётов

Полный прогон: 10 VU, 2 минуты, 153 прохода, 672 запроса, **ни одной ошибки**.
Пауз между запросами в этом сценарии нет намеренно: десять одновременных
выгрузок — не поведение человека, а худший случай, ради которого требование и
написано.

| Что                                       | p50     | p95     | max     |
| ----------------------------------------- | ------- | ------- | ------- |
| Экран отчёта за учебный год               | 2038 мс | 2559 мс | 3021 мс |
| Выгрузка XLSX за учебный год (3028 строк) | 3176 мс | 4002 мс | 4265 мс |
| Выгрузка JSON за учебный год              | 2189 мс | 2585 мс | 3016 мс |
| Выгрузка PDF за квартал (движение)        | 534 мс  | 840 мс  | 1546 мс |

**`N7` выполняется** в том смысле, в каком оно написано: десять одновременных
отчётов система собирает и отдаёт, не теряя ни одного. Секунды здесь нет и не
обещано: `N1` говорит про отклик интерфейса, а выгрузка за год — это файл,
который собирают и ждут.

Про PDF отдельно. **Годовой срез портфеля в PDF не выгружается вовсе**: у
формата потолок в 2000 строк, а в отчёте их 3028, и выгрузка отвечает отказом с
объяснением — «Выгрузка PDF этого объёма не собирается. В отчёте 3028 строк, в
файл этого формата помещается 2000. Сузьте период или добавьте фильтр». Это
поведение по замыслу, а не сбой, поэтому PDF в сценарии меряется на самом
большом периоде, который он принимает. Но требование `N7` названо «xlsx и pdf за
большой период», и в этой части оно **не выполнено**: за большой период PDF
недоступен.

Разница между JSON (2189 мс) и XLSX (3176 мс) — это цена сборки книги: около
секунды на 3028 строк. Сам отчёт, то есть выборка, стоит примерно как JSON.

## F13: кэш повторного открытия

Кэш живёт в Redis и устроен как кэш дашборда данных об обучении: область
доступа — в ключе, поколение — для обесценивания, короткий срок жизни. Что
именно кэшируется:

- **общая половина карточки** — сама запись, её процесс, программы, продукты и
  перечень документов;
- **лента комментариев** и **история правок плана** — самое дорогое чтение
  карточки: к выборке строк добавляются подписи ссылочных значений, до четырёх
  запросов по справочникам;
- **подбор из справочника** для форм — действующие организации и люди.

Поколение у карточки — не счётчик, а `interactions.last_activity_at`: его
двигает **каждое** событие по записи, поэтому ни одна команда движка не может
«забыть» позвать инвалидацию — её не зовут вовсе, а момент последнего события
читается бесплатно, вместе с проверкой видимости.

**Чего в кэше нет: контактов людей.** Стороны карточки читаются из базы каждый
раз, потому что сериализатор контактов не только маскирует их по правам, но и
оставляет след просмотра персональных данных, — ответ из Redis этот след
потерял бы. Проверено тестом: два открытия карточки дают два события
`people.pii_viewed`.

### Повторное открытие карточки: до и после

Сорок пар «холодное открытие — повторное», один пользователь, числа из
`Server-Timing`:

| Карточка                            | Первое открытие: total / db | Повторное: total / db | Разница по total / по db |
| ----------------------------------- | --------------------------- | --------------------- | ------------------------ |
| Обычная (4 комментария, 3 правки)   | 75,4 / 61,0 мс              | 67,0 / 52,1 мс        | −11 % / −15 %            |
| Долгая (40 комментариев, 30 правок) | 76,3 / 59,1 мс              | 71,0 / 53,3 мс        | −7 % / −10 %             |

Выигрыш скромный, и вот почему: карточка собирается девятью чтениями, а кэш
покрывает три из них. Остальное — состояние стадии, сводка «что могу сейчас»,
приговор о закрытии, список ответственных, замены документов и журнал обмена —
читается из базы каждый раз, и на них приходится большая часть из пятидесяти
миллисекунд ожидания базы.

### Подбор из справочника

Пять пар «холодное чтение — повторное» на странице контактов: 25,2 → 20,6;
14,6 → 12,0; 11,8 → 17,6; 11,2 → 12,1; 24,8 → 17,6 мс. **Разница в пределах
шума.** На трёхстах организациях и трёх сотнях людей сам подбор стоит единицы
миллисекунд, и снимать с базы нечего. Смысл этого кэша — в снятии запросов под
нагрузкой, где база и есть узкое место, но отдельным замером это не
подтверждено: разделить вклад одного кэша внутри прогона на 50 VU нечем.

### Инвалидация

Подбор обесценивается после каждой записи в справочник: все шестнадцать
операций `src/lib/server/directory/write.ts` проходят через один помощник
`written()`, загрузка каталога файлом — через `invalidated()` в
`confirmCatalogImport`, обезличивание — через `forgotten()` в
`anonymizePerson`. Обесценивание идёт **после** того, как запись завершилась:
до фиксации транзакции показывать ещё нечего.

Назначения ответственных (`assignResponsible`, `releaseResponsible`) своей
точки инвалидации не требуют: отпечаток действующих назначений входит в сам
ключ, поэтому снятый вуз пропадает из подсказки в ту же секунду. Это проверено
отдельным тестом.

Одно место остаётся неточным, и это видно в коде: приём заявки с сайта
(`src/lib/server/integrations/exchange/applications.ts`) заводит организацию,
человека и его роль в **своей** транзакции, передавая её сервисам справочника.
Вложенные вызовы обесценивают кэш, когда их работа сделана, но внешняя
транзакция ещё не зафиксирована, — и в этом окне читатель теоретически успел бы
положить в кэш то, чего ещё нет. Окно измеряется миллисекундами, а последствие
ограничено сроком жизни записи в 30 секунд; закрывается оно одной строкой
`invalidateDirectoryOptions()` после фиксации транзакции приёма заявки.

Для карточки такого долга нет вовсе: её поколение считается по данным
(`last_activity_at`), а не по вызову.

## Что делать дальше

По порядку убывания эффекта — это выводы замера, а не план работ.

1. **Отчёт за год — самая дорогая операция системы и единственная, которая не
   укладывается в секунду даже без нагрузки.** Один запрос: `db;dur=874,9` из
   `total;dur=914,1` для среза и `db;dur=1011,9` из `1095,8` для движения.
   Приложение здесь ни при чём — время целиком в выборке. Смотреть надо план
   запроса отчёта и индексы под окно `stage_entries`, а не код сборщика.
2. **Экран отчёта читает справочники фильтров на каждое открытие** —
   `readFilterOptions` в `src/lib/server/reports/options.ts` делает семь
   выборок, и ни одна из них не зависит от того, что человек ищет. Это первый
   кандидат в тот же кэш: разрез — область доступа, поколение — справочник.
3. **Действующая редакция процесса читается по нескольку раз на один запрос** —
   `readActiveRevision` зовут и карточка, и её сводка, и список, и доска.
   Структура процесса меняется публикацией, то есть редко; это идеальные данные
   для кэша с поколением по `process_groups.active_revision_id`.
4. **Карточка собирается девятью чтениями подряд.** Половина из них — про одно и
   то же состояние стадии. Сводить их в одно чтение дороже, чем кэшировать, но
   именно там лежат оставшиеся пятьдесят миллисекунд.

## Чего не измеряли и почему

- **Отдельный стенд.** Всё мерилось на машине разработчика, где в это же время
  работали и другие контейнеры, и сам k6. Числа на 50 VU поэтому пессимистичны и
  показывают «не хуже, чем».
- **Несколько экземпляров приложения.** Стенд поднимает один процесс Node.
  `adapter-node` обслуживает запросы в одном процессе, и второй экземпляр рядом
  — самый дешёвый способ снять нагрузку с процессора; проверить это на одной
  машине нельзя.
- **Сеть.** Всё в пределах петли: ни задержки канала, ни обратного прокси, ни
  TLS в числах нет. На стенде за nginx к каждому ответу прибавится время прокси.
- **Долгий прогон.** Каждый сценарий длится минуты, а не часы: утечек памяти,
  распухания таблиц и деградации плана запросов такой замер не покажет.
- **Трудозатраты и самостоятельный проход новых пользователей** — это не
  нагрузка, а наблюдение за людьми; в матрице требований эти строки остаются со
  статусом «не проверено».

## Как повторить

```bash
# 1. Поднять нагрузочный стек и залить набор (свой проект Compose, свои порты)
scripts/load/run.sh up

# 2. Короткая проба — проверить, что сценарий жив (5 VU, 30 с)
scripts/load/run.sh probe

# 3. Замер кэша повторного открытия карточки
scripts/load/run.sh cache

# 4. Полный прогон обоих сценариев
DURATION=4m VUS=50 REPORT_VUS=10 REPORT_DURATION=2m scripts/load/run.sh full

# 5. Погасить стек вместе с его томами
scripts/load/run.sh down
```

Результаты складываются в каталог `OUT` (по умолчанию — временный; его имя
печатается в конце). Стек поднимается командой

```bash
docker compose -p lct-load --env-file scripts/load/load.env \
  -f docker-compose.yml -f docker-compose.prod.yml -f scripts/load/compose.load.yml \
  up -d --build
```

и слушает 127.0.0.1:3100 (приложение) и 127.0.0.1:3180 (каталог учётных
записей). Подробности — [`scripts/load/README.md`](../scripts/load/README.md).

Одиночный замер без k6 — тем же `Server-Timing`:

```bash
curl -sI -b cookies.txt 'http://localhost:3100/reports?mode=slice&from=2026-09-01&to=2027-08-31' \
  | grep -i server-timing
# server-timing: db;dur=874.9, app;dur=39.2, total;dur=914.1
```
