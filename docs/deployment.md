# Развёртывание

Инструкция для сервера: один хост, Docker Compose, обратный прокси перед приложением.
Локальный запуск и разработка — в [`../README.md`](../README.md) и [`development.md`](development.md).

## Что нужно на сервере

- Docker 25+ с плагином Compose 2.24+ (нужны теги слияния `!reset` / `!override`
  в `docker-compose.prod.yml`; проверить — `docker compose version`).
- ~3,5 ГБ свободной оперативной памяти на стек и ~2 ГБ на сборку образа.
  Суммарный лимит контейнеров — 3264 МБ (см. `docker-compose.prod.yml`).
  Если памяти на сборку не хватает, образ собирают на другой машине и переносят:
  `docker save lct-crm-app | gzip | ssh <host> 'gunzip | docker load'`,
  а у сервиса `app` в оверрайде вместо `build` указывают `image: lct-crm-app`.
- ~3 ГБ на диске под образы и тома.
- nginx (или другой прокси), который терминирует TLS и проксирует на порт приложения.

Наружу публикуются только приложение и Keycloak, и только на loopback
(`127.0.0.1:${APP_PORT}` и `127.0.0.1:${KEYCLOAK_PORT}`): перед обоими стоит один и тот же прокси,
раздел «Keycloak» ниже. PostgreSQL, Redis, Gotenberg и MinIO доступны исключительно
внутри сети Compose: у базы там все данные, а у консоли MinIO —
все документы системы. Понадобилась консоль MinIO — туннель на время работы
(`ssh -L 9001:localhost:9001 <host>` вместе с `docker compose port minio 9001`), а не
опубликованный порт.

Стенд с профилем `stand` поднимает ещё Mailpit — почтовый сервер-ловушку для уведомлений. Его порт
SMTP не публикуется вовсе, а веб-интерфейс стоит на loopback хоста
(`127.0.0.1:${MAILPIT_PORT:-8025}`) и в прокси не добавляется: смотрят его через туннель, раздел
«Почта уведомлений и Mailpit».

## Конфигурация

Все переменные обязательны: без любой из них сервер не стартует и пишет, чего не хватает
(`src/lib/server/config.ts`). Шаблон — `.env.example`; на сервере `.env` отличается от него
адресами (внутри сети Compose это имена сервисов, а не `localhost`) и двумя добавками.

| Переменная                | Значение на сервере                                                                          |
| ------------------------- | -------------------------------------------------------------------------------------------- |
| `NODE_ENV`                | `production`                                                                                 |
| `DATABASE_URL`            | `postgres://lct:lct@postgres:5432/lct`                                                       |
| `REDIS_URL`               | `redis://redis:6379`                                                                         |
| `GOTENBERG_URL`           | `http://gotenberg:3000`                                                                      |
| `SMTP_URL`                | Почтовый сервер уведомлений: релей заказчика или `smtp://mailpit:1025` на стенде             |
| `SMTP_FROM`               | Обратный адрес письма, например `lct-crm@<домен>`; пусто — почта не настроена                |
| `ORIGIN`                  | `https://<домен>` — ровно тот адрес, по которому открывается приложение в браузере           |
| `DEMO_MODE`               | `true` на публичном стенде, `false` у заказчика; ровно `true` или `false`                    |
| `SEED_DEMO_PASSWORD`      | Общий пароль трёх демонстрационных записей каталога; читает импорт realm Keycloak            |
| `DEMO_PASSWORD_HINT`      | Тот же пароль для карточки на странице входа; пусто — карточка его не называет               |
| `TRUST_PROXY`             | `true` — приложение стоит за nginx и берёт адрес клиента из `X-Forwarded-For`                |
| `ALLOW_LOCAL_TARGETS`     | `false` — сервер ходит наружу только на публичные адреса (см. ниже)                          |
| `EXCHANGE_SECRET`         | Секрет подписи исходящих сообщений обмена, не короче 32 символов; пусто — обмен не настроен  |
| `EXCHANGE_API_KEY_CMS`    | Ключ обмена для имитатора сайта: заводит сид стенда, читает `mock-cms`; пусто — ключа нет    |
| `EXCHANGE_API_KEY_LMS`    | То же для имитатора системы обучения; значение обязано отличаться от предыдущего             |
| `S3_ACCESS_KEY`           | Ключ доступа к хранилищу документов; он же корневой пользователь MinIO                       |
| `S3_SECRET_KEY`           | Секретный ключ хранилища; он же пароль корневого пользователя MinIO                          |
| `APP_PORT`                | порт на `127.0.0.1`, куда смотрит прокси; по умолчанию `8099`                                |
| `FONTS_DIR`               | каталог с файлами гарнитуры Rostelecom Basis; по умолчанию `./static/fonts` (раздел «Шрифт») |
| `KEYCLOAK_ADMIN`          | Администратор самого Keycloak (realm `master`), не учётная запись CRM                        |
| `KEYCLOAK_ADMIN_PASSWORD` | Его пароль; заводится при первом старте и больше переменной не управляется                   |
| `KEYCLOAK_PORT`           | порт на `127.0.0.1`, куда смотрит прокси для `/auth`; по умолчанию `8098`                    |
| `OIDC_PUBLIC_URL`         | `https://<домен>/auth` — публичный адрес Keycloak целиком, вместе с путём                    |
| `OIDC_ISSUER_URL`         | `https://<домен>/auth/realms/lct`                                                            |
| `OIDC_CLIENT_ID`          | `lct-crm`                                                                                    |
| `OIDC_CLIENT_SECRET`      | Секрет клиента; он же попадает в realm при импорте                                           |

`SEED_DEMO_PASSWORD` обязательна независимо от `DEMO_MODE`: realm Keycloak импортируется с ней в
любом случае, и без переменной `docker compose up` останавливается и называет её. Приложение её не
читает — паролей у него нет вовсе.

`DEMO_PASSWORD_HINT` — та же строка, но для экрана: карточка страницы входа показывает её рядом с
тремя именами, и только при `DEMO_MODE=true`. На **публичном стенде** обе переменные совпадают и
пароль публичный: стенд открыт зрителям, и пароль, который надо у кого-то спрашивать, закрыл бы
показ (граница демонстрации — права, а не знание пароля, `docs/security.md`). У **заказчика**
`DEMO_PASSWORD_HINT` не задают вовсе: там `DEMO_MODE=false`, и карточки нет. Заданное, но испорченное
значение (пробелы, длиннее 128 символов) страница входа не проглатывает — это ошибка настройки, и она
видна сразу.

`ALLOW_LOCAL_TARGETS` решает, разрешено ли серверу ходить по своей инициативе на петлю и в приватные
сети. Адрес приёмника подписки, адрес системы обучения и подключения обмена задаёт человек, а запрос
по ним делает сервер — изнутри сети Compose, где стоят Keycloak, MinIO и база: снаружи они
недостижимы, а изнутри отвечают без всякого ключа. На развёртывании должно быть `false`; `true`
ставят только там, где имитаторы и приёмник подняты рядом, на `127.0.0.1`, — на машине разработчика
и в прогоне. Умолчание зависит от режима: в `production` — запрет.

`EXCHANGE_SECRET` либо пуст (обмен не настроен), либо не короче 32 символов: подпись HMAC-SHA256
стоит ровно столько, сколько стоит подбор ключа, и короткий секрет процесс не примет при старте.

### Почта уведомлений и Mailpit

`SMTP_URL` и `SMTP_FROM` — это почтовый сервер, через который уходят напоминания о зависших
взаимодействиях (`docs/integrations.md`, раздел «Уведомления»), и обратный адрес письма. Умолчания у
них нет намеренно: подставленный `localhost:25` означал бы письма, которые никуда не уходят и об
этом молчат. Пустая строка равна «не настроено» — канал «почта» тогда не отправляет и пишет об этом
строкой в журнале доставок `/notifications`, а не молча.

**У заказчика** сюда ставят адрес корпоративного релея: `smtp://relay.example.org:587`, для
защищённого соединения `smtps://…`, логин и пароль — частью адреса
(`smtp://user:pass@relay:587`, спецсимволы кодируются процентами). `SMTP_FROM` — адрес, с которого
письмо приходит, и он должен быть разрешён релею, иначе письма отобьются.

**На стенде** настоящего релея нет и быть не должно: адреса демонстрационных записей синтетические,
а рассылка с публичного стенда на живые адреса — это рассылка. Поэтому стенд поднимает **Mailpit**,
почтовый сервер-ловушку: он принимает всё и не выпускает наружу ничего.

```bash
# Mailpit живёт в профиле `stand`, как и имитаторы CMS и LMS
docker compose -f docker-compose.yml -f docker-compose.prod.yml --profile stand up -d

# в .env стенда
SMTP_URL=smtp://mailpit:1025
SMTP_FROM=lct-crm@<домен>
```

Веб-интерфейс Mailpit показывает каждое отправленное письмо целиком — это и есть доказательство,
что уведомление ушло. Порт SMTP наружу не выходит вовсе, а веб-интерфейс опубликован только на
loopback хоста (`127.0.0.1:${MAILPIT_PORT:-8025}`), как приложение и каталог, — то есть смотрят его
через туннель:

```bash
ssh -L 8025:127.0.0.1:8025 <host>
# затем http://localhost:8025 в браузере
```

`MAILPIT_PORT` меняют, если 8025 на хосте уже занят; в прокси этот порт не добавляют — наружу
почтовый ящик стенда не показывают.

Состояния Mailpit не хранит: контейнер пересоздали — почтовый ящик пуст, и это правильно, письма
стенда живут ровно столько, сколько идёт показ.

`EXCHANGE_API_KEY_CMS` и `EXCHANGE_API_KEY_LMS` — единственные две переменные, которые читает не
приложение, а сид (`docs/seeds.md`, «Ключи обмена»). Они нужны стенду с `DEMO_MODE=true`, который
поднимает имитаторов профиля `stand`: выпустить ключ через интерфейс там некому — демонстрационная
сессия не получает права `api_keys.manage`, а у штатного администратора нет учётной записи в
каталоге, пока её не завели в консоли Keycloak. Поэтому значение задаёт `.env`: сид заводит по ключу
на подключение (сайт и система обучения — разные значения, формат `lct_` и 32 символа base64url;
сгенерировать — `lct_$(openssl rand -base64 24 | tr '+/' '_-' | tr -d '=')`), а имитаторы
представляются теми же значениями. Развёртывание у заказчика оставляет их пустыми: там обмен идёт с
настоящими системами, а ключи им выпускает администратор обычным путём.

Ключ заводится один раз. Смена значения в `.env` заведённый ключ **не** переписывает — сид пишет
предупреждение и оставляет прежний; чтобы сменить ключ, его отзывают на экране «Настройки → Ключи
доступа» и перезапускают приложение (сид идёт при старте контейнера). Значения в репозитории нет:
`.env.example` оставляет обе переменные пустыми, и стенд без них поднимается, просто без обмена.

Значение в `.env.example` — заполнитель (`change-me-before-deploy-Aa1!`), и заменить его надо **до
первого развёртывания**: импорт realm отрабатывает один раз, на пустой базе, и позже подстановка
ничего не меняет. Заполнитель политику realm проходит — стек с ним поднимается, — и ровно поэтому
забыть о нём легко.

`S3_ACCESS_KEY` и `S3_SECRET_KEY` — это одна пара на стек: MinIO поднимается с ней как с
корневой, приложение ею подписывает запросы. Значения придумывает развёртывание (например,
`openssl rand -hex 24`); в `.env.example` стоят локальные, и на сервере их меняют вместе с
паролями. Без них `docker compose up` останавливается и называет недостающую переменную —
умолчания у секрета быть не может.

`S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_FORCE_PATH_STYLE` и `BODY_SIZE_LIMIT` в `.env` не
пишут: их задаёт `docker-compose.prod.yml`, потому что они описывают устройство развёртывания, а не
его настройки, и значение из `environment` всё равно перекрыло бы `.env`. Хранилище документов — MinIO в сети Compose (`http://minio:9000`, бакет
`lct-documents`) на томе `minio-data`; том переживает пересборку образа и `docker compose down`
без `-v`. Бакет заводит одноразовый сервис `minio-init`: он ждёт, пока MinIO ответит на проверку
здоровья, создаёт бакет, если его нет, и выходит; приложение стартует только после него
(`service_completed_successfully`). Заводить бакет руками не нужно, а ключи приложения этого и не
умеют — им нужны только объекты. Про `BODY_SIZE_LIMIT` — раздел «Потолки на размер загрузки» ниже.

Бакет пустой, а база не пустая — это не рабочее состояние: строки `documents` ссылаются на
объекты по ключу, и скачивание такого документа отвечает отказом, а не пустым файлом. На стенде,
который поднимают заново, базу и бакет заводят вместе; на стенде, который переносят, — переносят
оба (раздел «Резервное копирование»).

**Администратор стенда заводится в каталоге, а не переменной.** Демонстрационная сессия не получает
прав на пользователей, ключи, внешние адреса подключений и обезличивание — какой бы ролью ни вошли,
— поэтому на стенде с `DEMO_MODE=true` нужна обычная учётная запись оператора. Сид кладёт под неё
строку `admin@staff.lct-crm.local` в базу приложения; сама учётная запись заводится в консоли
Keycloak с этой же подтверждённой почтой и ролью realm `crm-admin`, и первый вход свяжет их. См.
раздел «Keycloak» ниже и [`seeds.md`](seeds.md), «Администратор стенда».

`ORIGIN` обязан совпадать с публичным адресом до символа: adapter-node по нему проверяет
источник POST-запросов, при расхождении формы отваливаются с 403.

`APP_PORT` читает только Compose (подстановка в `docker-compose.prod.yml`), приложение
внутри контейнера всегда слушает 3000.

Файл с секретом — `chmod 600 .env`. В репозиторий он не попадает (`.gitignore`).

## Первый запуск

```bash
git clone <repo> /srv/lct-crm && cd /srv/lct-crm
cp .env.example .env && chmod 600 .env      # дальше править по таблице выше
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
```

Compose поднимает PostgreSQL, Redis, Keycloak, Gotenberg и MinIO (а с `--profile stand` — ещё
Mailpit и имитаторы), ждёт их healthcheck'ов,
прогоняет `minio-init` (бакет документов) и только потом запускает приложение. Контейнер приложения при старте сам применяет миграции
(`node scripts/migrate.ts` в `Dockerfile`) — отдельного шага миграции в развёртывании нет.
Миграции идемпотентны: применённые пропускаются.

Следом, и только при `DEMO_MODE=true`, контейнер заливает демонстрационные данные
(`node scripts/seed/index.ts --if-demo`): справочники, три демонстрационные учётные записи, двух
сотрудников, администратора стенда и машинного субъекта обмена. Сид тоже идемпотентен и не затирает
правки, сделанные на стенде руками. При `DEMO_MODE=false` сид не делает ничего. Что именно заливается и как это устроено — в [`seeds.md`](seeds.md).

Проверить, что всё поднялось:

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml ps
curl -s http://127.0.0.1:8099/api/health
```

`/api/health` отвечает `{"status":"ok","db":"ok","redis":"ok","storage":"ok","version":"…"}` и
кодом 200, только если ответили база, Redis и хранилище документов. Иначе — 503 и текст ошибки
того сервиса, который лёг, с кодом отказа (`Хранилище файлов не отвечает (ECONNREFUSED)`), но без
адресов и ключей. Тот же эндпоинт использует healthcheck контейнера, поэтому лежащее хранилище
делает контейнер приложения `unhealthy`: приложение, которому некуда положить документ, здоровым
не считается. Перезапуска по кругу от этого не случается — неисправный контейнер Docker сам не
перезапускает.

Дальше — прокси: шаблон `deploy/nginx/crm.conf.example`, в нём заменить `CRM_DOMAIN`,
`CRM_PORT` и пути к сертификату, положить в `sites-available`, слинковать в `sites-enabled`
и перезагрузить nginx после `nginx -t`.

Буферы заголовков в шаблоне увеличены не про запас. SvelteKit отдаёт заголовок `Link` со
ссылками на модули, которые странице понадобятся (`rel=modulepreload`); на страницах со
списками и диалогами он вырастает до 4–5 КБ. Дефолтного `proxy_buffer_size 4k` на такой ответ
не хватает: nginx не режет заголовок, а отвечает 502 и пишет в `crm_error.log`
«upstream sent too big header while reading response header from upstream». Приложение при
этом исправно — в его логе обычный 200. Отсюда `proxy_buffer_size 32k`, `proxy_buffers 8 32k`
и `proxy_busy_buffers_size 64k` в `location /`: если прокси на стенде настраивают не по
шаблону, эти три строки нужно перенести руками.

### Адрес клиента за прокси

Обязательна строка `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;`. По адресу
клиента считаются лимит заходов на вход и лимит частоты API, и он же стоит в каждой строке журнала
действий; без этой строки приложение видит только адрес соединения, и все посетители попадают туда
одним адресом — самого прокси.

Адрес разбирает приложение, а не транспорт: `ADDRESS_HEADER` и `XFF_DEPTH` adapter-node **не
задаются** (`docker-compose.prod.yml` их не ставит, в `.env` их тоже быть не должно). С
`ADDRESS_HEADER=X-Forwarded-For` adapter-node бросает исключение на каждом запросе без заголовка, а
такие запросы на стенде обычные: имитаторы `mock-cms` и `mock-lms` профиля `stand` ходят к
`http://app:3000` внутри сети Compose, минуя nginx, и проверка здоровья контейнера — тоже. Ответом
на них был 500 при исправном приложении.

Правило приложения — `clientAddress()` в `src/lib/server/http.ts`:

| `TRUST_PROXY` | `X-Forwarded-For` | Адрес клиента                                 |
| ------------- | ----------------- | --------------------------------------------- |
| `true`        | есть              | последняя запись заголовка                    |
| `true`        | нет               | адрес соединения                              |
| `false`       | любой             | адрес соединения, заголовок не читается вовсе |

Последняя, а не первая: `$proxy_add_x_forwarded_for` дописывает наблюдённый адрес справа к тому,
что прислал клиент, поэтому крайняя справа запись — единственная, которую поставил наш nginx, а всё
левее неё сочинил тот, кто пришёл. Возьми приложение крайнюю слева — и любой посетитель назначал бы
себе адрес сам, обходя и лимит входов, и запись в журнале. Правило верно ровно потому, что прокси в
этой схеме один: nginx на том же хосте, приложение опубликовано только на `127.0.0.1:${APP_PORT}` и
других путей снаружи к нему нет. Появится второй прокси (CDN, балансировщик) — правило придётся
менять вместе со схемой: крайняя справа станет адресом этого второго прокси.

`TRUST_PROXY=false` при стоящем впереди nginx — не безопасная осторожность, а потеря адреса: все
посетители станут одним. `TRUST_PROXY=true` у приложения, доступного напрямую, наоборот, отдаёт
выбор адреса тому, кто пришёл.

### Потолки на размер загрузки

Размер загружаемого файла ограничивают три независимых места, и они обязаны идти по убыванию:
иначе отказ приходит не оттуда, откуда его ждут, и без объяснения.

| Потолок                         | Значение | Что происходит при превышении                                     |
| ------------------------------- | -------- | ----------------------------------------------------------------- |
| nginx, `client_max_body_size`   | `32m`    | 413 от прокси, приложение запроса не видит                        |
| adapter-node, `BODY_SIZE_LIMIT` | `27M`    | 413 до маршрута, форма не успевает показать ошибку                |
| код, `MAX_DOCUMENT_SIZE_BYTES`  | 25 МиБ   | отказ формы с текстом «Файл больше 25 МиБ» — единственный внятный |

Запас между потолками нужен на multipart-конверт: в теле запроса кроме самого файла едут
границы частей и остальные поля формы, поэтому `BODY_SIZE_LIMIT` считают не от размера файла.
Опускать `BODY_SIZE_LIMIT` до потолка контракта нельзя: файл ровно в 25 МиБ обязан загружаться,
а с конвертом он в 25 МиБ не помещается.

Единственная ручка, которой стенд вправе прикрутить загрузку, — `client_max_body_size`: он
режет ещё до приложения и не расходится с тем, что обещает форма.

## Шрифт

Интерфейс набран фирменной гарнитурой **Rostelecom Basis** — она часть «Дизайн-системы
Ростелекома», как и цвета темы (`design.md`). Файлов шрифта в репозитории нет и не будет:
лицензии на их распространение у нас нет, а публичный репозиторий — это распространение.

**Без файлов всё работает.** Запрос за шрифтом отвечает 404, браузер берёт следующее семейство в
`--font-sans` — Inter Variable, который лежит в сборке, — и меняется только рисунок букв: ни
раскладка, ни размеры, ни плотность от этого не зависят. Разворачивать стенд без шрифта можно.

Что нужно сделать, чтобы шрифт был:

1. Взять архив гарнитуры (`Rostelecom Basis Font`) — его выдаёт заказчик вместе с доступом к
   дизайн-системе. В архиве только начертания: файла лицензии в нём нет, и шрифт используется
   ровно на стенде этой системы, а не раздаётся дальше.
2. Положить на машину развёртывания четыре начертания в двух форматах, именами как есть:

   ```
   RostelecomBasis-Light.woff2     RostelecomBasis-Light.woff
   RostelecomBasis-Regular.woff2   RostelecomBasis-Regular.woff
   RostelecomBasis-Medium.woff2    RostelecomBasis-Medium.woff
   RostelecomBasis-Bold.woff2      RostelecomBasis-Bold.woff
   ```

   Имена — часть контракта: по ним шрифт ищет `src/app.css`, и переименованный файл не найдётся.
   `woff2` берут все нынешние браузеры, `woff` остаётся запасным форматом.

3. Назвать каталог в `.env`:

   ```
   FONTS_DIR=/srv/lct-crm/fonts
   ```

   Путь абсолютный или относительный каталогу с `docker-compose.yml`; по умолчанию —
   `./static/fonts`. `docker-compose.prod.yml` монтирует этот каталог в контейнер только на чтение,
   в `/app/build/client/fonts`: `build/client` — это то, что adapter-node отдаёт как статику,
   поэтому файлы видны по адресу `/fonts/…`.

4. Перезапустить приложение: `docker compose … up -d app`. Список файлов статики сервер составляет
   при старте, поэтому каталог, наполненный на работающем контейнере, сам собой не подхватится.

Проверить:

```bash
curl -sI http://127.0.0.1:8099/fonts/RostelecomBasis-Regular.woff2 | head -1
# HTTP/1.1 200 OK  — шрифт на месте
# HTTP/1.1 404 Not Found — стенд идёт на запасной гарнитуре
```

В образ шрифт не попадает: `static/fonts` перечислен в `.dockerignore`, поэтому даже сборка на
машине, где файлы лежат локально, унесёт их мимо образа. Единственный источник на стенде — этот том.

## Keycloak

Каталог учётных записей и единственный вход в систему: приложение своих паролей не хранит и не
спрашивает (`auth.md`). Realm, роли и демонстрационные учётные записи приезжают импортом.
Устройство realm — [`../keycloak/README.md`](../keycloak/README.md), отображение ролей —
[`access-matrix.md`](access-matrix.md), раздел 6.

**Без Keycloak в систему не войти никто.** Контейнер входит в обязательный состав стека, а не
стоит рядом «на будущее»: недоступный каталог означает, что страница входа отвечает «каталог
учётных записей сейчас не отвечает», и это единственное, что она может ответить.

Образ `quay.io/keycloak/keycloak:26.7.4`, режим `start` (рабочий, не `start-dev`). `--optimized`
не используется: он требует образа, собранного `kc.sh build` под PostgreSQL, а образ берётся
готовым, поэтому Keycloak дособирает конфигурацию сам при старте — это около пяти секунд сверху.
Измеренное время до `healthy` на чистой базе — 16 секунд, при перезапуске — 4. В покое контейнер
занимает около 600 МБ при потолке 768 МБ; на 512 МБ он поднимается, но живёт впритык к потолку и
первый же всплеск нагрузки означает OOM.

### Своя база

Keycloak хранит realm в **отдельной базе `keycloak`** того же PostgreSQL. В базе приложения ему
места нет: миграции ходят по всей схеме, а дамп приложения не должен уносить учётные записи
каталога.

Базу заводит скрипт `keycloak/initdb-keycloak.sh`, подключённый томом в `docker-entrypoint-initdb.d`.
Образ postgres выполняет такие скрипты **ровно один раз — при инициализации пустого тома**. На
стенде, который уже работает, том не пуст, и базу заводят руками, до первого старта Keycloak:

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml \
  exec postgres psql -U lct -d lct -c 'create database keycloak owner "lct"'
```

Без базы контейнер не поднимется и напишет об этом в лог — молча на встроенную H2 он не съедет.

### Что делать, если realm переимпортировали

Пересозданный контейнер каталога — новый realm, и `sub` у тех же людей другой. База приложения при
этом остаётся прежней, и вход отвечает «ваша почта уже числится за другой учётной записью системы»:
связывание по почте принимает только запись без субъекта, и ослаблять это правило нельзя — иначе
чужой адрес в токене отдавал бы чужой портфель (`auth.md`, «Каталог перезавели»).

Войти при этом не может никто, кого каталог знал раньше, — включая администратора, поэтому первый
шаг делается в базе, и только один:

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml exec postgres \
  psql -U lct -d lct -c "update users set external_subject = null \
  where email = 'admin@staff.lct-crm.local';"
```

Дальше администратор входит и отвязывает остальных кнопкой «Отвязать» в `/settings/users`: каждая
следующая запись связывается заново при первом же входе владельца, вместе с портфелем, назначениями
и следом в журнале. Поэтому realm на работающем стенде не переимпортируют, а правят в консоли.

### Импорт realm

`start --import-realm` импортирует `keycloak/realm-lct.json` **только в пустую базу**: realm,
заведённый раньше, импорт не трогает (стратегия `IGNORE_EXISTING`). Отсюда правило: значения,
которые подставляются в realm, задают в `.env` **до первого запуска**.

Подставляются три (подробно — `keycloak/README.md`):

| Переменная           | Что задаёт                                 | Откуда берётся на стенде                   |
| -------------------- | ------------------------------------------ | ------------------------------------------ |
| `OIDC_CLIENT_SECRET` | Секрет клиента `lct-crm`                   | `.env`                                     |
| `ORIGIN`             | Адрес приложения в списке адресов возврата | `.env`, та же переменная, что у приложения |
| `SEED_DEMO_PASSWORD` | Общий пароль трёх демонстрационных записей | `.env`                                     |

Умолчание в самом файле realm — `lct-demo-2026`; локальный стек подставляет на его место
`SEED_DEMO_PASSWORD` из `.env` (у `docker-compose.yml` для этого есть своё умолчание). На стенде
значение задают в `.env` своим, и **то же самое** значение ставят в `DEMO_PASSWORD_HINT`, иначе
карточка входа покажет пароль, которым не войти.

Почты демонстрационных записей realm совпадают с почтами строк, которые кладёт сид: при первом
входе запись найдётся по подтверждённой почте, и человек войдёт со своим портфелем, а не двойником.
Поменять пароль **после** импорта переменная уже не может — это делают в каталоге:

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml exec keycloak \
  /opt/keycloak/bin/kcadm.sh config credentials --server http://localhost:8080/auth \
  --realm master --user "$KEYCLOAK_ADMIN" --password "$KEYCLOAK_ADMIN_PASSWORD"

docker compose -f docker-compose.yml -f docker-compose.prod.yml exec keycloak \
  /opt/keycloak/bin/kcadm.sh set-password -r lct --username manager --new-password '<новый>'
```

Так же — `lead` и `admin`. То же самое делается мышью в консоли по адресу `https://<домен>/auth/admin`.
Сменили пароль в каталоге — поменяйте и `DEMO_PASSWORD_HINT` в `.env` стенда, иначе карточка входа
продолжит показывать прежний: приложение о содержимом каталога ничего не знает.

### Путь, а не поддомен

Keycloak стоит **под путём `/auth` того же домена**, а не на своём поддомене: у стенда один
сертификат и одна запись в DNS, и поддомен стоил бы и того, и другого — ради демонстрации, которая
живёт неделями. `KC_HTTP_RELATIVE_PATH=/auth` заставляет его и отвечать по этому пути, поэтому путь
снаружи совпадает с путём внутри и ссылки, которые Keycloak строит сам, ведут туда же.

Плата за это — общее происхождение с приложением: cookie Keycloak живут на том же домене, пусть и
на своём пути. Они `HttpOnly`, но разделения по происхождению у них нет; поддомен дал бы его.
Решение обратимо: меняются `KC_HOSTNAME`, `KC_HTTP_RELATIVE_PATH`, адреса возврата в realm и
`location` в прокси.

`KC_HOSTNAME`, `KC_HTTP_RELATIVE_PATH`, `KC_PROXY_HEADERS`, `KC_DB*` и проверку здоровья задаёт
`docker-compose.prod.yml` — они описывают устройство развёртывания, а не его настройки, и в `.env`
их не пишут.

### Фрагмент прокси

В шаблон `deploy/nginx/crm.conf.example` этот фрагмент не входит — шаблон описывает прокси перед
приложением. Добавляется он в тот же `server`-блок, **до** `location /`:

```nginx
    # Keycloak: путь снаружи совпадает с KC_HTTP_RELATIVE_PATH, поэтому URI
    # передаётся как есть — без слеша в конце proxy_pass.
    location /auth/ {
        proxy_pass http://127.0.0.1:8098;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        # Обязательны оба: с KC_PROXY_HEADERS=xforwarded Keycloak берёт схему и
        # имя хоста отсюда. Без них он считает соединение незашифрованным и
        # разворачивает вход обратно на http.
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-Host $host;

        # Страница входа отдаёт свои заголовки безопасности сама —
        # Strict-Transport-Security, X-Frame-Options, X-Content-Type-Options,
        # Referrer-Policy, Content-Security-Policy и X-Robots-Tag. Повторять их
        # здесь через add_header нельзя: заголовки не заменяются, а
        # дублируются.
        proxy_buffer_size 32k;
        proxy_buffers 8 32k;
        proxy_busy_buffers_size 64k;
    }
```

Проверка после перезагрузки nginx:

```bash
curl -s https://<домен>/auth/realms/lct/.well-known/openid-configuration | head -c 200
```

В ответе `"issuer":"https://<домен>/auth/realms/lct"` — ровно тот адрес, по которому открывается
стенд. Если там оказался `http://` или имя контейнера, прокси не передаёт `X-Forwarded-*`, и вход
сломается на первом же перенаправлении.

## Обновление

```bash
cd /srv/lct-crm
git pull --ff-only
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
```

Пересобирается и заменяется только приложение; база, Redis и их тома остаются на месте,
новые миграции применяются при старте нового контейнера. Простой — несколько секунд.

Каталог прав приводит к коду не сид, а миграция: `scripts/migrate.ts` применяет миграции и
тут же заливает `seedRolesAndPermissions` ([`seeds.md`](seeds.md)) — одной транзакцией и без
единой строки данных. Запускается она на старте каждого контейнера, на любой установке,
поэтому релиз, добавивший право, выдаёт его ролям сам: делать после обновления ничего не надо.

**Полный сид (`pnpm run db:seed`) на боевой установке не запускают никогда.** Он заводит
демонстрационные учётные записи с общим и заведомо публичным паролем из `SEED_DEMO_PASSWORD` — при `DEMO_MODE=false`
ограничения демонстрации на них не действуют, то есть это обычные записи с полными правами
своей роли, — и заливает два десятка выдуманных вузов вперемешку с настоящими данными. Если
каталог прав всё же нужно обновить, не дожидаясь перезапуска приложения, есть ровно одна
ручка — та же операция и ничего кроме неё:

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml \
  exec app node scripts/seed/index.ts --roles-only
```

Откат — на предыдущий коммит той же командой. Миграции назад не откатываются: если релиз
менял схему, перед откатом нужен дамп (ниже) и ручное решение, что с данными.

## Логи, остановка, перезапуск

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml logs -f app
docker compose -f docker-compose.yml -f docker-compose.prod.yml restart app
docker compose -f docker-compose.yml -f docker-compose.prod.yml down        # тома целы
```

`down -v` удаляет тома вместе с данными — на сервере так не делают.

## Резервное копирование

Дамп базы (формат `custom`, сжатый, годится для `pg_restore`):

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml \
  exec -T postgres pg_dump -U lct -d lct -Fc > lct-$(date +%F).dump
```

Восстановление в пустую базу:

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml \
  exec -T postgres pg_restore -U lct -d lct --clean --if-exists < lct-2026-01-01.dump
```

Файлы документов лежат в MinIO, в томе `minio-data`, и в дамп базы не попадают: в ней только
ключи объектов. Бэкап хранилища — копия бакета наружу, объект в объект:

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml run --rm --no-deps \
  -v "$PWD/backup:/backup" --entrypoint sh minio-init -c \
  'mc alias set stack http://minio:9000 "$MINIO_ROOT_USER" "$MINIO_ROOT_PASSWORD" >/dev/null \
   && mc mirror --overwrite stack/lct-documents "/backup/lct-documents-$(date +%F)"'
```

В `backup/lct-documents-<дата>/files/` лягут обычные файлы с ключами вместо имён — их читает
кто угодно, MinIO для этого не нужен. Восстановление — тот же `mc mirror` в обратную сторону,
в пустой бакет (`mc mirror /backup/... stack/lct-documents`).

Базу и хранилище снимают вместе: запись в базе без объекта — битая карточка документа, объект
без записи — мусор, который никто не найдёт.

База Keycloak в этот дамп не попадает — она отдельная, и снимается отдельной командой
(`pg_dump -U lct -d keycloak -Fc`). Без неё восстановленный стенд поднимется, но войти в него будет
некому: учётные записи, роли и клиент живут там. Если realm не правили руками, дешевле не
восстанавливать её, а дать Keycloak импортировать `keycloak/realm-lct.json` в пустую базу заново —
это то же состояние.

Redis в бэкапе не нуждается: там сессии и кэш, они восстанавливаются сами.
Gotenberg и Mailpit состояния не хранят: почтовый ящик стенда живёт ровно столько, сколько идёт
показ.
