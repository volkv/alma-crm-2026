# Снимки и ролики README

Всё, что README показывает картинками, лежит в `docs/media/` и собирается скриптами из
`scripts/readme-media/`. Руками ничего не снимают: снимок, сделанный мышкой, устаревает молча —
экран переименовали, а картинка осталась прежней, и заметить это можно только случайно. Скрипт же
пересобирает любой кадр одной командой, и расхождение с продуктом видно сразу.

| Файл                                   | Что внутри                                                            |
| -------------------------------------- | --------------------------------------------------------------------- |
| `scripts/readme-media/shots.ts`        | список кадров README: имя файла, адрес, роль, что ждать перед съёмкой |
| `scripts/readme-media/help-shots.ts`   | список кадров встроенной справки — тем же устройством                 |
| `scripts/readme-media/capture.ts`      | съёмка кадров обоих наборов                                           |
| `scripts/readme-media/record.ts`       | запись роликов и сборка GIF через `ffmpeg`                            |
| `docs/media/*.svg`, `docs/media/*.jpg` | баннер, кнопки и логотип команды — рисованные, скриптами не берутся   |

## Что нужно

- поднятый стенд, в который можно войти;
- `SEED_DEMO_PASSWORD` — пароль демонстрационных записей **каталога учётных записей**; в репозитории
  его нет, он принадлежит той машине, на которой подняли Keycloak;
- для роликов — `ffmpeg` в `PATH`.

Съёмка ходит по стенду тем же путём, что и человек: нажимает «Войти», заполняет форму Keycloak,
возвращается в приложение. Другого входа в системе нет, и подделанная сессия снимала бы систему,
которой не существует.

## Как снять

```bash
docker compose up -d --build            # стенд целиком
export SEED_DEMO_PASSWORD='…'           # пароль демонстрационных записей каталога
export MEDIA_BASE_URL=http://localhost:3000

node scripts/readme-media/capture.ts --list        # что вообще снимается
node scripts/readme-media/capture.ts               # все кадры
node scripts/readme-media/capture.ts reports exchange   # только названные
node scripts/readme-media/record.ts                # все ролики
```

Кадр сохраняется в `docs/media/<имя>.png`, ролик — в `docs/media/<имя>.gif`. Имя кадра и есть имя
файла, на который ссылается README: добавили строку в `shots.ts` — добавили картинку.

Неснятый кадр не останавливает съёмку: скрипт печатает список несобранного и завершается ненулевым
кодом. Это не перестраховка — кадр обычно не снимается не потому, что сломан скрипт, а потому что
сломан экран: страница не ожила или на ней нет того, ради чего её открывали.

## Кадры встроенной справки

Снимки в статьях `/help` снимаются тем же скриптом и с того же стенда — другой набор кадров.
`MEDIA_BASE_URL` при этом указывает на тот стенд, с которого снимают: локальный
`http://localhost:3000` или публичный `https://crm.volkv.com` (пароль демонстрационных записей —
всё тот же `SEED_DEMO_PASSWORD` из окружения той машины, в репозитории его нет).

```bash
node scripts/readme-media/capture.ts --set=help --list      # что снимается
node scripts/readme-media/capture.ts --set=help             # все кадры справки
node scripts/readme-media/capture.ts --set=help user/reports-1 admin/audit-1   # только названные
```

Отличий от набора README три, и все они объявлены в `capture.ts` рядом со списками:

- **куда** — `static/help/`, то есть в статику приложения: статья ссылается на кадр адресом
  `/help/<раздел>/<имя>.png`. Адрес абсолютный, потому что тот же текст показывает страница
  `/help/print`, лежащая на другом уровне адреса;
- **окно** — 1280×860 вместо 1920×1200: кадр стоит внутри колонки статьи, и снимок с широкого окна
  читатель видит уменьшенным вместе с подписями, ради которых его и показывают;
- **вес** — готовый PNG пережимается палитрой через `ffmpeg` (`palettegen`/`paletteuse`, 256 цветов,
  без размывания). Кадры справки едут внутри образа и тянутся в браузер читателя, поэтому их вес —
  часть продукта: интерфейс из заливок и текста после пережатия весит втрое-вчетверо меньше, и
  разницы на экране не видно. Кадры README лежат в репозитории и открываются по одному, их не трогаем.

Имя кадра — это путь: `user/start-2` даёт `static/help/user/start-2.png`. Кадр, которому нужен не
адрес, а действие (открыть поиск по `Ctrl+K`, нажать строку в списке, прокрутить к блоку), приносит
свой шаг полем `prepare` — он выполняется после того, как страница ожила, и до съёмки.

Новая статья без снимка не проходит прогон: `e2e/help.test.ts` требует, чтобы у каждой статьи
реестра был хотя бы один кадр, чтобы он отдавался с кодом 200 и чтобы у него была подпись.

## Стенд для съёмки

Данные на кадрах — набор демонстрационного стенда (`scripts/seed`), и он детерминирован: адрес
карточки на любой машине получается один и тот же, поэтому `shots.ts` берёт идентификаторы у
`scripts/seed/ids.ts`, а не переписывает их числом.

Чтобы на кадре `exchange` был не пустой журнал, обмен на стенде должен что-то пережить. Порядок:

1. ключи обмена на стенде уже есть: их заводит сид по `EXCHANGE_API_KEY_CMS` и
   `EXCHANGE_API_KEY_LMS` из `.env` (`docs/seeds.md`, «Ключи обмена»), и теми же значениями
   представляются имитаторы. Выпускать ключ в интерфейсе и перезапускать `mock-cms`/`mock-lms` не
   нужно;
2. переменных в `.env` нет — задать их (по ключу на подключение, разные значения) и поднять стенд
   заново: `docker compose up -d`. Ключ заводится сидом при старте приложения, имитаторы получают
   его тем же `up`;
3. нажать триггер заявки: `curl -X POST http://localhost:58081/__send-application -H 'content-type: application/json' -d '{"form":"b2b"}'`;
4. дождаться, пока снимок статуса уедет обратно (`curl http://localhost:58081/__state`);
5. на карточке заведённого взаимодействия нажать «Отправить в LMS»;
6. вернуть результат потока: `POST /api/v1/exchange/learning-groups/results` ключом системы
   обучения (`EXCHANGE_API_KEY_LMS`; ключ сайта там получит `403`), тело — пример из
   `docs/exchange-contract.md`, раздел 6.

## Скринкаст

Ролики README показывают по разделу каждый; защите нужен связный проход по трём сценам README —
от заявки с сайта до выгрузки отчёта, тремя ролями подряд. Его записывает
`scripts/readme-media/screencast.ts`: своя сессия и свой контекст браузера на сцену, курсор в кадре,
паузы на ключевых состояниях, никаких ускорений. Готовый файл — mp4 (H.264, 1280×800, 25 кадров в
секунду), длительность — около трёх минут.

```bash
export MEDIA_BASE_URL=https://crm.volkv.com
export SEED_DEMO_PASSWORD='…'          # пароль демонстрационных записей каталога
export EXCHANGE_API_KEY_CMS='…'        # ключ сайта: им подаётся заявка
export EXCHANGE_API_KEY_LMS='…'        # ключ системы обучения: им приходит результат потока
export SCREENCAST_DIR=…                # каталог вне репозитория, куда лечь ролику

node scripts/readme-media/screencast.ts --list   # что за сцены и в каком порядке
node scripts/readme-media/screencast.ts          # запись целиком
```

Предварительные условия: поднятый стенд с настроенным обменом (адрес карточки заявки и адрес
заведения группы — в разделе «Интеграции»), `ffmpeg` и `ffprobe` в `PATH`. Ролик и таймкоды
(`timecodes.json`) кладутся в `SCREENCAST_DIR`; по умолчанию это временный каталог машины. **В
репозиторий видео не попадает**: оно весит десятки мегабайт и переснимается одной командой. Текст
закадра пишется по таймкодам и живёт там же, рядом с роликом, — в репозитории ему тоже не место.

**Что проход делает со стендом.** Он не притворяется: заявка подаётся ключом сайта в
`POST /api/v1/applications`, группа уезжает в систему обучения кнопкой с карточки, результат потока
приходит ключом системы обучения. Поэтому на стенде остаются: одно взаимодействие «Заявка с сайта:
…» с комментарием заявки, снимок-вложение к переходу, учебная группа и четыре строки журнала обмена.
Это демонстрационные записи, и они накапливаются от прогона к прогону — перед записью набело стенд
стоит вернуть к эталону кнопкой сброса демонстрационных данных («Настройки», право `settings.write`).

**Что проход возвращает обратно.** Две правки касаются общих данных, и обе откатываются тем же
путём, которым делались, — интерфейсом и от имени той же роли: ответственный за взаимодействие
(руководитель ставит Вересову и возвращает Менеджера Демо) и название стадии `communication` в
действующем процессе (администратор переименовывает её черновиком, применяет ко всем и вторым
черновиком возвращает прежнее имя). Возврат идёт и после обрыва: сцена, упавшая посередине, печатает
причину, после чего стенд всё равно приводится в прежний вид.

**Чего в записи не будет.**

- **Снимок статуса заявки уходит с отказом.** Имитатор сайта принимает статус только по той заявке,
  которую отправил сам, а заявку скрипта подаёт не он — и честно отвечает `404`. В журнале обмена
  это видно строкой «Не доставлено» и ответом получателя. Публичного адреса у `mock-cms` нет
  (`docker-compose.prod.yml`, `ports: !reset []`), поэтому снаружи стенда нажать его триггер нечем:
  сцену с зелёным статусом снимают с локального стека, где заявка подаётся через
  `__send-application` (см. «Стенд для съёмки»).
- **Результат потока стадию не подтверждает.** Подтверждение засчитывается только на стадии с
  признаком «Получены данные системы обучения», а в начальном процессе он выключен у всех стадий
  (`src/lib/server/stages/definitions.ts`, стадия `classes`). Взаимодействие заявки стоит на первой
  стадии, и система отвечает «стадия не подтверждена» — числа при этом приходят и видны на карточке.
- **Подписи самого браузера остаются английскими** — кнопка выбора файла и порядок частей в поле
  даты. В сборке Chromium, которую ставит Playwright, лежит только английская локаль; на языке
  страницы (`ru-RU`) и на подписях приложения это не сказывается.
