# Снимки и ролики README

Всё, что README показывает картинками, лежит в `docs/media/` и собирается скриптами из
`scripts/readme-media/`. Руками ничего не снимают: снимок, сделанный мышкой, устаревает молча —
экран переименовали, а картинка осталась прежней, и заметить это можно только случайно. Скрипт же
пересобирает любой кадр одной командой, и расхождение с продуктом видно сразу.

| Файл                                   | Что внутри                                                            |
| -------------------------------------- | --------------------------------------------------------------------- |
| `scripts/readme-media/shots.ts`        | список кадров README: имя файла, адрес, роль, что ждать перед съёмкой |
| `scripts/readme-media/help-shots.ts`   | список кадров встроенной справки — тем же устройством                 |
| `scripts/readme-media/capture.ts`      | съёмка кадров обоих наборов                                           |
| `scripts/readme-media/record.ts`       | запись роликов и сборка GIF через `ffmpeg`                            |
| `scripts/readme-media/screencast.ts`   | связный проход показа: сцены, таймкоды, субтитры                      |
| `docs/media/*.svg`, `docs/media/*.jpg` | баннер, кнопки и логотип команды — рисованные, скриптами не берутся   |

Кадру, которому на экране нужен второй человек — присутствие в карточке, живой комментарий,
непрочитанное упоминание, — оба набора кадров (`shots.ts` и `help-shots.ts`) дают поле `companion`:
второй сотрудник входит своей ролью и, если кадру нужно упоминание, до съёмки оставляет коллеге
комментарий с «@» в другом деле, а после — держит карточку кадра открытой своей вкладкой, пока снимок
не сделан. Когда упоминание было, `capture.ts` после съёмки сам открывает дело, где упомянули, — тем
же путём, что и человек, — и этим отмечает упоминание прочитанным: иначе непрочитанное на общем
демонстрационном стенде росло бы с каждым прогоном.

## Что нужно

- поднятый стенд, в который можно войти;
- `SEED_DEMO_PASSWORD` — пароль демонстрационных записей **каталога учётных записей**: локально это
  умолчание realm `lct-demo-2026`, на публичном стенде — то, что задали в его `.env` (пароль стенда
  публичный, `docs/security.md`, но принадлежит он машине, на которой подняли Keycloak);
- для роликов — `ffmpeg` в `PATH`;
- для кадра `organization-card` (README) — выход в интернет: он нажимает «Прочитать «Сведения» на
  сайте» и читает настоящий сайт вуза (`https://www.spbstu.ru`). Флаг «Внешние источники» включён
  сидом по умолчанию (`scripts/seed/settings.ts`); без сети кадр не снимется, но остальные не
  пострадают — `capture.ts` продолжает съёмку и после несобранного кадра.

Съёмка ходит по стенду тем же путём, что и человек: нажимает «Войти», заполняет форму Keycloak,
возвращается в приложение. Другого входа в системе нет, и подделанная сессия снимала бы систему,
которой не существует.

## Как снять

```bash
docker compose up -d --build            # стенд целиком
export SEED_DEMO_PASSWORD='…'           # пароль демонстрационных записей каталога
export MEDIA_BASE_URL=http://localhost:3000

node scripts/readme-media/capture.ts --list        # что вообще снимается
node scripts/readme-media/capture.ts               # все кадры
node scripts/readme-media/capture.ts reports exchange   # только названные
node scripts/readme-media/record.ts                # все ролики
```

Кадр сохраняется в `docs/media/<имя>.png`, ролик — в `docs/media/<имя>.gif`. Имя кадра и есть имя
файла, на который ссылается README: добавили строку в `shots.ts` — добавили картинку.

Неснятый кадр не останавливает съёмку: скрипт печатает список несобранного и завершается ненулевым
кодом. Это не перестраховка — кадр обычно не снимается не потому, что сломан скрипт, а потому что
сломан экран: страница не ожила или на ней нет того, ради чего её открывали.

## Подсказки первого входа и тема

Браузер съёмки каждый раз чистый, а подсказки первого входа показываются, пока их не закрыли, —
поэтому сразу после входа скрипт нажимает «Пропустить», как это делает человек. Ни `capture.ts`, ни
`record.ts` не подкладывают признак «показаны» в хранилище: скрытого выключателя в продукте нет, и
кадр, снятый с подложенным значением, показывал бы систему, которой не существует.

Два поля кадра меняют не страницу, а то, что помнит о человеке браузер, и такой кадр снимается в
своей сессии — иначе он менял бы все следующие снимки этой роли:

- `tour: true` — подсказки остаются открытыми: это и есть кадр (`onboarding`, `user/start-3`);
- `theme: 'dark'` — перед съёмкой переключатель в шапке доводится нажатиями до тёмного положения
  (`theme-dark`): кнопка одна, а положения идут по кругу. Нажимается именно переключатель, а не
  подменяется системная тема: на кадре должно быть видно и выбранное положение.

## Кадры встроенной справки

Снимки в статьях `/help` снимаются тем же скриптом и с того же стенда — другой набор кадров.
`MEDIA_BASE_URL` при этом указывает на тот стенд, с которого снимают: локальный
`http://localhost:3000` или публичный `https://alma.volkv.com` (пароль демонстрационных записей —
всё тот же `SEED_DEMO_PASSWORD` из окружения той машины; на самом стенде он написан на странице
входа).

```bash
node scripts/readme-media/capture.ts --set=help --list      # что снимается
node scripts/readme-media/capture.ts --set=help             # все кадры справки
node scripts/readme-media/capture.ts --set=help user/reports-1 admin/audit-1   # только названные
```

Отличий от набора README три, и все они объявлены в `capture.ts` рядом со списками:

- **куда** — `static/help/`, то есть в статику приложения: статья ссылается на кадр адресом
  `/help/<раздел>/<имя>.png`. Адрес абсолютный, потому что тот же текст показывает страница
  `/help/print`, лежащая на другом уровне адреса;
- **окно** — 1280×860 вместо 1920×1200: кадр стоит внутри колонки статьи, и снимок с широкого окна
  читатель видит уменьшенным вместе с подписями, ради которых его и показывают;
- **вес** — готовый PNG пережимается палитрой через `ffmpeg` (`palettegen`/`paletteuse`, 256 цветов,
  без размывания). Кадры справки едут внутри образа и тянутся в браузер читателя, поэтому их вес —
  часть продукта: интерфейс из заливок и текста после пережатия весит втрое-вчетверо меньше, и
  разницы на экране не видно. Кадры README лежат в репозитории и открываются по одному, их не трогаем.

Имя кадра — это путь: `user/start-2` даёт `static/help/user/start-2.png`. Кадр, которому нужен не
адрес, а действие (открыть поиск по `Ctrl+K`, нажать строку в списке, прокрутить к блоку), приносит
свой шаг полем `prepare` — он выполняется после того, как страница ожила, и до съёмки.

У каждой статьи реестра должен быть хотя бы один кадр: он отдаётся с кодом 200 и несёт подпись.

## Стенд для съёмки

Данные на кадрах — набор демонстрационного стенда (`scripts/seed`), и он детерминирован: адрес
карточки на любой машине получается один и тот же, поэтому `shots.ts` берёт идентификаторы у
`scripts/seed/ids.ts`, а не переписывает их числом.

Чтобы на кадре `exchange` был не пустой журнал, обмен на стенде должен что-то пережить. Порядок:

1. ключи обмена на стенде уже есть: их заводит сид по `EXCHANGE_API_KEY_CMS` и
   `EXCHANGE_API_KEY_LMS` из `.env` (`docs/seeds.md`, «Ключи обмена»), и теми же значениями
   представляются имитаторы. Выпускать ключ в интерфейсе и перезапускать `mock-cms`/`mock-lms` не
   нужно;
2. переменных в `.env` нет — задать их (по ключу на подключение, разные значения) и поднять стенд
   заново: `docker compose up -d`. Ключ заводится сидом при старте приложения, имитаторы получают
   его тем же `up`;
3. нажать триггер заявки: `curl -X POST http://localhost:58081/__send-application -H 'content-type: application/json' -d '{"form":"b2b"}'`;
4. дождаться, пока снимок статуса уедет обратно (`curl http://localhost:58081/__state`);
5. на карточке заведённого взаимодействия нажать «Заявить поток» на панели «Система обучения» и в
   открывшемся диалоге — «Отправить в LMS»;
6. вернуть результат потока: `POST /api/v1/exchange/learning-groups/results` ключом системы
   обучения (`EXCHANGE_API_KEY_LMS`; ключ сайта там получит `403`), тело — пример из
   `docs/exchange-contract.md`, раздел 6.

## Скринкаст

Ролики README показывают по разделу каждый; показу нужен связный проход — от заявки с сайта до
отчёта, тремя ролями подряд. Его записывает `scripts/readme-media/screencast.ts`: своя сессия и свой
контекст браузера на сцену, курсор в кадре, паузы под закадровый текст, никаких ускорений. Готовый
файл — mp4 (H.264, 1280×800, 25 кадров в секунду), длительность — от 2:40 до 2:50.

Закадровый текст лежит в самом скрипте, рядом со сценами, и это не украшение: реплика задаёт
минимальную длину сцены. Сцена, отыгранная быстрее, чем читается её текст, добирает паузу в конце, а
не обрезает фразу; из того же текста и измеренных длительностей собирается `subtitles.srt`.

### Сцены

`node scripts/readme-media/screencast.ts --list` печатает их вместе с ролью и длиной реплики.

| Сцена           | Роль          | Что в кадре                                                                                                                                                   |
| --------------- | ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `title`         | —             | титульная карточка: задача, обещание, команда                                                                                                                 |
| `hook`          | менеджер      | число отчёта → столбец воронки → карточка → раскрытое «Сделано на стадии» с отметкой по документу                                                             |
| `intake`        | администратор | «Демо: заявка с сайта», журнал обмена, взаимодействие, снимок статуса на стороне сайта                                                                        |
| `work`          | менеджер      | главное действие с условиями, закрытый шаг с объяснением, чек-лист, переход с комментарием и файлом, кто в деле, живой комментарий руководителя с упоминанием |
| `process`       | администратор | черновик действующего процесса, переименование стадии, предпросмотр затронутых, «Применить ко всем»                                                           |
| `handover`      | руководитель  | вход через каталог учётных записей в кадре, передача вуза другому менеджеру вместе с записями                                                                 |
| `handover-gone` | менеджер      | у прежнего ответственного записей по этому вузу больше нет                                                                                                    |
| `lms`           | руководитель  | «Заявить поток» → «Отправить в LMS», результат со страницы имитатора, раскрытое «Сделано на стадии»                                                           |
| `reports`       | менеджер      | срез и движение, клик по столбцу, вид PDF «Целиком», выгрузки XLSX и PDF, открытый файл                                                                       |
| `final`         | —             | финальная карточка: стенд, встроенная справка, описание API, репозиторий                                                                                      |

Карточки — не картинки, а страницы: они рисуются таблицами стилей самого стенда, поэтому цвета,
шрифт и ритм у них те же, что у экрана в следующем кадре. Адрес карточки принадлежит стенду, но до
сервера не доходит — запрос перехватывает сам скрипт.

### Как записать

```bash
export MEDIA_BASE_URL=https://alma.volkv.com
export SEED_DEMO_PASSWORD='…'          # пароль демонстрационных записей каталога
export SCREENCAST_DIR=…                # каталог вне репозитория, куда лечь ролику

node scripts/readme-media/screencast.ts --list   # сцены, роли, длина реплик
node scripts/readme-media/screencast.ts          # запись целиком
```

Ключи обмена скрипту не нужны: заявку подаёт имитатор сайта своим триггером — тем же, что жмёт
кнопка «Демо: заявка с сайта», — а результат потока присылает имитатор системы обучения со своей
страницы. Управляющие адреса имитаторов (`__state`, `__scenario`) не используются вовсе: они
закрыты токеном и раскрывают состояние стенда целиком.

В `SCREENCAST_DIR` ложатся `screencast-draft.mp4`, `timecodes.json` (сцены, роли, реплики),
`subtitles.srt` и `frames/<сцена>.png` — по ключевому кадру на сцену, снятому в её конце. **В
репозиторий видео не попадает**: оно весит десятки мегабайт и переснимается одной командой. Текст
закадра живёт там же, рядом с роликом.

### Субтитры и голос

Ролик пишется без звука и без вшитых субтитров: и то и другое добавляется после того, как текст
прочитан вслух. Обе операции — `ffmpeg`:

```bash
# субтитры в картинку: их видно там, где ролик смотрят без звука
ffmpeg -i screencast-draft.mp4 \
  -vf "subtitles=subtitles.srt:force_style='FontName=DejaVu Sans,FontSize=18,Outline=1,Shadow=0'" \
  -c:v libx264 -crf 20 -preset slow -pix_fmt yuv420p screencast-subtitles.mp4

# голос поверх готовой картинки
ffmpeg -i screencast-subtitles.mp4 -i voice.m4a -map 0:v -map 1:a \
  -c:v copy -c:a aac -b:a 128k -shortest screencast-final.mp4
```

Метки `subtitles.srt` — расчётные: внутри сцены фразы делят её время по числу слов. После записи
голоса их уточняют по нему, иначе субтитр расходится с тем, что слышно.

### Что нужно стенду

- поднятый стенд с настроенным обменом (адрес карточки заявки и адрес заведения группы — в разделе
  «Интеграции»), с работающими имитаторами по адресам `/mock-cms/` и `/mock-lms/`;
- демонстрационный режим: кнопка «Демо: заявка с сайта» появляется на экране «Внешние системы»
  только при `DEMO_MODE` и заданном адресе триггера имитатора;
- учётные записи `manager`, `lead`, `admin` и пароль к ним в `SEED_DEMO_PASSWORD`;
- `ffmpeg` и `ffprobe` в `PATH`;
- полная сборка Chromium, которую ставит Playwright, — скрипт просит её явно (`channel: 'chromium'`).
  «Headless shell», которым Playwright запускается по умолчанию, не годится: в нём нет файлов
  локалей, и подписи браузера в кадре — кнопка выбора файла и поле даты — остаются английскими.

### Что проход делает со стендом

Он не притворяется: заявку подаёт имитатор сайта, группу в систему обучения заводит человек кнопкой
с карточки, результат потока приходит от имитатора системы обучения. Поэтому на стенде остаются
демонстрационные следы: очередная ревизия заявки сайта и снимки её статуса, учебная группа с числами
на карточке «Ведение занятий», строки журнала обмена, история переходов с приложенным файлом, версии
процесса и записи о назначении ответственного за вуз. Всё это — демонстрационные данные; стенд
возвращают к эталону сбросом демонстрационных данных («Настройки», право `settings.write`), и он же
идёт по расписанию ночью.

Что проход возвращает сам, тем же путём, которым менял, — интерфейсом и от имени роли, которой это
по силам:

1. **вуз** — руководитель назначает прежнего ответственного обратно, вместе с незакрытыми записями;
2. **стадия заявки** — прежний ответственный возвращает её на исходную стадию и снимает пункты
   чек-листа, которые закрыл в кадре;
3. **название стадии процесса** — администратор переименовывает её вторым черновиком и применяет ко
   всем.

Порядок обязателен: пока вуз числится за другим менеджером, прежний ответственный записи не видит и
стадию вернуть не может. Возврат идёт и после обрыва: сцена, упавшая посередине, печатает причину,
после чего стенд всё равно приводится в прежний вид.

### Чего в записи не будет

- **Подтверждение стадии в сцене `lms` уже стоит до нажатия.** Стадию «Ведение занятий» на
  демонстрационном стенде подтверждает результат первого потока, который кладёт сид
  (`scripts/seed/interactions.ts`), — поэтому в кадре видно не появление отметки, а то, чем она
  поставлена: новый поток, числа от системы обучения и подпись «записью в системе обучения». Первым
  подтверждением это стало бы только на взаимодействии, доведённом до этой стадии в самой записи, —
  а это девять переходов.
- **Отметки по документу в кадре никто не ставит.** Крючок показывает уже подтверждённую стадию
  подписания: отметку по подписанному экземпляру ставит сид. Как её ставят руками — отдельный ролик
  раздела «Документы».
- **Числа отчёта в сцене `reports` — область менеджера,** а не стенда целиком: отчёт считается по
  области доступа того, кто его открыл, и после передачи вуза в предыдущей сцене записи по нему в
  выборку не входят.

## Полный обзор

Скринкаст рассказывает одну историю за три минуты; эксперту нужен обзор продукта целиком — шесть–восемь минут
по разделам README. Его записывает `scripts/readme-media/overview.ts` той же механикой (`film.ts`) и теми же
действиями в кадре (`acts.ts`), что и скринкаст, и показывает сверх них: сводку «Мой день», отказ сохранения поверх
чужой правки, карточку вуза со «Сведениями» с сайта, подбором программ, договорами и сверкой с ЕГРЮЛ, пакет
документов и отметку «Утверждён» на подписанном экземпляре, приглашение на встречу (.ics), список слушателей
потока, удаление стадии с предпросмотром переноса, матрицу прав и пространства, данные об обучении, карту
автоматизации, повторную подачу заявки без дубля, самодиагностику и Swagger.

```bash
export MEDIA_BASE_URL=https://alma.volkv.com
export SEED_DEMO_PASSWORD='…'
export OVERVIEW_DIR=…                  # каталог вне репозитория
node scripts/readme-media/overview.ts --list
node scripts/readme-media/overview.ts
```

В `OVERVIEW_DIR` ложатся `overview-draft.mp4`, `timecodes.json`, `subtitles.srt`, `voiceover.md` (реплики по сценам
с таймкодами) и `frames/`. Требования к стенду — те же, что у скринкаста, плюс включённые внешние источники
реквизитов (Dadata) для сцены карточки вуза.

Сам проход возвращает название и стадию заявки, ответственного за вуз, название стадии процесса. Удаление стадии
не применяется вовсе — черновик отменяется после предпросмотра. До ночного сброса остаются: собранное соглашение и
подписанный экземпляр с отметкой «Утверждён» (отметку снять нельзя), новый поток с результатом и тремя слушателями,
правки названия заявки, ревизии заявки сайта, версии процесса, записи о назначении ответственного, одно обращение
к Dadata.

Кнопка «Повторить» журнала обмена в обзор не попадает: на стенде нет недоставленных сообщений, а сломать имитатор
можно только управляющим адресом, закрытым токеном.
