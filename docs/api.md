# Публичный API

Машинный интерфейс CRM: им пользуются интеграции заказчика (выгрузки, обмен с Moodle и 1С,
отчётные роботы) и он же лежит в основе демонстрации «система не закрыта сама в себе».

Всё под `/api/v1` работает по одним и тем же правилам — их задаёт одна обёртка
(`src/lib/server/api/handler.ts`), а не каждый эндпоинт по-своему.

- Описание в машинном виде: `GET /api/openapi.json` (OpenAPI 3.1, без ключа).
- Описание для человека: `GET /api/docs` — Swagger UI. Это страница приложения, а не эндпоинт:
  не вошедшего она отправляет на `/login`, файлы интерфейса отдаются с нашего же адреса, и
  обращений к внешним CDN на ней нет.
- `GET /api/health` к API не относится: это проба живости для Docker и балансировщика.

## Как получить ключ

Ключ выпускает администратор (право `api_keys.manage`) на конкретного пользователя. Ключ
действует правами и областью доступа этого пользователя: у машины не может быть прав больше,
чем у человека, от имени которого она ходит.

Ключ выглядит как `lct_` и 32 символа: `lct_5Fj2Xq8pR0mN4vH7yB1cW6tK3sL9dZaQ`. **Он
показывается один раз — в момент выпуска.** В базе остаётся только `sha256`, поэтому
восстановить потерянный ключ неоткуда: его отзывают и выпускают новый.

Отзыв не удаляет ключ, а проставляет `revoked_at`: записи журнала ссылаются на ключ, и
удаление сделало бы их нечитаемыми.

### Служебные ключи обмена

Ключ действует правами **и областью** своего владельца — у машины не может быть прав больше, чем у
человека, от имени которого она ходит. У обмена с сайтом и системой обучения такого человека нет:
привязка к сотруднику отдала бы чужой системе его область, а придумывать ему живого владельца
нечестно. Поэтому такие ключи выпускаются на **машинного субъекта** — учётную запись роли `service`
(`service@exchange.lct-crm.local`), которая не входит в систему никогда.

Права роли закрыты и перечислены целиком: `exchange.intake`, `exchange.results`, `stages.confirm`.
Ни `interactions.write`, ни `stages.transition` она не получает: подтвердить стадию и вести процесс
— разные полномочия, и внешняя система имеет только первое.

Область такого ключа — `all`: заявка приходит по любому вузу. Ширина безопасна ровно потому, что
ключ роли `service` допускается **только к маршрутам, помеченным `service: true`** в описании
эндпоинта. На любом другом маршруте он получает 403 — и получает его раньше проверки права, чтобы
совпавшее право никуда его не пустило. Обычные маршруты API остаются людям.

**У такого ключа есть подключение обмена** — система (`cms` или `lms`) и экземпляр. Его выбирают при
выпуске, экземпляр берётся из настроек интеграций, а маршрут объявляет своё направление и сверяется с
ним: `POST /v1/applications` принимает только ключ сайта, `POST /v1/exchange/learning-groups/results`
— только ключ системы обучения, несовпадение — `403`. Без этой пары различить их нечем: права роли
`service` одинаковы у всех ключей обмена, и ключ сайта подавал бы результаты учебных групп, то есть
правил бы данные обучения в чужих взаимодействиях. У ключа на человека подключения нет и быть не
может; ключ, выпущенный до появления этой пары, на маршруты обмена не проходит — его отзывают и
выпускают заново.

## Как обращаться

```bash
KEY='lct_5Fj2Xq8pR0mN4vH7yB1cW6tK3sL9dZaQ'
BASE='https://crm.example.org/api'

# Список организаций: страница, фильтр по типу, поиск по наименованию и ИНН
curl -sS "$BASE/v1/organizations?page=1&pageSize=20&kind=educational_institution&q=СЗПУ" \
  -H "Authorization: Bearer $KEY"

# Одна организация
curl -sS "$BASE/v1/organizations/2f1c9a0e-6b3d-4a77-8f21-0c5e9d4b7a10" \
  -H "Authorization: Bearer $KEY"
```

Представляться можно только заголовком `Authorization: Bearer <ключ>`. Cookie сессии браузера
API не смотрит вовсе, даже если она пришла: иначе запрос со страницы приложения выполнялся бы
от лица пользователя без всякого ключа — это и есть CSRF.

Каждый ответ несёт `x-request-id`. Его стоит писать в лог интеграции: по нему обращение
находится в журнале действий системы одной строкой. Исключение — отказы безымянному вызывающему:
401 (ключа нет или он негоден) и 429 по лимиту адреса. До сервиса такой запрос не доходит, и журнал
пишет их не построчно, а одной записью `api.unauthenticated_burst` в минуту на адрес (почему —
`admin.md`). Отказ по лимиту самого ключа сюда не относится: за ним стоит известный владелец, и он
идёт обычной строкой `api.request`. Отладка ключа идёт по коду и тексту ошибки в ответе, а не по
журналу.

## Страницы списков

Список отдаётся конвертом:

```json
{ "items": [], "total": 137, "page": 1, "pageSize": 20 }
```

Параметры — `page` (с единицы) и `pageSize` (до 100). Те же имена у внутренних выборок: второй
словарь для одного и того же понятия — это способ однажды разойтись.

## Лимит частоты

- 120 запросов в минуту на ключ;
- 600 запросов в минуту на адрес — общий потолок, в него попадают и запросы без ключа.

Окно фиксированное, минутное. Каждый ответ несёт остаток:

```
RateLimit-Limit: 120
RateLimit-Remaining: 118
RateLimit-Reset: 41
```

Заголовки показывают тот из двух лимитов, который ближе к отказу. При превышении приходит
`429` и `Retry-After` в секундах; запрос, который не пропустили, всё равно засчитан.

## Идемпотентность

Изменяющие запросы (`POST`, `PUT`, `PATCH`) принимают `Idempotency-Key` — произвольную строку,
которую придумывает клиент (обычно UUID на попытку, а не на повтор):

```bash
curl -sS -X POST "$BASE/v1/interactions" \
  -H "Authorization: Bearer $KEY" \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: 6b1f0f4c-6a1a-4f0e-9a5d-2c9a5f0d1e77' \
  -d '{"title":"Переговоры с СЗПУ"}'
```

Ответ запоминается на 24 часа вместе с отпечатком тела:

| Повтор                          | Что будет                                                                            |
| ------------------------------- | ------------------------------------------------------------------------------------ |
| тот же ключ, то же тело         | тот же ответ, заголовок `Idempotency-Replay: true`, работа не выполняется второй раз |
| тот же ключ, другое тело        | `422`, код `idempotency_mismatch`                                                    |
| тот же ключ, ответ ещё не готов | `409`: первый запрос ещё выполняется                                                 |
| без заголовка                   | обычное выполнение, ничего не запоминается                                           |

Неудачный запрос не запоминается: повтор после ошибки выполнится заново.

## Ошибки

Любой неуспех приходит одним и тем же телом, без стека и без текста SQL:

```json
{
	"error": {
		"code": "validation",
		"message": "Запрос не прошёл проверку",
		"requestId": "0f0d1f0a-7c9a-4a0b-9f2e-1b7c3d4e5f60",
		"details": { "issues": ["query.page: Номер страницы — целое число"] }
	}
}
```

| Код                    | HTTP | Когда                                                                       |
| ---------------------- | ---- | --------------------------------------------------------------------------- |
| `validation`           | 400  | параметры или тело не прошли проверку; поля — в `details.issues`            |
| `unauthorized`         | 401  | ключа нет, он недействителен, отозван или владелец деактивирован            |
| `forbidden`            | 403  | владельцу ключа не хватает права — или это ключ обмена вне маршрутов обмена |
| `not_found`            | 404  | записи нет — или она вне области доступа владельца ключа                    |
| `conflict`             | 409  | действие противоречит состоянию записи                                      |
| `idempotency_mismatch` | 422  | ключ идемпотентности уже использован с другим телом                         |
| `rate_limited`         | 429  | превышен лимит частоты                                                      |
| `internal`             | 500  | ошибка на нашей стороне; `requestId` — то, что стоит нам прислать           |

Запись вне области доступа отдаётся как `404`, а не `403`: иначе перебором идентификаторов
можно было бы узнать, что существует за её пределами.

## Что уже есть

| Метод и путь                             | Право                | Что делает                                           |
| ---------------------------------------- | -------------------- | ---------------------------------------------------- |
| `GET /v1/organizations`                  | `organizations.read` | страница списка, фильтр `kind`, поиск `q`            |
| `GET /v1/organizations/{id}`             | `organizations.read` | карточка организации                                 |
| `GET /v1/interactions`                   | `interactions.read`  | страница списка: состояние, стадия, просрочка, поиск |
| `GET /v1/interactions/{id}`              | `interactions.read`  | карточка: стороны, программы, продукты, лента стадий |
| `POST /v1/interactions/{id}/transitions` | `stages.transition`  | шаг вперёд, возврат или пропуск; с `Idempotency-Key` |
| `POST /v1/applications`                  | `exchange.intake`    | заявка с сайта: контрагент, контакт, взаимодействие  |

**Обмен** (`docs/exchange-contract.md`) — три маршрута, и все три открыты только служебному ключу
роли `service`:

| Метод и путь                                | Право              | Что делает                                    |
| ------------------------------------------- | ------------------ | --------------------------------------------- |
| `POST /v1/applications`                     | `exchange.intake`  | заявка с сайта: создать или обновить          |
| `POST /v1/exchange/learning-groups/results` | `exchange.results` | результат учебной группы из системы обучения  |
| `GET /v1/exchange/files/{key}`              | `exchange.intake`  | вложение обмена по ключу объекта, телом файла |

Заявка с сайта — единственный эндпоинт, который заводит записи справочника: контрагента, человека и
его роль. Делает это не ключ, а сотрудник из настройки «Ответственный за входящие заявки»: у
машинного субъекта нет ни `organizations.write`, ни `interactions.write`. Тело — конверт обмена,
правила сверки и повторов — в [`integrations.md`](integrations.md).

Вложение обмена отдаётся **телом файла**, а не JSON: у него свой обработчик, а ключ, лимит частоты,
граница машинного субъекта и запись в журнал — те же самые, из того же кода. Отпечаток файла едет
заголовком `X-Exchange-Sha256`. Принадлежность сверяется с **подключением того ключа, которым
пришли**: ключ без подключения отвечает `403`, чужой ключ объекта — `404`.

Записи организаций через API пока нет: в `src/lib/server/directory/` есть только чтение.
Эндпоинт появится вместе с сервисом записи — обёртка для этого готова.

# Как добавить эндпоинт

Эндпоинт — это описание: схемы входа, схема выхода, право и вызов сервиса. Всё остальное
(ключ, лимит, идемпотентность, формат ошибки, журнал, `Cache-Control`) делает обёртка.

`src/routes/api/v1/<ресурс>/+server.ts`:

```ts
import type { RequestHandler } from './$types';
import { apiPageSchema } from '$lib/contracts/api';
import { interactionListQuerySchema } from '$lib/contracts/interactions';
import { apiHandler, type ApiEndpointConfig } from '$lib/server/api/handler';
import { registerRoute } from '$lib/server/api/openapi';
import { listInteractions } from '$lib/server/interactions/read';

const listInteractionsEndpoint = {
	auth: 'key',
	query: interactionListQuerySchema,
	output: apiPageSchema(apiInteractionSchema),
	permission: 'interactions.read'
} satisfies ApiEndpointConfig;

registerRoute({
	method: 'get',
	path: '/v1/interactions',
	summary: 'Список взаимодействий',
	tags: ['Взаимодействия'],
	config: listInteractionsEndpoint
});

export const GET: RequestHandler = apiHandler(listInteractionsEndpoint, async (ctx, { query }) => {
	const result = await listInteractions(ctx, query);

	return { ...result, items: result.items.map(toApiInteraction) };
});
```

Правила, которые стоят за этим кодом:

1. **Один объект на эндпоинт.** `registerRoute` и `apiHandler` получают один и тот же
   `satisfies ApiEndpointConfig`, поэтому документация не может разойтись с поведением.
   `satisfies` (а не аннотация типа) — чтобы обёртка вывела из схем типы `query`, `body` и
   `params` для обработчика.
2. **Путь в `registerRoute` — в нотации OpenAPI и относительно `/api`**: `/v1/interactions/{id}`,
   а не `/api/v1/interactions/[id]`.
3. **Изменяющий запрос — с `idempotent: true`.** Иначе повтор после разрыва связи создаст
   вторую запись.
4. **`output` обязателен и проверяется.** Ответ, не сошедшийся со своей схемой, наружу не
   уходит: это ошибка нашего кода, и клиент получает `500`, а не наполовину правильный ответ.
5. **Моменты времени переводятся в строки явно.** Внутренние представления несут `Date`,
   наружу уезжает ISO 8601 — это делает функция вида `toApiOrganization` в
   `src/lib/contracts/api.ts`, а не `JSON.stringify` «как получится».
6. **Люди — только через `toPersonView(ctx, person)`.** Маскирование контактов живёт там, и
   ответ API не исключение.
7. **Обработчик не смотрит в `event`.** Всё, что ему нужно, уже разобрано: `ctx` — кто
   обратился, `{ params, query, body }` — что прислал. Сервис принимает `(ctx, input)` и ничего
   не знает про HTTP.
8. **Новый код ошибки — в `API_ERROR_CODES`** (`src/lib/contracts/api.ts`) и в таблицу выше.
   Предметные ошибки (`ValidationError`, `ForbiddenError`, `NotFoundError`, `ConflictError`)
   переводятся в HTTP сами, добавлять для них ничего не нужно.

## Переход по стадиям и прочие действия

Действие, а не изменение записи, оформляется как `POST` на подресурс, например
`POST /v1/interactions/{id}/transitions`. Такому эндпоинту нужны `params`, `body`,
`permission: 'stages.transition'` и обязательно `idempotent: true`: повторённый переход по
стадиям — это вторая запись в истории взаимодействия, и защищает от неё только
`Idempotency-Key`.

## Где что лежит

| Файл                                     | Что в нём                                                                     |
| ---------------------------------------- | ----------------------------------------------------------------------------- |
| `src/lib/contracts/api.ts`               | конверт ошибки, конверт страницы, представления для JSON, схема выпуска ключа |
| `src/lib/server/api/handler.ts`          | обёртка: ключ, лимит, разбор, идемпотентность, ошибки, журнал                 |
| `src/lib/server/api/keys.ts`             | выпуск, отзыв, список и проверка ключей                                       |
| `src/lib/server/api/rate-limit.ts`       | фиксированное окно в Redis и заголовки `RateLimit-*`                          |
| `src/lib/server/api/idempotency.ts`      | память об ответах на сутки                                                    |
| `src/lib/server/api/openapi.ts`          | реестр маршрутов и сборка документа                                           |
| `src/lib/server/api/docs.ts`             | Swagger UI из локальных файлов                                                |
| `src/routes/api/openapi.json/+server.ts` | загружает файлы маршрутов и отдаёт документ                                   |

Все ключи API в Redis начинаются с `lct:api:` (`API_REDIS_PREFIX`) — по нему их видно в
`redis-cli --scan` и можно вычистить.

## Управление ключами из интерфейса

Странице настроек нужны три вызова из `src/lib/server/api/keys.ts`, все требуют права
`api_keys.manage`:

```ts
const created = await createApiKey(ctx, {
	name: 'Выгрузка в 1С',
	ownerUserId,
	// У ключа на человека подключения обмена нет; у ключа машинного субъекта оно обязательно.
	exchangeSystem: null
});
// created.key показывается пользователю ровно один раз и больше нигде не хранится
await listApiKeys(ctx); // ApiKeyView[]: без ключа и без хеша, отозванные тоже здесь
await revokeApiKey(ctx, apiKeyId);
```

Форма выпуска проверяется схемой `createApiKeySchema` (`src/lib/contracts/api.ts`). Поле
«Подключение обмена» появляется, когда владелец — машинный субъект: у ключа внешней системы оно
обязательно, у ключа на человека запрещено. Показывать `created.key` нужно так, чтобы его можно было
скопировать, и прямо говорить, что второй раз его не покажут.
