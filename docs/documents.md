# Документы

Всё, что связано с файлами: где они лежат, как попадают в систему, как генерируются по шаблонам
и как отдаются человеку. Код — `src/lib/server/documents/`, маршрут скачивания —
`src/routes/(app)/documents/[id=uuid]/download/+server.ts`.

## Хранилище

Файлы лежат объектами в S3-совместимом хранилище (`S3_ENDPOINT`, `S3_BUCKET`; в поставке это
MinIO из compose с томом `minio-data`):

```
<бакет>/
  files/<uuid>     готовый объект, ключ — идентификатор, без расширения
  tmp/<uuid>       объект, который ещё не проверен и не записан в базу
```

Ключ ничего не значит: тип, размер, хеш и название документа хранятся в таблице `documents`, а
`file_path` — это ключ объекта (`files/<uuid>`). Имя файла, под которым документ прислали, в
ключ не попадает: иначе список ключей читался бы как список организаций, а сами ключи
подбирались бы по названиям. Ключ приходит из базы, то есть формально это произвольные данные,
поэтому перед каждым обращением он сверяется с формой (`storedObjectKey`).

Наружу хранилище не смотрит: подписанных ссылок (presigned URL) приложение не выдаёт, и
единственный путь к файлу — маршрут скачивания с проверкой права и области доступа (см.
«Скачивание»). Ключи доступа приложения нужны ему только чтобы читать и писать объекты: бакет
заводит установка стека (`minio-init` в compose), а не приложение.

**Файл неизменяем.** Новая редакция документа — это новая запись и новый объект; перезаписи
существующего объекта в коде нет вовсе — каждая запись идёт на свой, только что придуманный
ключ. Иначе хеш, размер и даты согласования описывали бы файл, которого уже нет.

### Протокол записи

Хранилище и база не умеют фиксироваться вместе, поэтому запись разведена на шаги
(`storage.ts`):

1. `stageBlob(bytes, mime)` — проверка размера и содержимого, sha256, запись объекта
   `tmp/<uuid>`; хеш уходит вместе с телом (`x-amz-checksum-sha256`), и хранилище отвергает
   запись, если содержимое ему не соответствует;
2. `promoteBlob(blob)` — копирование на `files/<uuid>` внутри бакета и удаление временного
   объекта; тело файла второй раз по сети не едет;
3. `INSERT` в `documents` — уже в транзакции вызывающего сервиса.

Порядок шагов важен: тело файла уходит в хранилище до транзакции, а внутри неё идут только
команды. Транзакция не должна ждать чужую службу с двадцатью пятью мегабайтами в руках.

Если что-то сломалось после шага 1, вызывающий обязан позвать `discardStaged(blobs, error)`:
она убирает и временный объект, и объект в `files/`, если перенос успел пройти. Файл без
записи в базе — мусор, который никто не найдёт; запись без файла — битая карточка, поэтому
обратный порядок («сначала база») невозможен.

Удаления документов в системе нет: `discardStaged` — единственный путь, по которому объект
пропадает из хранилища, и он компенсирует только неудавшуюся запись.

Известное ограничение: объект, записанный на шаге 1, переживает падение процесса между шагами —
`discardStaged` зовётся из `catch`, а падения у `catch` нет. Такие объекты остаются под `tmp/`,
на них никто не ссылается, и хранилище само их не убирает: правило жизненного цикла на префикс
`tmp/` в бакете не настроено. Под `files/` такого мусора не бывает.

### Отказы хранилища

Любой отказ хранилища — это `DocumentStorageError` (`errors.ts`): русское сообщение плюс код
отказа (`NoSuchKey`, `NoSuchBucket`, `AccessDenied`). Адрес хранилища и ключи доступа, которые
S3-клиент кладёт в свои сообщения, наружу не выходят. Это отказ инфраструктуры, а не
предметная ошибка: он доезжает до 500 и до логов, а не превращается в «документ не найден».

Хранилище входит и в пробу живости: `pingStorage()` (дешёвый `HeadBucket` с потолком в 2 с)
отвечает за поле `storage` в `/api/health`, и без него эндпоинт отдаёт 503. Приложение, которому
некуда положить документ, здоровым не считается — см. [`deployment.md`](deployment.md).

### Проверка содержимого

`mime.ts` определяет тип по содержимому и сверяет его с заявленным. Тип, присланный клиентом,
ничего не доказывает: его выбирает браузер по расширению, а расширение выбирает человек.

| Формат           | По чему опознаётся                                                 |
| ---------------- | ------------------------------------------------------------------ |
| PDF              | `%PDF-`                                                            |
| PNG, JPEG        | сигнатура первых байтов                                            |
| DOCX, XLSX, PPTX | zip, внутри `[Content_Types].xml` и `word/`, `xl/` или `ppt/`      |
| DOC, XLS         | контейнер OLE2 и имя основного потока (`WordDocument`, `Workbook`) |
| ZIP              | zip, не похожий ни на один пакет Office                            |
| TXT              | корректный UTF-8 без управляющих байтов и без признаков разметки   |

Список допустимых типов (`ALLOWED_DOCUMENT_MIME_TYPES`) и потолок размера
(`MAX_DOCUMENT_SIZE_BYTES`, 25 МиБ) объявлены в `src/lib/contracts/documents.ts` — одна и та же
граница работает на форме, в API и в хранилище. Переименованный HTML, исполняемый файл и
подмена одного разрешённого типа другим отвергаются с `ValidationError`.

Потолок контракта — самый узкий из трёх и единственный, который умеет объяснить отказ. Выше
него стоят транспортные: `BODY_SIZE_LIMIT` у adapter-node (`27M` в обоих compose и в
`playwright.config.ts`) и `client_max_body_size` у прокси (`32m`). Их умолчания на это не
рассчитаны: у adapter-node оно 512K, то есть без явного значения 413 получает любой скан, ещё
не дойдя до маршрута. Таблица трёх потолков и порядок их изменения — в
[`deployment.md`](deployment.md#потолки-на-размер-загрузки).

## Шаблоны

Файлы шаблонов лежат в каталоге `templates/` в репозитории: шаблон — часть поставки, его правят
и ревьюят вместе с кодом. В базе (`document_templates`) хранится не он, а его копия в
хранилище: сгенерированный документ должен ссылаться на неизменяемый файл, иначе объяснить,
из чего он получился, уже нельзя.

`ensureTemplateRegistered(ctx, key)` (`templates.ts`) при первом обращении переносит файл в
хранилище и заводит запись; при каждом следующем сверяет sha256 файла из поставки с файлом в
хранилище. Совпало — ничего не пишется. Не совпало (шаблон поправили) или файла в хранилище нет
— заводится новая версия того же ключа, старый файл остаётся на месте. Отдельного шага
инициализации не нужно: генерация зовёт эту функцию сама.

### Теги

Разметка — docxtemplater с `paragraphLoop` и `linebreaks`. Простой тег — `{city}`, цикл —
`{#programs}…{/programs}`, внутри цикла доступны поля элемента (`{name}`).

Шаблон `agreement` («Соглашение о сотрудничестве»):

| Тег                                        | Что подставляется                             |
| ------------------------------------------ | --------------------------------------------- |
| `{city}`, `{date}`                         | место и дата подписания                       |
| `{operatorName}`, `{operatorSigner}`       | оператор и его подписант в родительном падеже |
| `{institutionName}`, `{institutionSigner}` | вуз и его подписант в родительном падеже      |
| `{customerName}`                           | заказчик подготовки                           |
| `{periodStart}`, `{periodEnd}`             | срок действия                                 |
| `{#programs}{name}{/programs}`             | список образовательных программ               |

**Необязательных тегов нет.** Тег, которому не нашлось значения, — это `ValidationError` с
перечнем тегов, а не пустое место в договоре: пустая строка выглядит как осознанное «не
применимо», хотя на деле это потеря данных. Проверок две: объявленные в шаблоне переменные
сверяются с ключами `data` до рендера, а теги, которых нет в объявлении (например, поле внутри
цикла), ловятся при рендере.

### Как добавить шаблон

1. положить `.docx` в `templates/`;
2. добавить ключ в `DOCUMENT_TEMPLATE_KEYS` и описание в `BUILT_IN_TEMPLATES` (`templates.ts`) —
   название, имя файла и список переменных с подписями для формы;
3. позвать `generateDocument` с новым `templateKey`; запись в `document_templates` появится
   сама при первом обращении.

Шаблон должен быть валидным пакетом OOXML: он проходит ту же проверку содержимого, что и
загружаемые файлы.

## Генерация

`generateDocument(ctx, { templateKey, interactionId?, data, title, formats })`
(`generate.ts`) требует права `documents.generate`, а при указанном `interactionId` — ещё и
того, чтобы взаимодействие было в области доступа.

DOCX собирается в памяти, PDF получается из него конвертацией. Своего рендерера PDF нет
намеренно: документ обязан выглядеть одинаково в обоих форматах, а это обеспечивает только
печать из того же DOCX. На каждый запрошенный формат создаётся своя запись `documents` с
`kind: 'generated'`; порядок ответа — `docx`, затем `pdf`.

Порядок шагов: рендер → конвертация → транзакция. Конвертация ходит по сети и может занять
секунды; держать всё это время открытую транзакцию значит держать блокировки из-за чужой службы.

Событие журнала — `documents.generated` с `templateId`, `documentId` и `interactionId`. Ключ
шаблона в подробности события не попадает: там допустимы только ссылки на записи.

### Gotenberg

Конвертация — `POST $GOTENBERG_URL/forms/libreoffice/convert`, потолок ожидания 30 секунд.
Отказ службы — `DocumentConversionError` (`errors.ts`); в её сообщении нет ни адреса Gotenberg,
ни любых других ссылок: по ним видно, что и где крутится за приложением. Это не ошибка
предметной области, поэтому в `$lib/server/errors` её нет и в 4xx она не переводится.

Кириллица работает без дополнительной настройки: в образе `gotenberg/gotenberg:8` (проверено на
8.37.0) есть DejaVu, Liberation, Carlito и Noto — 86 гарнитур с поддержкой русского языка.
Монтировать шрифты в контейнер не нужно; интеграционный тест это доказывает, вытаскивая русский
текст из готового PDF через `pdftotext`.

## Загрузка

`uploadDocument(ctx, { interactionId?, kind, title, file: { mime, bytes } })` (`upload.ts`) —
право `documents.write`, протокол записи из раздела «Хранилище», событие `documents.uploaded`.
Входные данные проверяются схемой `uploadDocumentSchema` из контрактов — той же, что и форма в
браузере: контракт на клиенте это удобство, а не защита.

Исходное имя файла не хранится: колонки под него нет, а имя при скачивании всё равно строится
из названия документа.

## Редакции

Файл неизменяем, поэтому исправленный документ — это новая запись со ссылкой на ту, которую она
заменила (`documents.supersedes_id`), а не правка старой. Три факта по документу (согласован,
утверждён, введён в действие) остаются на редакции: согласовывали конкретный файл, и переносить
его отметки на другой нельзя — их ставят заново.

`uploadDocumentRevision(ctx, { supersedesId, file })` (`upload.ts`) — право `documents.write`,
событие `documents.version_uploaded` с `documentId` и `supersededDocumentId`. Вид, название и
взаимодействие новая редакция берёт у заменяемой: иначе «редакцией» можно было бы назвать любой
другой файл, и цепочка перестала бы быть цепочкой одного документа. Форма поэтому спрашивает
только файл.

Одну редакцию заменяют один раз — это держит частичный уникальный индекс
`documents_supersedes_key WHERE supersedes_id is not null`. Без него у документа вырастает две
«следующих» редакции, и на вопрос «какая действует сейчас» ответа нет. Сервис проверяет то же
самое до записи и отвечает `ConflictError`: код `23505` человеку ничего не объясняет, а две
вкладки с одной и той же кнопкой — обычное дело.

**Действующая редакция** — та, которую никто не заменил. Цепочку целиком отдаёт
`listDocumentRevisions(ctx, documentId)`: рекурсивный запрос идёт от открытой записи вверх до
первой редакции и оттуда вниз по заменившим, поэтому карточка получает всю историю одним
обращением, а не по запросу на редакцию.

Заменённая редакция остаётся: её карточка открывается, файл скачивается, а на действующую ведёт
ссылка. Скрывают её только из списков — раздел `/documents` по умолчанию отбирает действующие
(`revisions=current`, параметра в адресе нет), а панель документов взаимодействия прячет
заменённые за переключателем и показывает у них пометку «Заменён редакцией от …».

Генерация по шаблону редакций пока не создаёт: за одну сборку появляется пара файлов (DOCX и PDF),
и какая из них какую заменяет — вопрос, на который команда генерации сейчас не отвечает. Повторная
сборка встаёт рядом отдельной парой, как и раньше.

## Скачивание

`GET /documents/<id>/download` — право `documents.read` плюс область доступа. Маршрут лежит
внутри оболочки приложения, а не в `/api`: это ссылка со страницы, и отвечать на отказ надо
страницей, а не JSON.

- файл читается потоком из хранилища, целиком в память не попадает;
- `Content-Disposition: attachment` с именем в двух видах — ASCII-запасным и `filename*` в UTF-8
  по RFC 5987 (без второго кириллица превращается в мусор);
- `Cache-Control: no-store` — документы бывают персональными;
- `X-Content-Type-Options: nosniff` — тип задаём мы, подбирать его по содержимому браузер не должен;
- событие журнала — `documents.downloaded`.

Перед отдачей размер объекта в хранилище сверяется с записью: файл неизменяем, и расхождение
означает, что в хранилище лазили мимо приложения. Пропавший объект — тоже отказ, а не пустой
ответ: так выглядит стенд, которому подменили бакет, и молчать об этом нельзя.

## Список документов

Раздел `/documents` — один список всех файлов системы: `listDocuments(ctx, query)` (`read.ts`)
и страница `src/routes/(app)/documents/`. Право — `documents.read`, область доступа — та же,
что у скачивания (см. ниже), и считается она прямо в условии выборки: чужой документ не
приходит на страницу вовсе, а не прячется в разметке.

Состояние списка (страница, размер, сортировка, поиск, фильтры) живёт в строке запроса, как во
всех списках продукта, — значит, отфильтрованный список это ссылка. Сервер отдаёт одну страницу
строк и общее их число; сортировка идёт по названию, формату, размеру или дате, а по умолчанию —
дата по убыванию: раздел открывают ради того, что появилось последним.

Колонка **«Вид»** отвечает на вопрос «откуда файл»: загружен человеком или собран по шаблону.
Отдельного столбца под это в схеме нет и заводить его незачем — генерация пишет в
`documents.kind` метку `generated` (`GENERATED_DOCUMENT_KIND` в контрактах), а загрузка кладёт
туда вид, который назвал человек. Поэтому «не `generated`» и означает «загружен», а названный
человеком вид показан рядом с названием: терять его нельзя, это единственное место, где он виден.

Колонка **«Формат»** — тип файла, названный расширением: `DOCUMENT_FORMAT_MIME_TYPES` в
контрактах. Соответствие объявлено явно, потому что `documents.mime` — произвольная строка из
базы, и придумывать неизвестному типу формат наугад нельзя; фильтр по формату отбирает по тому
же соответствию, а не по подстроке в mime.

Фильтров четыре — вид, формат, отметки и редакции; отметки отвечают и на вопрос «что ещё никто не
согласовал» (значение «Без отметок»), а редакции по умолчанию оставляют в списке только
действующие: заменённая никуда не девается, и без отбора соглашение из трёх редакций выглядело бы
как три разных соглашения. Поиск идёт по названию документа и по названию
взаимодействия: файл ищут по делу, к которому он приложен, не реже, чем по имени.

Загрузки «вне взаимодействия» в разделе нет. Документ появляется из карточки — там известно, к
какому делу он относится и кто стороны; форма загрузки без этого контекста заводила бы файлы,
которые потом некому предъявить. Поэтому пустой раздел — это ссылка на список взаимодействий, а
не кнопка «загрузить».

## Область доступа

Документ привязан к взаимодействию, а взаимодействие — к организациям-сторонам
(`interaction_parties`). Значит, документ виден тому, в чью область доступа попала хотя бы одна
из сторон. Документ без взаимодействия — типовая форма оператора, а не имущество организации:
к таким записям область не применяется, как и к программам с продуктами в справочнике.

Запись вне области отдаётся как `NotFoundError`, а не `ForbiddenError`: иначе перебором
идентификаторов можно узнать, что существует за её пределами.

## Отметки

`markDocument(ctx, documentId, fact, at?, note?)` (`status.ts`) — право `documents.write`, событие
`documents.status_changed` (в подробностях — изменённые поля и взаимодействие документа). Факты
(`agreed`, `approved`, `in_effect`) независимы: документ бывает согласован и не утверждён, а дата
вступления в силу вообще приходит из договора. `at` позволяет записать факт задним числом, `note` —
объяснить отметку словами.

Каждый факт ставится один раз, повторная попытка — `ConflictError`. Условие «ещё не отмечено»
живёт в самом `UPDATE`, а не в проверке перед ним: между чтением и записью отметку мог поставить
кто-то другой.

### Откуда отметку ставят

Три входа, один сервис:

| Вход                             | Что это                                                                 |
| -------------------------------- | ----------------------------------------------------------------------- |
| карточка документа               | форма внизу блока «Документ»: какой факт, каким днём и комментарий      |
| панель документов взаимодействия | кнопка «Отметить» в строке файла и диалог с теми же тремя полями        |
| `POST /v1/documents/{id}/marks`  | тело `{ fact, at?, note? }`, право `documents.write`, `Idempotency-Key` |

Форма предлагает только те факты, которых у документа ещё нет: снять отметку нельзя, и предлагать
поставить уже поставленную значило бы обещать команду, которой не существует. Исправляют отметку
так же, как исправляют файл, — новой редакцией: у неё свои отметки, и ставят их заново.

### День отметки

Отметка датируется **сутками**, а не моментом: согласовывают днём, а не минутой, и принятый момент
делал бы вид, что время известно. День приходит из календаря формы, момент по нему считает
`markMomentFromDay` (контракт): сегодняшний день — это «сейчас», прошлый — его начало по Москве.

Границы дня считает `markDayBounds`, а претензию к выбранному дню — `markDayIssue`; обе функции
живут в контракте и работают на обе стороны: форма ставит по ним `min` и `max` календаря, сервис
ими же отвечает на попытку выйти за границы. Второго свода правил на клиенте нет — разойтись двум
копиям одного правила негде.

- **не позже сегодняшнего дня** по московскому календарю: факта, которого ещё не было, не бывает;
- **не раньше дня, когда документ появился в системе** (`documents.created_at`).

Нижняя граница — компромисс, и его цена названа прямо: скан соглашения, подписанного до того, как
файл загрузили, датируется днём загрузки, а не днём подписи. Отдельного поля «дата документа» в
схеме нет, и пока его нет, единственная проверяемая нижняя граница — появление файла в системе;
без неё в отметку проезжает опечатка вида «2016» и остаётся там навсегда.

### Комментарий к отметке

Необязательный текст до 500 символов: номер протокола, кто подписал экземпляр, на каком совещании
утвердили. Хранится по колонке на факт — `agreed_note`, `approved_note`, `in_effect_note`, — а не
одной на документ: отметка неизменяема, и общий комментарий пришлось бы переписывать второй
отметкой. Виден рядом с бейджем отметки на карточке документа и в панели дела.

**В журнал действий комментарий не попадает.** Свободный текст в подробностях события запрещён —
там допустимы только ссылки на записи, имена полей и счётчики (`validateAuditDetails`), — поэтому
событие называет `approved_note` в списке изменённых полей, а содержимое остаётся в базе.

### Отметка подтверждает стадию

Документ, приложенный к взаимодействию, — это ещё и доказательство исполнения стадии. Если открытая
стадия ждёт отметку (`stages.requires_document_mark`, в поставляемом процессе это «Подписание
соглашения» и отметка «Утверждён»), движок засчитывает факт **той же транзакцией**, что и сама
отметка: «отметили, а подтверждение потеряли» — не то состояние, в котором система имеет право
оказаться. Взаимодействие при этом никуда не двигается: переход остаётся решением сотрудника.
Отдельного права на это нет — право произвести факт и есть `documents.write`; требовать сверх него
`stages.confirm` значило бы, что отметка по документу отказывает или нет в зависимости от того, на
какой стадии стоит дело. Подробности — `docs/stages.md`, раздел о готовности перехода.

## Тесты

- `tests/unit/documents/` — распознавание типов по содержимому, границы размера, имя файла и
  заголовок `Content-Disposition` с кириллицей, вычистка адресов из ошибки конвертации. Docker
  не нужен.
- `tests/unit/documents/marks.test.ts` — границы дня отметки, момент по выбранному дню и то, что
  схема принимает сутки, а не момент. Базы не требует: правило чистое.
- `tests/integration/documents/` — регистрация шаблона, генерация DOCX и PDF с русскими данными,
  отказ при незаполненном теге, компенсация при падении записи в базу, права и область доступа,
  однократность отметок, отметка задним числом и с карточки документа.
- `tests/integration/api/endpoints.test.ts` — отметка ключом API: задним числом, отказ дню из
  будущего, повтор по `Idempotency-Key` и `404` на документ вне области доступа.
- `tests/integration/stages/engine.test.ts` — отметка как доказательство стадии: отказ без неё,
  отметка ответственного её не заменяет, отметка другого вида не засчитывается, факт остаётся в
  закрытой записи и засчитывается при входе на стадию.
- `e2e/documents.test.ts` — отметка с карточки в браузере: форма, комментарий, бейдж и колонка
  «Отметки» в разделе.

Интеграционным тестам нужен **не только PostgreSQL в testcontainers, но и Gotenberg**: PDF
печатается настоящей службой, потому что проверяется именно она — конвертация и кириллические
шрифты в её образе. Поднимать контейнер руками не надо, это делает сам скрипт:

```bash
pnpm run test:integration   # docker compose up -d --wait gotenberg && vitest run --project integration
```

Отсюда два предусловия, одинаковых для машины разработчика и для CI:

- **Docker с плагином Compose** — и под testcontainers, и под сервис `gotenberg` из
  `docker-compose.yml`. Адрес службы тесты берут из `GOTENBERG_URL` (`http://localhost:3001`,
  как в `.env.example`);
- **`pdftotext`** (пакет `poppler-utils`) — им тест вытаскивает русский текст из готового PDF.
  На `ubuntu-latest` в GitHub Actions он есть из коробки.

Файлы документов в прогоне живут в MinIO из testcontainers (`tests/integration/helpers/storage.ts`):
контейнер поднимается на файл тестов и уезжает вместе с ним, своего каталога на диске тесты не
заводят.
