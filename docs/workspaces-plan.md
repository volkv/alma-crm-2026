# Пространства: технический план

Все семь шагов первой очереди из `docs/workspaces.md` выполнены (коммиты `82dfb40`…`bd68dd8`,
2026-09-23). Документ описывает, как это было сделано — точки касания в коде и проверки на каждом
шаге, — как запись для истории и образец для похожего перехода. Первый пункт второй очереди —
членство сотрудника в пространстве как граница доступа — сделан отдельной работой после плана
(`drizzle/0024_workspace_members.sql`, `docs/workspaces.md`, «Пространство — граница доступа»). Числа вхождений и списки файлов в «Карте
касаний» и по шагам — снимок на момент планирования, не то, что стоит перепроверять построчно
сегодня; путь и факт переименования по каждому шагу — проверены по текущему коду.

## Правила, общие для всех шагов

**Каждый шаг оставляет систему рабочей.** Проверка шага — зелёные типы, линтер и набор тестов, а
для шагов с видимым результатом ещё и открытый экран. Шаг, который нельзя предъявить, слишком
крупный и делится.

**Переименования идут миграцией, а не пересозданием.** `alter table … rename`, `alter table …
rename column` сохраняют данные, внешние ключи и индексы; `drizzle-kit` на переименование без
подсказки предлагает `drop`/`create`, поэтому SQL для шагов 1, 2 и 7 пишется руками, а
`drizzle-kit generate` используется как сверка, а не как источник.

**Порядок необратимости.** Шаги 1–2 меняют схему и откатываются только встречной миграцией. Шаги
3–6 — код и маршруты, откатываются `git revert`. Поэтому схему двигаем первой и убеждаемся, что
всё зелено, прежде чем трогать экраны.

**Что обязано уцелеть.** Ни один шаг не вправе нарушить три свойства работающего движка: одна
действующая редакция на процесс, один черновик на процесс, вечный реестр ключей стадий. Их
проверяет `tests/integration/stages/engine.test.ts` — этот набор должен проходить после каждого
шага, а не в конце.

## Шаг 1. Переименование группы в пространство

**Миграция** `drizzle/0019_workspaces_rename.sql`:

```
alter table process_groups rename to workspaces;
alter table interactions rename column process_group_id to workspace_id;
```

Плюс переименование ограничений и индексов, чтобы имена не врали:
`process_groups_key_key` → `workspaces_key_key`, `process_groups_position_key` →
`workspaces_position_key`, индексы по `interactions.process_group_id`. Внешние ключи Postgres
переносит сам.

**Код.** Схема `src/lib/server/db/schema/interactions.ts`: экспорт `processGroups` → `workspaces`,
поле `processGroupId` → `workspaceId`, комментарии переписываются под новое понятие. Дальше —
двадцать два файла из карты касаний, механически.

**Контракты.** `src/lib/contracts/interactions.ts`: `processGroupKey` / `processGroupName` в
`InteractionView` и в схемах списка. Это видно наружу — `src/routes/api/v1/`, — поэтому вместе с
ними правятся примеры OpenAPI, где сегодня стоит `'b2b'`.

**Проверка.** Полный прогон тестов. Экраны не меняются ничем, кроме имён в коде: доска по-прежнему
выбирает группу сама, `?group=b2b` по-прежнему работает.

## Шаг 2. Выделение процесса из пространства

**Миграция** `drizzle/0020_workflows.sql`, в одной транзакции:

1. `create table workflows` — `id`, `key` (уникален), `name`, `description`, `active_revision_id`
   (FK на `process_revisions`, `on delete restrict`), временные метки.
2. Строка процесса на каждое пространство: `insert into workflows (key, name, …) select key, name,
… from workspaces` — ключи совпадают, потому что сегодня процесс и место — одно и то же.
3. `alter table workspaces add column workflow_id uuid references workflows(id) on delete restrict`
   — **допускает пустоту**, заполняется по совпадению ключа.
4. `alter table process_revisions rename column group_id to workflow_id` и перенаправление FK на
   `workflows` по совпадению ключа; то же для `process_stage_keys`.
5. Перенос `active_revision_id` из `workspaces` в `workflows`, затем `alter table workspaces drop
column active_revision_id`.
6. Переименование частичного уникального индекса `process_revisions_one_draft_per_group` →
   `…_one_draft_per_workflow` и уникальности `(group_id, version)` → `(workflow_id, version)`.

**Код.** Основная работа — `src/lib/server/stages/process.ts`: всё, что брало редакцию по группе,
берёт её по процессу, а блокировка `FOR UPDATE` на время публикации переезжает с пространства на
процесс. Это важнее, чем кажется: блокировать пространство при публикации процесса, назначенного
двум пространствам, — значит пропустить гонку.

`ensureProcess(tx, groupKey, definition)` становится `ensureWorkflow(tx, workflowKey, definition)`;
`scripts/seed/process.ts` заводит процесс и привязывает к нему пространство двумя действиями
вместо одного.

**Проверка.** `tests/integration/stages/engine.test.ts` целиком, плюс новый случай: один процесс,
назначенный двум пространствам, — публикация редакции меняет процесс в обоих, а взаимодействия
переносятся в обоих.

## Шаг 3. Меню из базы

**Данные.** `src/routes/(app)/+layout.server.ts` отдаёт список пространств: `id`, `key`, `name`,
`position`, признак «процесс назначен». Загрузчик макета уже отдаёт пользователя и признак стенда —
пространства едут туда же и по той же причине: панель одинакова на каждой странице.

**Меню.** `src/lib/nav.ts`: `navGroups` перестаёт быть `as const`-списком из четырёх заголовков.
Появляется функция, которая собирает заголовки из постоянных («Главное», «Справочники»,
«Настройки», «Остальное») и по одному на пространство, вставляя их между первым и вторым. Секции
пространства — пока одна, «Взаимодействия», с правом `interactions.read`.

`sectionFor` в `src/lib/components/app-shell/nav-links.ts` сопоставляет по префиксу и продолжает
работать: у секции пространства префикс `/w/<key>/interactions`.

Правятся все потребители списка: `app-nav.svelte`, `app-dock.svelte`, `command-palette.svelte`.

**Проверка.** Экран открыт: в панели две новые секции с именами процессов, пункты ведут на
`/interactions` — адреса ещё старые. Секция пространства без процесса видна и ведёт туда же.

## Шаг 4. Маршруты под префикс

**Перенос.** `src/routes/(app)/interactions/**` → `src/routes/(app)/w/[workspace]/interactions/**`
целиком: список, `new`, карточка `[id=uuid]`, `lookup`.

**Отбор.** Параметр `group` уходит из `src/routes/(app)/w/[workspace]/interactions/filters.ts` —
из типа `InteractionFilters`, из `readFilters`, из `filtersHref` и из списка в
`clearedFiltersHref`. Пространство приходит из `params.workspace`.

`chooseBoardGroup` и `readGroupOptions` в `src/lib/server/interactions/board.ts` удаляются:
выбирать больше нечего, пространство задано адресом. Неизвестный ключ в адресе — 404, а не молчаливый
выбор соседнего.

**Ссылки.** Четырнадцать мест, где встречается `'/interactions'`, получают ключ пространства.
`resolve()` из `$app/paths` типизирован по объединению маршрутов, и у параметризованного пути
подпись другая — там, где сегодня стоит обходной приём с `Pathname & '/'`
(`nav-links.ts`), он может понадобиться и здесь.

Ссылки из разделов, которые сами пространству не принадлежат, — `documents`, `audit/labels.ts`,
`home/links.ts`, `reports/query.ts` — ведут на карточку взаимодействия, и ключ они берут из самой
записи: `interactions.workspace_id` уже есть в выборке.

**Совместимость.** `/interactions` остаётся как перенаправление на пространство, где у сотрудника
есть работа, — ровно та логика, которую удалили из доски, но теперь она живёт в одном месте и
однократно, а не подменяет содержимое экрана. Старые ссылки и закладки не ломаются.

**Проверка.** Открыты обе доски по своим адресам; у них разные колонки и разные карточки. Ссылка,
скопированная из адресной строки, у другого человека открывает то же самое.

## Шаг 5. Создание взаимодействия в пространстве

`resolveGroupForParties` в `src/lib/server/interactions/write.ts` (объявление около L99, вызовы на
L360 и L499) перестаёт выводить пространство из вида основной стороны — оно приходит параметром из
адреса.

Форма `new` в пространстве без назначенного процесса недоступна: стадии, на которую ставить запись,
не существует. Кнопка «Завести» на доске такого пространства не показывается, загрузчик формы
отвечает отказом со словами.

Приём заявки с сайта (`src/lib/server/integrations/exchange/intake.ts`) продолжает определять
пространство по таблице соответствий: у него нет человека, который выбрал бы.

**Проверка.** `tests/integration/interactions/interactions.test.ts`, `…/board.test.ts`,
`tests/integration/integrations/exchange.test.ts`.

## Шаг 6. Настройка пространств

Раздел `/settings/workspaces`: список, создание, переименование, порядок, назначение процесса.

`createWorkspace` / `renameWorkspace` / `reorderWorkspaces` в
`src/lib/server/stages/process.ts` рядом с остальной работой над процессом. Порядок —
`position` с уникальностью, поэтому перестановка идёт одной транзакцией со сдвигом соседей, а не
записью одного значения.

**Правило смены процесса:** назначить можно всегда, сменить — только пока в пространстве нет ни
одного взаимодействия. Проверка в команде, а не в форме: адрес набирают руками.

Право — `stages.configure`, то же, которым открывается редактор процесса.

**Проверка.** Заведено третье пространство, ему назначен один из существующих процессов, оно
появилось в меню со своей доской. Это и есть предъявление «движка» заказчику.

## Шаг 7. Разделение настроек процесса и маршрутов приёма

`/settings/process` разделяется: `/settings/workflows` — список процессов с созданием, редактор
`/settings/workflows/[key]` — тот же, что сегодня `/settings/process/[key]`, но открывается по
ключу процесса, а не пространства.

Миграция `drizzle/0021_workspace_intake_routes.sql`: `process_group_counterparty_kinds` →
`workspace_intake_routes`, колонка `group_id` → `workspace_id`. Первичный ключ по виду
контрагента **сохраняется**: приёму извне нужен однозначный адресат.

`resolveProcessGroup` в `src/lib/server/stages/process.ts` становится `resolveIntakeWorkspace` и
зовётся только из приёма заявок.

**Проверка.** Полный прогон; отдельно — что ручное создание взаимодействия не обращается к таблице
маршрутов ни разу.

## Риски (как разрешились)

**Переименование в двадцати двух файлах и двадцати тестах было механической работой и именно
поэтому опасной.** Поиск по `processGroup` не находил всё: строковые ключи в тестах, примеры в
OpenAPI, тексты в `src/routes/(app)/audit/labels.ts` и в справке требовали отдельного прохода
поиском по `group`. По коду на `205f0de` таких остатков не осталось: схема, контракты, тексты и
справка говорят «пространство» и «процесс».

**Шаг 2 переносил блокировку публикации.** Оставь `FOR UPDATE` на пространстве — процесс, назначенный
двум пространствам, опубликовался бы дважды одновременно. Решено переносом блокировки на
`workflows.id` (`lockWorkflow` в `src/lib/server/stages/process.ts`, `.for('update')` /
`.for('share')`): публикация меняет работу в обоих пространствах сразу, записи переезжают в обоих.

**Шаг 4 трогал типизированные маршруты.** `resolve()` разбирает аргумент по объединению всех путей
приложения, и вывод типов на этом объединении уже работал на пределе — в `nav-links.ts` был
обходной приём с комментарием об этом. Параметризованный сегмент `/w/[workspace]/` потребовал того
же приёма в дополнительных местах — по коду по-прежнему видно, где именно.

**Демонстрационный стенд.** `src/lib/server/demo/reset.ts` и сиды знали про две группы по ключам.
После шага 2 сид (`scripts/seed/process.ts`) заводит процесс и пространство раздельно, двумя
действиями: `ensureWorkflow`, затем `assignWorkflow` — порядок важен, потому что пространство без
процесса законно, а процесс без пространства — мусор.
