# Модули

Руководство для разработчика, который добавляет в Альма CRM свой модуль: термины, устройство папки
модуля, все слоты, граница между ядром и модулем, подключение модулю пространству, тесты и текущие
ограничения. Короткое введение в устройство — [`architecture.md`](architecture.md), раздел «Модули и
платформа».

## Термины

- **Ядро.** Всё, что работает независимо от того, какие модули установлены: маршруты
  (`src/routes/**`), серверные сервисы (`src/lib/server/**`), фасад платформы (`$lib/platform/**`),
  общий словарь (`$lib/contracts/**`), дизайн-система (`$lib/components/ui/**` и соседние). Ядро не
  знает, какие модули есть в поставке, — кроме реестров платформы, которым это положено (раздел
  «Граница» ниже).
- **Модуль.** Подключаемая единица продукта: папка `src/modules/<key>/` (модуль заказчика —
  `src/modules/custom/<key>/`) с манифестом. Манифест объявляет, что модуль добавляет в ядро — панели
  карточки, факты шапки, действия, пункты меню, шаблоны и виды документов. Модуль подключают одной
  строкой в `crm.config.ts`; без строки в конфиге модуля как будто нет, даже если папка на месте.
- **Слот.** Место в ядре, куда модуль может что-то положить: панель карточки, факт в шапке, действие
  карточки, пункт меню, шаблон или вид документа. Слоты открывает ядро, заполняют — модули. Все слоты
  разобраны в разделе «Слоты модуля» ниже.
- **Пространство.** Рабочее место направления (например, «Вузы» или «Физические и юридические
  лица»): свои взаимодействия, назначенный процесс и свой набор подключённых модулей. У одного и того
  же модуля в разных пространствах может быть разное состояние — включён в одном, выключен в другом.
- **Процесс.** Описание стадий работы с контрагентом. Процесс может **требовать** модуль — например,
  стадия с занятиями требует модуль обучения, — и тогда модуль действует в пространстве, даже если
  его отдельно не включали.

### Правило видимости

Слот модуля (панель, факт шапки, действие, пункт меню) виден, если выполняются оба условия:

1. **процесс выбрал слот** — там, где слот выбирают (например, состав карточки в редакторе процесса);
2. **модуль действует в этом пространстве.**

Модуль **действует**, если он **подключён** (в пространстве есть строка `workspace_modules`) **или**
**требуется** хотя бы одной стадией активной редакции процесса (`requiredByStage` в манифесте вернул
`true` или пункт её чек-листа закрывается правилом модуля). Модуль, который никто не подключал, но без которого не пройти обязательную стадию, обязан
быть виден — иначе на экране была бы стадия без инструмента её выполнить. Модуль бывает в трёх
состояниях относительно пространства: **установлен** (есть в `crm.config.ts`), **подключён** (строка
`workspace_modules`) и **действует** (подключён или требуется стадией). Функции над этими множествами
живут без базы в `$lib/platform/registry.ts` (`activeModules`, `requiredModules`, `visiblePanels`),
чтение из базы — `src/lib/server/platform/workspace-modules.ts` (`readActiveModules`).

## Модуль на диске

```
src/modules/<key>/                 (модуль заказчика — src/modules/custom/<key>/)
  index.ts            манифест: чистые данные и функции (обязателен)
  card.ts              панели, факты шапки, диалоги карточки (компоненты Svelte)
  card.server.ts       действия формы карточки, файлы, загрузка данных карточки
  sections.ts          страницы пунктов меню: компонент и значок
  sections.server.ts   загрузчики страниц
  ui/**, server/**     внутренности модуля: компоненты и серверный код, которые
                        больше никто не импортирует
```

`index.ts` — единственный обязательный файл: он же и есть модуль в смысле реестра, всё остальное —
как модуль заполняет слоты, которые сам объявил. Файл добавляют, когда модулю нужна соответствующая
часть: нет своей страницы меню — не заводят `sections.ts`/`sections.server.ts`; нет действий формы,
файлов и своих данных карточки — не заводят `card.server.ts`.

Ключ модуля — `^[a-z][a-z0-9-]{1,31}$` (`MODULE_KEY_PATTERN`, `$lib/platform/define.ts`). То же
ограничение стоит в базе (`workspace_modules_key_format`, `src/lib/server/db/schema/modules.ts`) и в
адресе страниц модуля (`/w/<пространство>/m/<модуль>/<раздел>`). По имени папка обычно совпадает с
ключом манифеста, но реестры находят модуль по ключу из `index.ts`, а не по имени папки: реестры
собирают все файлы `card.ts`/`sections.ts` под `src/modules/*/` и `src/modules/custom/*/` жадным
`import.meta.glob` и раскладывают их по ключу манифеста (`card-ui-registry.ts`,
`sections-registry.ts`).

### `index.ts` — чистый TypeScript, без сборки

`index.ts` читает не только приложение, но и миграция с сидом (`scripts/seed/aliases.ts`), которые
идут обычным процессом Node, — поэтому в манифесте нет `.svelte`, `import.meta.glob` и `enum`, а
импорты из `$lib/contracts/**` — только типами (`import type`). Это же требование лежит на всей
«чистой цепочке»: `crm.config.ts`, `$lib/platform/{define,config,core-panels,registry}.ts` и
`$lib/contracts/process-card.ts`. Нарушение ловит `tests/unit/platform/boundary.test.ts` (раздел
«чистая цепочка (сид исполняет её обычным Node)»).

## Подключение модуля

Модуль перечисляют в корневом `crm.config.ts` (рядом с `vite.config.ts`, вне `src/lib`) через
`defineConfig` (`$lib/platform/config.ts`):

```ts
import { defineConfig } from '$lib/platform/config';
import contracts from './src/modules/contracts/index.ts';
import payment from './src/modules/payment/index.ts';
import learning from './src/modules/learning/index.ts';
import meetings from './src/modules/meetings/index.ts';
// Модуль заказчика — одна строка импорта и ключ в списке:
// import acme from './src/modules/custom/acme/index.ts';

export default defineConfig({ modules: [contracts, payment, learning, meetings] });
```

Расширение `.ts` в пути пишут явно: без него сид, который читает конфиг обычным процессом Node, файл
не найдёт (хук Node иначе принял бы `.config` за расширение).

`defineConfig` проверяет установку при загрузке — на сборке, на старте приложения и в сиде, — и
роняет её с понятной ошибкой, если:

- модуль подключён в конфиге дважды (совпал ключ);
- две панели (ядра или модулей) заявили один ключ;
- у модуля дважды объявлен факт шапки, действие или пункт меню;
- у шаблона или вида документа два модуля-владельца.

## Новый модуль за 15 минут

Пример: модуль «Заметки партнёра» — одна панель карточки и один пункт меню. Модуль ничего не хранит
сам (свои таблицы — направление развития, раздел «Таблицы модуля» ниже), только показывает, что уже
доступно через фасад ядра. Папка — `src/modules/partner-notes/`.

**1. Манифест `index.ts`.**

```ts
import { defineModule } from '$lib/platform/define';

export default defineModule({
	key: 'partner-notes',
	label: 'Заметки партнёра',
	description: 'Свободная заметка о контрагенте на карточке и её список по пространству',
	panels: [
		{
			key: 'partner_notes',
			label: 'Заметки партнёра',
			hint: 'Короткая заметка о контрагенте, которую видят все, кто открывает карточку',
			order: 45
		}
	],
	headerFacts: [],
	cardActions: [],
	sections: [{ key: 'list', label: 'Заметки партнёра', permission: 'interactions.read' }],
	documents: { templates: [], kinds: [] },
	requiredByStage: null
});
```

`order: 45` ставит панель между «Оплатой» (30) и «Слушателями» (40) в общем каталоге
(`PANEL_CATALOG`, `$lib/platform/registry.ts`) — порядок на экране задаёт каталог, а не процесс.

**2. Панель карточки `card.ts` и её компонент.**

```ts
// card.ts
import { defineCardUi } from '$lib/platform/card-ui';
import manifest from './index';
import PartnerNotesPanel from './ui/partner-notes-panel.svelte';

export default defineCardUi(manifest, {
	panels: { partner_notes: PartnerNotesPanel },
	headerFacts: {},
	dialogs: null
});
```

```svelte
<!-- ui/partner-notes-panel.svelte -->
<script lang="ts">
	import type { CardPanelProps } from '$lib/platform/card-ui';

	let { model }: CardPanelProps = $props();
</script>

<p class="text-sm text-muted-foreground">
	Заметка о «{model.interaction.title}» — здесь модуль рисует своё содержимое.
</p>
```

**3. Пункт меню `sections.ts` + `sections.server.ts`.**

```ts
// sections.ts
import NotebookIcon from '@lucide/svelte/icons/notebook';
import { defineSectionsUi } from '$lib/platform/sections';
import manifest from './index';
import PartnerNotesListPage from './ui/partner-notes-list-page.svelte';

export default defineSectionsUi(manifest, {
	list: {
		component: PartnerNotesListPage,
		icon: NotebookIcon,
		description: 'Все заметки партнёра пространства одним списком.'
	}
});
```

```ts
// sections.server.ts
import { error } from '@sveltejs/kit';
import { defineSectionsServer } from '$lib/platform/sections.server';
import manifest from './index';

export default defineSectionsServer(manifest, {
	list: async ({ workspace, rest }) => {
		if (rest.length > 0) error(404, 'Такой страницы нет');

		// Настоящий список — следующий шаг: своя таблица (раздел «Таблицы
		// модуля») или чтение сервиса ядра через $lib/platform/core.server.
		return { workspaceName: workspace.name };
	}
});
```

`ui/partner-notes-list-page.svelte` получает эти данные в `data` (`SectionPageProps`), как и любая
страница модуля.

**4. Строка в `crm.config.ts`.**

```ts
import partnerNotes from './src/modules/partner-notes/index.ts';
// …
export default defineConfig({ modules: [contracts, payment, learning, meetings, partnerNotes] });
```

Дальше модуль подключают пространству («Модули пространства» ниже) — и панель с пунктом меню
появляются там, где процесс выбрал панель, а администратор подключил модуль.

## Слоты модуля

Всё, что модуль может добавить в ядро, объявлено типом `ModuleManifest` (`$lib/platform/define.ts`).
Поля обязательны, пустой массив или `null` — законное значение слота, которым модуль не пользуется.

### Панели карточки

`panels: PanelSpec[]` в манифесте (`key`, `label`, `hint`, `order`). Компонент — в `card.ts`
(`defineCardUi(manifest, { panels: { <key>: Component } })`). Панели ядра — `terms` и `documents`
(`$lib/platform/core-panels.ts`) — их не выключить вместе с модулем, панели модулей встают между ними
по `order`. Каталог собирает `PANEL_CATALOG` (`$lib/platform/registry.ts`); что панель рисует и когда
прячет себя изнутри (например, «Система обучения» показывает содержимое, если поток есть, если его
требует текущая стадия или если данных обучения не ждёт ни одна стадия процесса — тогда модуль
включён в настройках, и кнопка «Заявить поток» в панели — единственный путь к первому потоку) —
решает сама панель. Так же «Договор и позиции» молчит у физического лица: коммерческое обучение
принимает и лиц, и компании, процесс выбирает панель для обоих (эталонный — с миграции `0040`), а
договор с позициями есть только у компании; у стороны без договоров панель вместо «Выбрать договор»
ведёт «Создать договор» в карточку организации с `?return=<адрес карточки дела>` (число договоров
отдаёт `load` модуля). Пустая страница «Потоки и слушатели» ведёт туда же: к списку взаимодействий,
а если процесс не выбрал панель — к составу карточки процесса. Компонент панели получает `CardPanelProps`: `source`,
`model`, `can` (`{ edit, upload, generate }`), `supersessions` и `data` — то, что модуль сам загрузил
в `card.server.ts` (`load`), `undefined`, если модуль его не грузил.

Реестр карточных частей — `$lib/platform/card-ui-registry.ts`: жадный `import.meta.glob` по
`card.ts` всех модулей, `cardPanelComponent(panel)` отдаёт компонент по ключу панели. Панель из
манифеста без компонента в `card.ts` роняет сборку сразу — раньше, чем у сотрудника на экране
появилась бы пустая панель.

### Факты шапки

`headerFacts: HeaderFactSpec[]` (`key`, `label`, `shapes` — на каких видах контрагента виден: вуз,
физическое лицо, юридическое лицо). Компонент — в `card.ts` (`headerFacts: { <key>: Component }`),
получает `HeaderFactProps` (`model`, `label`, `hide`, `data` — то, что модуль загрузил в `load`, как у
панели) и рисует блок целиком: подпись и значение. Пример — факт «Договор» модуля «Договоры и
лицензии» у вуза и юридического лица, факты «Стоимость» (лицо и компания, из данных модуля) и «Оплата»
(лицо) модуля «Оплата». Собирает факты по виду контрагента и действующим модулям
`headerFactsFor` (`$lib/platform/card-ui-registry.ts`).

### Действия карточки

`cardActions: CardActionSpec[]` (`key`, `label`, `requires` — право того же языка, что
`summary.canDo.actions` взаимодействия, или `null`, если действие доступно всякому, кто видит
карточку, `deniedReason`, `menu`). У действия три способа появиться на экране:

- **пункт меню «Ещё».** Если `menu: true`, действие всегда стоит в меню карточки на любой стадии
  (`buildCardActions`, `src/lib/components/interaction-card/model.ts`, зовёт `cardActionSpecs`).
  Право проверяется тем же `can(spec.requires)`, что и у действий ядра, отказ подписан
  `deniedReason`;
- **кнопка у пункта чек-листа.** Кнопку ставит процесс, а не модуль: в описании пункта выбирают
  действие `<модуль>:<действие>` (`action`, каталог — `$lib/platform/checklist.ts`, туда входят
  действия всех установленных модулей), и у пункта появляется кнопка, пока модуль действует в
  пространстве (`buildRequirements`, тот же файл). Кнопка пункт не закрывает;
- **диалог.** `dialogs: Component<CardDialogProps> | null` в `card.ts` — один компонент на все
  диалоги модуля. Диалог слушает текущую команду через `getCardCommands()` (`$lib/platform/card`) и
  открывается, когда команда — `{ kind: 'module', module: <ключ>, action: <ключ> }`; так работает
  «Пригласить на встречу» (`src/modules/meetings/ui/invite-dialog.svelte`, функция `isInvite`).

Факт, который действие модуля сохраняет в деле, модуль пишет через `recordModuleFact` фасада
(`$lib/server/platform/module-facts.ts`; внутри своей транзакции — `recordModuleFactIn`): строка
истории правок с полем `<модуль>:<факт>` и значением `{ text, data }` (`$lib/platform/module-fact.ts`)
— готовой фразой и данными, по которым модуль узнаёт факт обратно (`readModuleFact`). Фразу
показывает лента карточки, а у пункта чек-листа с действием этого модуля — последний сохранённый
факт рядом. Так «Встречи» хранят назначенную встречу (действие `meetingSchedule`): дата,
длительность, место, `UID` и `SEQUENCE` события календаря — повторное назначение встречи, которая
ещё впереди, переносит её тем же `UID` с большим `SEQUENCE`. Своей таблицы ради одной даты модулю не
нужно. Ядро пишет так же ручную отметку оплаты (`payment:manual_mark`).

Правила пунктов-фактов (`completion.kind = 'fact'`) — закрытый каталог ядра
(`$lib/platform/checklist-rules.ts`), у правила есть владелец: `licenses_issued` и
`handover_act_approved` — «Договоры и лицензии», потоки и документ об обучении — «Обучение»,
`contract_concluded` — «Оплата». Процесс, выбравший правило модуля, делает модуль нужным стадии
(`requiredModules`): без модуля данных для такого пункта нет. Проверку правил делает ядро
(`src/lib/server/stages/facts.ts`, см. `docs/stages.md`, «Пункт чек-листа»).

Действие карточки объявляют в `card.server.ts` (`CardActionHandler` в
`$lib/platform/card.server.ts`) под тем же именем, что в форме — `action="?/<имя>"`. Реестр
(`$lib/platform/card-registry.server.ts`, `moduleCardActionHandlers`) заворачивает каждое действие
проверкой `assertModuleActive` и роняет сборку, если имя действия совпадает с действием ядра или
другого модуля.

### `load` — свои данные карточки

`load: CardLoad | null` в `card.server.ts` (`defineCardServer(manifest, { load })`). Зовётся только у
модулей, действующих в пространстве дела (`loadModuleCardData`,
`$lib/platform/card-registry.server.ts`); `interaction` в аргументах уже прочитан загрузчиком
карточки под правами того, кто её открыл, — область доступа проверять второй раз не нужно. Результат
кладётся в `data.moduleData[<ключ модуля>]` на странице карточки и уходит панели, факту шапки или
диалогу тем же ключом (`context-panels.svelte`: `moduleDataOf(panel)` находит владельца панели через `panelOwner` и
берёт `moduleData[owner]`; диалог получает `data.moduleData?.[dialog.module]` напрямую,
`interactions/[id=uuid]/+page.svelte`). Тип данных модуля стоит держать в отдельном файле
(`src/modules/meetings/data.ts`, `MeetingsCardData`), чтобы Svelte-компонент их не тянул через
`card.server.ts`.

### Файлы карточки

`files: Record<string, CardFileHandler>` в `card.server.ts`. Адрес —
`…/interactions/[id]/files/<модуль>/<файл>`, диспетчер — `serveModuleFile`
(`$lib/platform/card-registry.server.ts`): незнакомый модуль или файл — 404, затем
`assertModuleActive`, затем сам обработчик. Примеры — `roster.xlsx` («Обучение», список слушателей
потока) и `meeting.ics` («Встречи», приглашение на встречу файлом календаря). Оба возвращают
`Cache-Control: no-store` и `X-Content-Type-Options: nosniff` — файл несёт персональные данные,
хранить его в браузере или прокси незачем; имя файла в заголовке — через `contentDisposition`
(`$lib/platform/core.server`).

### Разделы меню (страницы модуля)

`sections: SectionSpec[]` в манифесте (`key`, `label`, `permission` или `null` — видно всякому, кто
вошёл в пространство). UI — `sections.ts` (`defineSectionsUi`: компонент страницы и значок
`LucideIcon`, необязательное `description` — подпись под заголовком), загрузчик — `sections.server.ts`
(`defineSectionsServer`).

Один маршрут-диспетчер на все страницы всех модулей —
`src/routes/(app)/w/[workspace]/m/[module]/[...path]/`, адрес — `/w/<пространство>/m/<модуль>/<раздел>`.
Модуль не кладёт файлов в `src/routes`: страницу открывает диспетчер, проверки идут по порядку, и
каждая отвечает своими словами:

1. модуль и такой раздел в манифесте существуют — иначе 404 «Такого модуля в системе нет» /
   «У модуля «…» нет такой страницы»;
2. у человека есть право раздела (`section.permission`) — иначе 403;
3. модуль действует в этом пространстве (`workspace.modules.includes(module.key)`) — иначе 404
   «Модуль «…» не подключён к пространству «…»» (не 403: страницы, как и пункта меню на неё, попросту
   нет);
4. только затем зовётся `loadModuleSection(module.key, section.key, { event, ctx, workspace, rest })`.

`rest` — сегменты адреса после ключа раздела; раздел без вложенных страниц отвечает на лишний
сегмент 404 сам (`error(404, …)` в загрузчике, как в примере выше и в «Обучении»). Пункт меню
пространства собирает `moduleNavSections` (`$lib/platform/sections-registry.ts`) — только у
пространств, где модуль действует, и только пока не убрано право раздела.

### `requiredByStage` — модуль, нужный стадии

`requiredByStage: ((stage: StageRuleInput) => boolean) | null`. `StageRuleInput` — часть стадии, по
которой решают: `key`, `name`, `requiresLmsData`, `lmsGroupPurposes`, `requiresDocumentTemplate`,
`checklist`. Модуль, для которого правило вернуло `true` хоть на одной стадии активной редакции,
**действует** в пространстве этого процесса без строки в `workspace_modules` и его нельзя выключить
(`setWorkspaceModule` отвечает конфликтом с названием стадии). `null` — стадиям модуль не нужен
(«Встречи»).

Примеры: «Обучение» нужно стадии, которая подтверждается данными LMS —
`stage.requiresLmsData || stage.lmsGroupPurposes !== null`; «Договоры и лицензии» нужны стадии,
которая ждёт отметки на сублицензии или акте передачи — `stage.requiresDocumentTemplate` совпадает с
одним из шаблонов модуля; «Оплата» нужна стадии, в чек-листе которой есть пункт «Оплата получена»
(`payment_received`, `PAYMENT_CHECKLIST_KEY` в `$lib/contracts/payments.ts`) — в эталонном процессе
коммерческого обучения это стадия «Договор и оплата».

Кроме правила манифеста модуль нужен стадии, в чек-листе которой пункт закрывается правилом этого
модуля (`CHECKLIST_RULES`, поле `module`): в эталонном процессе вуза «Обучение» поэтому нужно ещё
«Обучению преподавателей» и «Повышению квалификации», а в коммерческом — «Завершению и документу об
обучении».

### Документы: шаблоны и виды

`documents: { templates: string[]; kinds: string[] }`. Каталог шаблонов (`DOCUMENT_TEMPLATE_KEYS`,
`$lib/contracts/documents.ts`) и каталог видов документа (`UPLOADED_DOCUMENT_KINDS`, там же)
**остаются закрытыми в ядре** — на них держатся публичное API (`apiProcessSchema`), снимок стадии и
проверки в базе. Модуль не заводит новый ключ шаблона сам — он объявляет, каким из уже существующих
ключей каталога он **владеет**: `templateOwner`/`kindOwner` (`$lib/platform/registry.ts`), у каждого
ключа не больше одного владельца — проверяет `defineConfig` при загрузке. Сейчас «Договоры и
лицензии» владеют шаблонами `sublicense` и `handover_act`, «Обучение» — видом `certificate`; чтобы
добавить модулю новый шаблон, сперва добавляют его ключ в закрытый каталог ядра, а модуль в своём
`index.ts` объявляет владение им.

Шаблон доступен делу, только если его выбрал процесс **и** модуль-владелец действует в пространстве
дела: `offeredTemplates(выбор процесса, действующие модули)` (`$lib/platform/registry.ts`). Выбор
процесса при выключенном модуле не пропадает — шаблон вернётся, когда модуль снова подключат. Сервер
отказывает в сборке шаблона недействующего модуля («Шаблон «…» даёт модуль «…», он не подключён к
пространству «…»», `assertTemplateOffered` в `src/lib/server/stages/card.ts`); подробности —
[`documents.md`](documents.md), раздел «Шаблоны модулей».

С видом документа так же: сервер отказывает в загрузке документа вида, которым владеет недействующий
в пространстве дела модуль («Вид документа «…» даёт модуль «…», он не подключён к пространству «…»»,
`assertKindOffered` в `src/lib/server/documents/upload.ts`), — и новой редакции такого документа
тоже. Диалог загрузки такой вид и не предлагает, но форма могла быть открыта до выключения модуля.
Документ без дела под правило не попадает: пространства у него нет. Уже загруженные документы вида
остаются на месте.

## Граница между ядром и модулем

Модулю доступны только:

- `$lib/platform/**` — фасад ядра: типы манифеста, реестры, серверные и клиентские сервисы, которые
  модулю разрешено звать (`$lib/platform/core.server.ts` и `$lib/platform/card.ts`);
- `$lib/contracts/**` — общий словарь типов и схем, тот же, что использует ядро, — **кроме**
  `$lib/contracts/process-card`: каталог панелей строится из реестра, реестр читает конфиг, а конфиг
  собран из манифестов модулей, — импорт каталога модулем замкнул бы этот круг. Ключи своих панелей,
  фактов и действий модуль и так знает из собственного манифеста, второй раз их читать неоткуда;
- дизайн-система: `$lib/components/ui/**`, `$lib/components/*.svelte`, `$lib/components/form/**`;
- `$lib/format`, `$lib/utils`, `$lib/icon` и внешние библиотеки.

Модулю **недоступны**: `$lib/server/**` (внутренности ядра — сервисы, схема базы, права — только
через `$lib/platform/core.server.ts`), конкретные разделы ядра (`$lib/components/<раздел>/**`),
`src/routes/**` (маршруты модуля собирает диспетчер ядра) и папка любого другого модуля.

**`$lib/platform/core.server.ts`** — единственная дверь модуля в сервисы ядра. Список экспортов
закрытый и полный заранее: контекст действующего лица и ошибки, база и права, журнал, таблицы,
которые модули читают (`interactions`, `people`, `programs`, `documents` и другие), формы
(`$lib/server/forms.ts`), дело (`getInteraction`, `updateInteraction`), обмен с системой обучения,
справочник и люди, файлы, и `assertModuleActive`/`readActiveModules`. Новый экспорт сюда — решение о
границе ядра, а не просто «дать модулю ещё одну функцию»: расширяют список, только когда модулю
действительно нужен ещё один сервис ядра, и добавляют его туда же, рядом с похожими по смыслу
экспортами, с той же оговоркой в комментарии, что и у соседей.

Ядро в обратную сторону не знает о модулях: `src/lib/**`, `src/routes/**`, `src/hooks*.ts` не
импортируют `**/modules/**` и `crm.config*` — кроме реестров платформы
(`src/lib/platform/*registry*.ts`), которым это и положено (они читают конфиг и подключают модули к
ядру). Иначе сборка и типы ядра зависели бы от того, какие модули установлены в конкретной поставке.

Границу проверяют два независимых способа:

- **ESLint** (`eslint.config.js`, правило `no-restricted-imports` на `files: ['src/modules/**']` и на
  `files: ['src/lib/**', 'src/routes/**', 'src/hooks*.ts']`) — ловит нарушение при линте изменённого
  файла;
- **`tests/unit/platform/boundary.test.ts`** — сканирует всё дерево модулей разом: относительные
  импорты модуля не выходят за пределы его собственной папки, модуль не обращается к `$lib/server`, а
  «чистая цепочка» не тянет `.svelte`, `import.meta.glob` и `enum`.

## Модули пространства

Модуль подключают и отключают пространству в настройках — `/settings/workspaces` (право
`stages.configure`), сервис — `src/lib/server/platform/workspace-modules.ts`
(`setWorkspaceModule`). Что модуль даёт пространству, читается словами, а не ключом
(`moduleContributions`) — администратор решает по тому, что появится у сотрудников: «Панель
«Договор с позициями и лицензиями»», «Действие «Пригласить на встречу»» и так далее.

Панель модуля видна в карточке, только если её выбрал и процесс пространства (правило видимости
выше). Поэтому у действующего модуля настройки называют его панели, которых процесс не выбрал
(`unchosenPanels` в `listWorkspaceModules`), и ведут ссылкой «Настроить состав карточки» в редактор
процесса на вкладку «Состав карточки» (`/settings/workflows/<процесс>#card`).

**Отключение не удаляет данные модуля.** Договоры, потоки, отметки об оплате остаются на месте —
модуль подключают обратно, и работа на месте. Отключение — это удаление строки `workspace_modules`,
не таблиц модуля.

**Модуль, нужный стадии действующей редакции, выключить нельзя.** Он всё равно продолжил бы
действовать по правилу стадии, а настройки говорили бы «выключен» — `setWorkspaceModule` отвечает
конфликтом с названием стадии («Модуль «Обучение» нужен стадии «Ведение занятий» процесса пространства
«…». Выключить его можно, когда стадии перестанут его требовать»). Повторное включение и выключение
уже включённого/выключенного ничего не меняют и в журнал не пишутся; удачное переключение пишет
`workspaces.module_enabled`/`workspaces.module_disabled` (подробности события — пространство, ключ
модуля).

**Бэкфилл и сброс демо-стенда.** Таблица `workspace_modules` появилась миграцией
`drizzle/0038_workspace_modules.sql`; та же миграция раздала модули двум демостендовым пространствам
(`b2b`, `b2c`, заведены ещё миграцией `0006_process_groups_backfill.sql`) по тому, чем они уже
пользовались: «Встречи» — обоим, «Договоры и лицензии» — где процесс держит панель `contract` или
шаблоны сублицензии/акта, «Оплата» — где процесс держит панель `payment`, «Обучение» — где процесс
держит панели обучения или стадия подтверждается данными LMS. Сид (`scripts/seed/process.ts`) строки
`workspace_modules` не трогает: он только назначает пространствам процесс (`assignWorkflow`). Поэтому
сброс демо-стенда — это пересоздание базы и `pnpm run db:migrate` (миграция `0038` переигрывает
бэкфилл на пустых `workspace_modules`), а не `pnpm run db:seed`; свежий сид без миграций демостендовые
модули не восстановит.

## Таблицы модуля

Данные, которые показывают модули (договоры, потоки, оплата), живут в схеме ядра
(`src/lib/server/db/schema/**`), а миграции — общие для всей установки (`drizzle/*.sql`, генерируются
`pnpm run db:generate` по `drizzle.config.ts`, который сейчас смотрит на всю папку схемы разом). Модуль,
который хочет своё хранилище, сегодня заводит таблицу в общей схеме ядра — со всеми её миграциями, ревью
и границами транзакций — и получает её через `$lib/platform/core.server.ts`.

Пример — стоимость дела у «Оплаты»: таблица `interaction_terms` (`src/lib/server/db/schema/terms.ts`,
миграция `drizzle/0040_interaction_terms.sql`) — стоимость в копейках, валюта (только рубли) и своя
версия строки, чтобы правка стоимости не двигала версию плана и две вкладки не затирали друг друга.
Сервис — в папке модуля (`src/modules/payment/server/terms.ts`: `readInteractionTerms`,
`setInteractionTerms`), `load` модуля отдаёт условия панели «Стоимость и оплата» и факту шапки
«Стоимость», действие карточки `?/setPrice` называет или снимает стоимость. Правка пишется в журнал
событием `interactions.updated` с `changedFields: ['price']`; в историю плана карточки она не попадает —
её ведёт сервис дела.

**Следующий шаг** — развести схему по модулям: `schema` в `drizzle.config.ts` по маске путей модулей
(`src/modules/*/server/schema.ts` или похожей), чтобы своя таблица модуля жила в его собственной
папке и мигрировала отдельно от ядра. Это ещё не сделано; когда будет — раздел допишут примером.

## Тесты модуля и частые ошибки

Модульные проверки — `tests/unit/platform/registry.test.ts` (каталог панелей, правила стадий,
слоты) и `tests/unit/platform/card-registry.test.ts` (действия карточки за проверкой
`assertModuleActive`); интеграционный тест переключения, модулей, нужных стадиям, и отказа в загрузке документа вида
выключенного модуля — `tests/integration/modules/workspace-modules.test.ts`.
Новый модуль добавляет unit-тест на свой ключевой бизнес-инвариант — не на каждый слот.

Частые ошибки при разработке модуля:

- **Устаревший кэш Vitest/Vite при новых файлах под `import.meta.glob`.** Реестры платформы собирают
  `card.ts`/`sections.ts` модулей жадным `import.meta.glob` (`fsModuleCache: true` в `vite.config.ts`).
  Новый файл модуля, который должен попасть под этот `glob`, иногда не подхватывается прогретым
  кэшем Vitest — помогает `rm -rf node_modules/.vitest-cache`.
- **Импорт конфига без явного `.ts`.** `crm.config.ts` и манифесты читает не только сборка, но и
  сид/миграция обычным процессом Node — без расширения `.ts` в специфструкторе файл не найдётся (хук
  Node иначе принял бы `.config` за расширение).
- **Совпадение имени действия с ядром или другим модулем.** Реестр (`moduleCardActionHandlers`)
  роняет сборку при загрузке, а не откладывает ошибку до нажатия кнопки — сообщение называет оба
  имени модуля (или «ядро»), которые заявили одно действие.
- **Панель, факт шапки или раздел в манифесте без компонента.** Реестры (`card-ui-registry.ts`,
  `sections-registry.ts`) роняют сборку при загрузке, если в `card.ts`/`sections.ts` модуля нет
  компонента на объявленный в манифесте ключ.

## Ограничения текущей версии

Честно о том, что модульная граница сегодня не покрывает:

- **Обмен с LMS остаётся сервисом ядра.** Модуль «Обучение» решает, где и кому виден обмен с системой
  обучения, но сами сервисы (`$lib/server/integrations/exchange/**`) — часть ядра: их зовут не только
  карточка, но и сид, фоновые задачи и проверки, которым до модулей пространства дела нет. Модуль
  получает доступ к ним через `$lib/platform/core.server.ts`, а не владеет ими.
- **Реакция на отметку «Утверждён» для актов пока в ядре.** Списание позиций договора при отметке
  «Утверждён» на сублицензии или акте передачи (`markItemsTransferred`) живёт в
  `src/lib/server/documents/status.ts` — общем сервисе документов, а не в модуле «Договоры и
  лицензии», хотя шаблонами владеет именно он.
