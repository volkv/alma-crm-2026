# Модули

Набросок для будущего чтения заказчиком: термины модульной архитектуры, раскладка папки модуля,
подключение и граница между ядром и модулем. Полное руководство (пошаговое создание модуля, тесты,
шаблон документации) — следующая редакция этого файла.

## Термины

- **Ядро.** Всё, что работает независимо от того, какие модули установлены: маршруты
  (`src/routes/**`), серверные сервисы (`src/lib/server/**`), фасад платформы (`$lib/platform/**`),
  общий словарь (`$lib/contracts/**`), дизайн-система (`$lib/components/ui/**` и соседние). Ядро не
  знает, какие модули есть в поставке.
- **Модуль.** Подключаемая единица продукта: папка `src/modules/<key>/` (кастомные модули —
  `src/modules/custom/<key>/`) с манифестом. Манифест объявляет, что модуль добавляет в ядро —
  панели карточки, факты шапки, действия, пункты меню, шаблоны документов. Модуль подключают одной
  строкой в `crm.config.ts`; без строки в конфиге модуля как будто нет, даже если папка на месте.
- **Слот.** Место в ядре, куда модуль может что-то положить: панель карточки, факт в шапке, действие
  карточки, пункт меню, шаблон или вид документа. Слоты открывает ядро, заполняют — модули.
- **Пространство.** Рабочее место направления (например, «Вузы» или «Физические и юридические
  лица»): свои взаимодействия, назначенный процесс и свой набор подключённых модулей. У одного и
  того же модуля в разных пространствах может быть разное состояние: включён в одном, выключен в
  другом.
- **Процесс.** Описание стадий работы с контрагентом. Процесс может **требовать** модуль — например,
  стадия с занятиями требует модуль обучения, — и тогда модуль действует в пространстве, даже если
  его отдельно не включали (см. «Правило видимости панели» ниже).

## Раскладка папки модуля

```
src/modules/<key>/                 (кастомные — src/modules/custom/<key>/)
  index.ts            манифест: чистые данные и функции (обязателен)
  card.ts             панели, факты шапки, диалоги карточки (Svelte)
  card.server.ts      действия формы карточки, файлы, загрузка данных карточки
  sections.ts          страницы пунктов меню: компонент и значок
  sections.server.ts  загрузчики страниц
  ui/**, server/**    внутренности модуля: компоненты и серверный код, которые
                       больше никто не импортирует
```

`index.ts` — единственный обязательный файл. Остальные добавляются по мере того, как модулю нужны
панель карточки, серверные действия или собственная страница в меню. Ключ модуля — `^[a-z][a-z0-9-]{1,31}$`,
это же ограничение стоит в базе (`workspace_modules_key_format`) и в адресе страниц модуля.

## Подключение модуля

Модуль перечисляют в корневом `crm.config.ts` — рядом с `vite.config.ts`, вне `src/lib`:

```ts
import { defineConfig } from '$lib/platform/config';
import contracts from './src/modules/contracts/index.ts';
import payment from './src/modules/payment/index.ts';
import learning from './src/modules/learning/index.ts';
import meetings from './src/modules/meetings/index.ts';
// Модуль заказчика — одна строка импорта и ключ в списке:
// import acme from './src/modules/custom/acme/index.ts';
export default defineConfig({ modules: [contracts, payment, learning, meetings] });
```

Расширение `.ts` в пути пишут явно: без него сид, который читает конфиг обычным процессом Node,
специфструктор не разрешит.

## Граница

Модулю доступны только:

- `$lib/platform/**` — фасад ядра: типы манифеста, реестр установленных модулей, серверные и
  клиентские сервисы, которые модулю разрешено звать;
- `$lib/contracts/**` — общий словарь типов и схем, тот же, что использует ядро;
- дизайн-система: `$lib/components/ui/**`, `$lib/components/*.svelte`, `$lib/components/form/**`;
- `$lib/format`, `$lib/utils`, `$lib/icon` и внешние библиотеки.

Модулю **не** доступны: `$lib/server/**` (внутренности ядра — только через `$lib/platform`),
конкретные фичи ядра (`$lib/components/<фича>/**`), `src/routes/**` (маршруты модуля собирает
диспетчер ядра) и папка любого другого модуля.

Ядру в обратную сторону не доступны `src/modules/**` и `crm.config*` — кроме реестров платформы
(`src/lib/platform/*registry*.ts`), которым это и положено: они читают конфиг и подключают модули к
ядру.

Проверяют границу два независимых способа:

- **ESLint** (`eslint.config.js`, правило `no-restricted-imports`) — ловит нарушение при линте
  изменённого файла;
- **`tests/unit/platform/boundary.test.ts`** — сканирует всё дерево разом: относительные импорты
  модуля не выходят за пределы его собственной папки, модуль не обращается к `$lib/server`, а
  «чистая цепочка» (манифесты и ядро платформы, которые сид исполняет обычным Node) не тянет
  `.svelte`, `import.meta.glob` и `enum` — эти три вещи ломают запуск вне сборки.

## Правило видимости панели

Панель модуля на карточке видна, если выполняются оба условия:

1. **процесс выбрал панель** — она стоит в составе карточки, который настраивают в редакторе
   процесса;
2. **модуль действует в этом пространстве.**

Модуль **действует**, если он **включён** (в пространстве есть строка `workspace_modules`) **или**
**требуется** хотя бы одной стадией активной редакции процесса. Модуль, который никто не включал, но
без которого не пройти обязательную стадию, обязан быть виден — иначе на экране была бы стадия без
инструмента её выполнить.
