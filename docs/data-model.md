# Модель данных и контракты

Документ описывает устройство ядра: где лежит схема базы, как её менять, какими схемами
описаны команды и ответы и по каким правилам сервисы вызываются из транспортов.

Набор полей — гипотеза до получения технического задания заказчика. Имена нейтральные,
смысл каждого столбца объяснён комментарием рядом с ним; переименование полей после
уточнения требований — ожидаемое событие, а не авария.

## Схема базы

`src/lib/server/db/schema/` — по файлу на предметную область, `index.ts` реэкспортирует всё.

| Файл                  | Что внутри                                                                                                                                            |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `shared.ts`           | Повторяющиеся столбцы: `createdAt`/`updatedAt`, внешняя ссылка и её уникальность                                                                      |
| `auth.ts`             | `permissions`, `roles`, `role_permissions`, `users`                                                                                                   |
| `settings.ts`         | `app_settings`                                                                                                                                        |
| `audit.ts`            | `audit_events`                                                                                                                                        |
| `directory.ts`        | `organizations`, `sites`, `people`, `affiliations`, `consents`, программы и продукты, `directions`, `product_directions`, `organization_responsibles` |
| `directory-import.ts` | `directory_imports`, `directory_import_rows` — загрузка каталога и её строки                                                                          |
| `interactions.ts`     | Пространства и их реестры, процессы, редакции процесса, стадии и переходы, взаимодействия, записи стадий, паузы, блокировки, комментарии, договоры    |
| `documents.ts`        | `document_templates`, `documents`, `stage_entry_documents`                                                                                            |
| `exchange.ts`         | `exchange_messages`, `learning_groups`, `learning_group_results`                                                                                      |
| `api.ts`              | `api_keys`                                                                                                                                            |

Соглашения:

- идентификаторы — `uuid` с `gen_random_uuid()`; ключи справочника прав и ролей — текстовые
  коды, потому что на них ссылается код;
- имена в TypeScript camelCase, в PostgreSQL snake_case (`casing: 'snake_case'`);
- моменты времени — `timestamptz`, календарные (учебные и договорные) даты — `date`;
- `created_at` и `updated_at` есть у каждой сущности. Их нет у `audit_events` и
  `interaction_changes`: это события, у них уже есть `occurred_at` и `changed_at`, а менять
  их нельзя;
- перечисления объявлены значениями из контрактов (`pgEnum('...', ORGANIZATION_KINDS)`), чтобы
  список вариантов не разъехался между формой и таблицей.

### Внешние идентификаторы

У организаций, площадок, программ, продуктов и взаимодействий есть пара
`external_source` + `external_id` с частичной уникальностью
`(external_source, external_id) WHERE external_source IS NOT NULL`. Это основа
идемпотентного импорта: повторная загрузка той же выгрузки обновляет запись, а не плодит
дубли. Записи без внешней ссылки друг другу не мешают.

### Ограничения, которые держат инварианты

| Где                           | Что                                                                                                                                                         |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `organizations`               | CHECK: уровень образования заполнен ровно у учебных заведений                                                                                               |
| `organizations`               | Частичная уникальность ИНН `WHERE inn IS NOT NULL`                                                                                                          |
| `affiliations`                | Составной внешний ключ `(site_id, organization_id) → sites(id, organization_id)`                                                                            |
| `stage_entries`               | Частичная уникальность `(interaction_id) WHERE left_at IS NULL`                                                                                             |
| `stage_pauses`                | Частичная уникальность `(stage_entry_id) WHERE ended_at IS NULL`, CHECK `ended_at > started_at`                                                             |
| `documents`                   | Частичная уникальность `(supersedes_id) WHERE supersedes_id IS NOT NULL`, CHECK «не заменяет сам себя»                                                      |
| `consents`                    | CHECK `withdrawn_at >= given_at` и «автор отзыва только вместе с отзывом»                                                                                   |
| `audit_events`                | Триггер `BEFORE UPDATE OR DELETE` → исключение                                                                                                              |
| `organizations`               | CHECK: ссылка на человека заполнена ровно у вида `individual`; уникальный `person_id`                                                                       |
| `interaction_parties`         | Частичная уникальность `(interaction_id) WHERE is_primary` — основная сторона одна                                                                          |
| `organization_responsibles`   | Частичная уникальность `(organization_id, direction_id) NULLS NOT DISTINCT WHERE valid_to IS NULL`                                                          |
| `workspace_intake_routes`     | Первичный ключ по виду заявителя: маршрут приёма извне ведёт ровно в одно пространство                                                                      |
| `workflows`                   | Уникальность `key`; `workspaces.workflow_id` — `on delete restrict`: назначенный процесс не удалить                                                         |
| `process_revisions`           | Уникальность `(workflow_id, version)`; частичная уникальность `(workflow_id) WHERE published_at IS NULL`                                                    |
| `stages`, `stage_transitions` | Уникальность `(revision_id, key)` и `(revision_id, position)`; `(from_stage_id, to_stage_id)`; CHECK `on_enter_notify` — `responsible`, `manager` или пусто |
| `stage_migration_rules`       | Уникальность `(revision_id, removed_stage_key)`, CHECK «ключи различны»                                                                                     |
| `process_stage_keys`          | Первичный ключ `(workflow_id, key)`: строка заводится с первым появлением ключа и не удаляется никогда                                                      |
| `interaction_contract_items`  | Составной внешний ключ `(contract_item_id, contract_id) → contract_items(id, contract_id)`                                                                  |
| `users`                       | Частичная уникальность `external_subject`, CHECK «сам себе не руководитель»                                                                                 |
| `exchange_messages`           | Уникальность `(direction, system, instance, event_id)` — повтор доставки не плодит строк                                                                    |
| `learning_groups`             | Уникальность `(interaction_id, stream_number)`; частичная уникальность внешнего идентификатора                                                              |
| `learning_group_results`      | CHECK `completed + expelled <= enrolled`                                                                                                                    |
| `directory_imports`           | CHECK «состояние `confirmed` ровно тогда, когда заполнен `confirmed_at`»                                                                                    |
| `directory_import_rows`       | Уникальность `(import_id, row_no)`; CHECK «действие `error` ровно тогда, когда у строки есть претензии»                                                     |

Составной внешний ключ у `affiliations` заменяет триггер: при `site_id IS NULL` правило
MATCH SIMPLE ничего не требует, а при заполненной площадке она обязана принадлежать той же
организации. Ради него у `sites` есть избыточный на первый взгляд уникальный ключ
`(id, organization_id)` — сослаться можно только на уникальный набор столбцов. Удаление
оставлено NO ACTION: проверка откладывается до конца оператора, поэтому каскад от
организации проходит, а точечное удаление площадки, на которую ссылается роль, отвергается.

### Импорт каталога

`directory_imports` и `directory_import_rows` — это **журнал загрузки, а не копия справочника**.
Результат импорта живёт в своих таблицах: организации, продукты, направления, договоры и позиции
после применения ничем не отличаются от заведённых руками. Эти две таблицы отвечают на другой
вопрос — «откуда в справочнике взялась эта строка и что именно импорт с ней сделал».

| Таблица                 | Что внутри                                                                                                                                          |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `directory_imports`     | Загрузка целиком: состояние, исходный файл, сопоставление колонок, счётчики строк по действиям, автор и момент применения                           |
| `directory_import_rows` | Строка файла: место в нём, разобранные значения, действие, претензии, что заводит и что меняет, ссылки на заведённые организацию, продукт и договор |

Разобранные значения хранятся отдельно от `raw` намеренно: применение работает с ними, а не с
текстом ячейки, — между предпросмотром и подтверждением файл читать заново нельзя, потому что человек
согласился с тем, что увидел. Ссылки на записи справочника — `on delete set null`: запись могут
архивировать и удалять своей жизнью, а строка загрузки остаётся.

CHECK «действие `error` ровно тогда, когда у строки есть претензии» держит правило раздела: строка с
претензией ничего не записывает, и «ошибка» в предпросмотре означает то же, что и в справочнике.
Правила самого импорта — в [`directory.md`](directory.md#импорт-каталога).

### Персональные данные и редакции документов

Почта и телефон человека лежат в `people` **зашифрованными**: `enc:v1:<вектор>:<шифртекст>:<тег>`
в base64, AES-256-GCM, свой вектор на каждое значение, ключ — `PII_ENCRYPTION_KEY` из окружения
установки. Шифртекст одного и того же адреса каждый раз разный, поэтому сравнивать по нему нельзя,
и рядом лежат `people.email_hash` и `people.phone_hash` — HMAC-SHA256 по нормализованному значению
(почта без пробелов и в нижнем регистре, телефон одними цифрами с ведущей `7` вместо `8`). По ним
идут дедупликация заявок с сайта, дедупликация импорта каталога и поиск по точному контакту; поиска
по части адреса или номера нет. Собирает и читает эти четыре колонки один модуль —
`src/lib/server/people/pii.ts`, — а расшифровывает наружу только сериализатор (ниже, «Контакты
людей»). Подробности и границы меры — в [`security.md`](security.md#шифрование-персональных-данных).

`comments.source` (`manual`, `application_intake`) отвечает на вопрос «кто написал этот текст».
Колонка нужна уничтожению персональных данных, а не экрану: свободный текст заявки с сайта — это
то, что человек написал о себе сам, вместе с фамилией и телефоном внутри, и уничтожение заменяет
его пометкой; комментарии сотрудников остаются, это содержание работы. По автору их не различить —
комментарий заявки подписан тем сотрудником, который принимает входящие. В схему запроса источник
не входит и прийти снаружи не может: «это написал заявитель» — утверждение системы о происхождении
текста. Строки, заведённые до появления колонки, считаются текстом сотрудника (миграция `0018`).

`people.retention_until` (дата) и `people.anonymized_at` отвечают на вопрос «до какого дня данные
хранятся и когда их уничтожили»; `consents` — на вопрос «на каком основании они лежат». Основание
задано перечислением `consent_basis` (`consent`, `contract`, `legal`): это ссылка на норму, а не
заметка. Даты получения и отзыва согласия — календарные (`date`), потому что согласие подписывают
днём, и точность до секунды в нём ничего не значит.

`documents.supersedes_id` — ссылка на редакцию, которую этот файл заменил. Файл неизменяем, поэтому
история документа — цепочка записей, а не версии одной строки. Частичный уникальный индекс
`documents_supersedes_key` держит правило «одну редакцию заменяют один раз»: иначе у документа
вырастает две «следующих» редакции и на вопрос «какая действует» ответа нет. Удаление ссылки —
`set null`: поштучно документы не удаляются вовсе, а каскад от взаимодействия сносит всю цепочку.
Подробности — в [`documents.md`](documents.md#редакции).

### Представление `stage_entry_status`

Срок стадии с учётом пауз. Создаётся custom-миграцией, в схеме объявлено через
`pgView(...).existing()` — Drizzle знает его форму и умеет из него выбирать, но не пытается
им управлять.

Окно записи — от входа на стадию до `left_at`, а у открытой записи до `now()`.
`paused_seconds` — суммарная длина пересечения пауз с окном (открытая пауза считается до
конца окна), и ровно на неё сдвигается `due_at`. Закрытая запись перестаёт «ехать»: её окно
больше не растёт. Норматив берётся из `stage_snapshot`, а не из таблицы `stages`: процесс
могли изменить, а срок уже пройденной стадии обязан остаться прежним.

Протухание считается не здесь: оно про тишину вокруг взаимодействия, а не про часы на
стадии, и опирается на `interactions.last_activity_at`, который обновляют сервисы.

### Схема m2: что уже добавлено и кто доводит переход

Предметная модель контура m2 описана в [`domain.md`](domain.md); здесь — состояние кода. Префлайт
(`drizzle/0005_*`, `drizzle/0006_*`) добавил всё новое **и ничего не удалил и не переименовал**:
приложение продолжало работать на прежних таблицах, а переименования и удаления делает та задача,
которая владеет соответствующим кодом. Иначе схема и сервисы разъехались бы на середине волны.

Добавлено префлайтом: таблицы `directions`, `product_directions`, `organization_responsibles`,
`workspaces` (тогда `process_groups`), `workspace_intake_routes` (тогда
`process_group_counterparty_kinds`), `process_stage_keys`,
`stage_migration_rules`, `contracts`, `contract_items`, `interaction_contract_items`,
`stage_entry_documents`, `learning_groups`, `learning_group_results`, `exchange_messages`; колонки
`organizations.person_id`, `users.manager_user_id`, `users.external_subject`,
`programs.direction_id`, `stages.is_final`, `stages.requires_lms_data`,
`interactions.workspace_id` (тогда `process_group_id`), `interactions.contract_id`,
`interactions.external_revision`, `stage_entries.migrated_at`,
`stage_entries.migrated_from_stage_key`, `stage_entries.lms_evidence`; значения перечислений
`organization_kind` (`individual`, `legal_entity`) и `stage_outcome` (`migrated`).

Живой процесс (`drizzle/0007_*`) доведён: `stage_routes` переименована в `process_revisions` и
получила `group_id` вместо `key` и `is_default`, `stages.route_id` и `stage_transitions.route_id`
стали `revision_id`, ссылка взаимодействия на своё пространство стала обязательной, а
`interactions.route_id` удалена последним шагом — после проверки «ни одной открытой записи вне
действующей редакции своего пространства». Реестр ключей (`process_stage_keys`) с этого момента
ведёт публикация.

Группа процесса стала пространством (`drizzle/0019_*`): `process_groups` переименована в
`workspaces`, `interactions.process_group_id` — в `interactions.workspace_id`, а индекс
`interactions_group_status_idx` — в `interactions_workspace_status_idx`. Это `alter table … rename`,
а не пересоздание: данные, внешние ключи и идентификаторы уцелели. Колонок `group_id` у
`process_revisions` и `process_stage_keys` 0019 не касалась — они переехали следующей миграцией,
когда процесс стал отдельной сущностью. Зачем это всё — `docs/workspaces.md`.

Процесс выделен из пространства (`drizzle/0020_*`): заведена таблица `workflows` — `key`, `name`,
`description`, `active_revision_id`, — и на каждое пространство в неё положен процесс с тем же
ключом и именем, потому что до этого места работы и самой работы было одно и то же.
`workspaces.workflow_id` говорит, какой процесс назначен месту, и **допускает пустоту**:
пространство заводят раньше, чем описывают его работу, и требовать готовый процесс заранее
значило бы запретить заводить пространство. `workspaces.active_revision_id` удалена —
действующая редакция стала свойством процесса (`workflows.active_revision_id`): публикация
переключает её одним значением, и значение обязано быть одно на процесс, а не по одному на
каждое место, которому он назначен. `process_revisions.group_id` и `process_stage_keys.group_id`
переименованы в `workflow_id` и смотрят на `workflows`; уникальность редакции стала
`(workflow_id, version)`, частичная уникальность черновика —
`process_revisions_one_draft_per_workflow`, первичный ключ реестра ключей — `(workflow_id, key)`.
Всё это ради одного: **один процесс можно назначить нескольким пространствам**, — а тогда стадия
`signing` в них обязана быть одной и той же стадией, иначе отчёт по двум местам не складывается.
Порядок шагов внутри миграции фиксирован: процессы, ссылка из пространства, редакции и реестр,
перенос действующей редакции — и только потом снятие колонки. Пока `workspaces.active_revision_id`
на месте, `DO $$ … RAISE EXCEPTION` сверяет, что у каждого пространства действующая редакция
процесса та же, что была у места; отказ на этом шаге оставляет данные восстановимыми, после
удаления колонки — уже нет.

Маршруты приёма отделены от настройки процесса (`drizzle/0021_*`):
`process_group_counterparty_kinds` переименована в `workspace_intake_routes`, колонка `group_id` —
в `workspace_id`, индекс — в `workspace_intake_routes_workspace_idx`. Это опять `alter table …
rename`, данными миграция не двигает. Таблица существовала ради двух дел: выбрать процесс при
создании взаимодействия и направить заявку, пришедшую с сайта. Первое отпало само — взаимодействие
заводят внутри пространства, и место известно из адреса, — и от таблицы осталось **только приём
извне**; имя `workspace_intake_routes` это и говорит. **Первичный ключ по виду заявителя
сохранён**, хотя первое дело его и держало: у заявки нет человека, который выбрал бы место, а
адресат обязан быть однозначным — два маршрута на один вид означали бы, что одна и та же заявка
попадает то в одно место, то в другое. Единственный её читатель — `resolveIntakeWorkspace` в
`src/lib/server/stages/process.ts`, и зовут его из приёма заявок
(`src/lib/server/integrations/exchange/intake.ts`), больше ниоткуда.

Вход через каталог учётных записей (`drizzle/0008_*`) доведён: `users.password_hash`,
`password_changed_at` и три столбца второго фактора удалены — своих паролей в базе больше нет, —
существующие записи роли `viewer` переведены на `manager`, и сама роль исчезла вместе со своими
правами. Порядок обязателен: `users.role_id` ссылается на `roles` с `on delete restrict`, поэтому
перевод идёт до удаления роли, а не после.

Что осталось сделать и кому:

| Шаг                                                                          | Чья задача |
| ---------------------------------------------------------------------------- | ---------- |
| `external_source = 'site'` → `<система>:<экземпляр>`                         | обмен      |
| Перенос словарей `exchange_direction` и `exchange_message_state` в контракты | обмен      |

**Пространства кладёт миграция, а их стадии — набор данных.** Без пространства у взаимодействия нет
места, а у заявки с сайта — адресата, поэтому `b2b` и `b2c` вместе с соответствием «вид
контрагента → пространство» приезжают на любую установку; заодно 0020 кладёт по процессу на
каждое из них и назначает его. Стадии — нет: навязывать заказчику наши четырнадцать стадий
установкой схемы незачем, и описывает их `ensureWorkflow` из сида, а назначение процесса
пространству — отдельное действие, `assignWorkflow`.
`reset()` в интеграционных тестах чистит таблицы целиком, и туда эти строки возвращает снимок,
снятый прогоном сразу после миграций (`tests/integration/helpers/db.ts`).

**Что делает миграция 0007 с данными.** Порядок фиксирован, и каждый шаг восстановим до последнего:
редакции привязываются к пространствам по семейству прежнего маршрута (`university-partnership` →
`b2b`, прочие семейства — по пространству на семейство, их завела 0006); у пространства остаётся
один черновик — последний, остальные удаляются вместе со своими стадиями; в каждой редакции
появляется финальная стадия (последняя по порядку, если ни одна не отмечена); открытые записи
перепривязываются **по ключу** к стадии действующей редакции своего пространства, закрытые не
трогаются; слепки открытых записей пересобираются по стадии, закрытые получают два новых признака
выключенными; `DO $$ … RAISE EXCEPTION` проверяет, что открытых записей вне действующей редакции не
осталось, — и только после этого ссылка взаимодействия на пространство становится обязательной, а
`route_id` удаляется.

**Новое значение перечисления и одна транзакция.** Мигратор Drizzle применяет все непримененные
файлы одной транзакцией, а PostgreSQL запрещает пользоваться значением перечисления, добавленным в
незакрытой транзакции («unsafe use of new value»). Разнести добавление и использование по разным
файлам поэтому недостаточно. Виды контрагента нужны уже в той же транзакции — проверке
`organizations_person_matches_kind` и строкам соответствия видов, — поэтому перечисление
`organization_kind` пересоздано: у типа, созданного в этой же транзакции, запрета нет. Значение
`stage_outcome.migrated` в миграции не используется, и оно добавлено обычным `ALTER TYPE ... ADD VALUE`.

**Чего не выражает билдер Drizzle**, поэтому лежит в custom-миграции рядом с представлениями и
триггерами: частичная уникальность `organization_responsibles` с `NULLS NOT DISTINCT` и индекс по
выражению `stage_entries ((stage_snapshot ->> 'key'))`. В схеме на них стоит комментарий: индекс,
которого не видно в файле таблицы, однажды удалят, не заметив.

**Переименование таблицы против снимка drizzle-kit.** Снимок (`drizzle/meta/*`) описывает
целевое состояние схемы и одинаков независимо от того, назвали ли операцию созданием или
переименованием; SQL — нет. Поэтому 0007 сгенерирован с ответами по умолчанию, а его SQL переписан
руками на `ALTER TABLE … RENAME` плюс перенос данных: `db:generate` после этого новых файлов не
создаёт, а `db:migrate` не теряет ни одной ссылки на стадии.

### Цикл изменения схемы

1. правим файлы в `schema/`;
2. `DATABASE_URL=... pnpm run db:generate` — drizzle-kit кладёт SQL в `drizzle/`;
3. читаем сгенерированный SQL глазами;
4. что drizzle-kit не выражает (триггеры, представления), добавляем отдельной custom-миграцией:
   `pnpm exec drizzle-kit generate --custom --name=<имя>`;
5. `pnpm run db:migrate`, затем `pnpm run test:integration`;
6. коммитим и схему, и миграцию.

Каталог прав и ролей SQL-миграциями не описан — его приводит к коду
`seedRolesAndPermissions(tx)` из `$lib/server/rbac/seed`, и зовёт её `scripts/migrate.ts` сразу
после применения миграций, на каждой установке и на каждом старте контейнера. Отсюда правило:
право, добавленное в `$lib/server/rbac/permissions`, приезжает к ролям вместе с релизом, руками
делать ничего не надо. Её же зовут тесты, а ручной прогон на работающей установке — это
`node scripts/seed/index.ts --roles-only` ([`seeds.md`](seeds.md)).

## Контракты

`src/lib/contracts/**` — схемы Zod 4 команд и запросов плюс типы представлений (DTO).
Серверных импортов здесь нет: одна и та же схема валидирует форму в браузере, тело запроса
к API и строку импорта. Сообщения об ошибках — по-русски, они показываются человеку.

Строки таблиц наружу не отдаются. Тип ответа объявлен в контрактах (`OrganizationView`,
`PersonView`, `AffiliationView`, `AuditEventView`, …), сервис приводит строку к нему явно —
иначе любое изменение схемы молча меняло бы контракт с интерфейсом и с API.

Проверка ИНН — `src/lib/validation/inn.ts`: чистая функция с контрольными суммами ФНС,
которой пользуются схемы.

## Как звать сервисы

Каждый сервис принимает `(ctx: ActorContext, input)`. Контекст собирает транспорт:

```ts
import { actorFromEvent } from '$lib/server/actor';

export const actions = {
	default: async (event) => {
		const ctx = actorFromEvent(event);
		const form = await superValidate(event.request, zod4(createOrganizationSchema));
		// …
	}
};
```

Фоновая работа — `systemActor(requestId)`. Такой контекст проходит любую проверку прав
(у него нет пользователя, а запускает его код, который решение уже принял), поэтому
создавать его из обработчика запроса нельзя.

`ActorContext` несёт `requestId`, источник (`ui` / `api` / `system`), пользователя, ключ API,
адрес, `user-agent` и область доступа. Сервис не смотрит в `locals`, не читает заголовки и не
решает, кто перед ним: тогда одно и то же действие ведёт себя одинаково из браузера, из API и
из скрипта.

### Транзакции

```ts
await withTransaction(ctx, async (tx) => {
	const interaction = await createInteraction(tx, …);
	await recordAuditEvent(ctx, { type: 'interactions.created', outcome: 'success' }, tx);
});
```

Транзакцию открывает сервис, отвечающий за операцию целиком; вложенные вызовы получают `tx`
параметром и новой транзакции не начинают. `withTransaction` кладёт `app.request_id` в
настройки сеанса, поэтому медленный или упавший запрос в логе PostgreSQL связывается с
записью журнала.

Открытая транзакция держит соединение целиком, а запись, сделанная рядом с ней отдельным
соединением (отказ журнала, след просмотра контактов), требует второго свободного — поэтому
пул задан явно (`POOL_MAX` в `$lib/server/db`, 24) и обязан вмещать вдвое больше соединений,
чем бывает одновременных транзакций: пул ровно на их число запирается насмерть. По той же
причине область следа, открытая внутри транзакции, получает её исполнителя третьим параметром
(`withPiiTrace(ctx, read, tx)`), а приём заявки держит одну область на весь запрос — снаружи
транзакции.

### Права и область доступа

Право — про действие, область — про строки.

```ts
requirePermission(ctx, 'organizations.write');

const where = and(scopeFilter(ctx, organizations.id), eq(organizations.kind, 'operator'));
```

Каталог прав и роли по умолчанию — `$lib/server/rbac/permissions`: 38 прав, роли `admin`, `lead`,
`manager` и невходящая `service` для ключей обмена. Выборки обязаны применять `scopeFilter` всегда,
в том числе там, где сегодня у всех полный доступ: правило, которое соблюдают не везде, — это не
правило. При пустой области условие превращается в `false`, а не в синтаксически невозможный
`in ()`.

Права роли читаются из базы `loadRolePermissions(roleId)` с кэшем на процесс; после любого
изменения ролей — `invalidateRoleCache()`.

### Ошибки и их перевод в HTTP

Сервисы бросают ошибки из `$lib/server/errors`, ничего не зная про HTTP. Переводит их
транспорт:

| Класс             | `code`       | Ответ API | Что делает форма                              |
| ----------------- | ------------ | --------- | --------------------------------------------- |
| `ValidationError` | `validation` | 400       | показывает `issues` рядом с полями            |
| `ForbiddenError`  | `forbidden`  | 403       | сообщение «недостаточно прав»                 |
| `NotFoundError`   | `not_found`  | 404       | страница «не найдено»                         |
| `ConflictError`   | `conflict`   | 409       | сообщение о том, что состояние уже изменилось |

Запись вне области доступа отдаётся как `NotFoundError`, а не как `ForbiddenError`: иначе
перебором идентификаторов можно узнать, что существует за пределами своей области.

### Контакты людей

`toPersonView(ctx, person)` — единственный способ отдать человека наружу. Он же единственное
место, где контакты расшифровываются: в строке `people` они лежат шифртекстом, и второй
расшифровке взяться неоткуда — значит, и утечь мимо маскирования нечему. Без права
`people.read_pii` почта и телефон маскируются (`i***@vuz.ru`, `+7 *** *** 45 67`), а
`contactsMasked` говорит интерфейсу показывать «скрыто», а не «не указано». Он же отмечает
раскрытие контактов в следе просмотра — одно событие `people.pii_viewed` на чтение, см.
[`directory.md`](directory.md#след-просмотра-контактов). Сериализатор
обязателен и во вложенных ответах, и в выгрузках, и в сгенерированных документах: маскирование
в компоненте рано или поздно забудут в том месте, про которое никто не вспомнил.

### Журнал действий

Событие берётся из словаря `AUDIT_EVENT_TYPES` (`$lib/contracts/audit`) — произвольную строку
записать нельзя. В `details` допустимы только ссылки на записи (ключ заканчивается на `Id`),
`changedFields` и единственный список идентификаторов `personIds` (след просмотра контактов);
ключи `email`, `phone`, `password`, `lastName`, `firstName`, `middleName` и любые другие
отвергаются. Причина простая: персональные данные, попавшие в неизменяемый
журнал, нельзя будет удалить по требованию субъекта, не сломав сам журнал.

`recordAuditEvent(ctx, event, tx?)` с `outcome: 'success'` и переданным `tx` пишет внутри
транзакции: не случилось действие — не должно остаться и записи о нём. `failure` и `denied`
всегда пишутся отдельным соединением, потому что транзакция вокруг них обычно откатывается,
а знать о попытке нужно именно тогда.

Выгрузка (`exportAuditEvents`) требует права `audit.export`, ограничена 50 000 записей за раз
и сама попадает в журнал. CSV отдаётся с BOM — иначе Excel читает кириллицу как мусор.

### Настройки

`getSetting(key)` подставляет значение по умолчанию при отсутствии строки; значения по
умолчанию живут только в `$lib/server/settings`. Непонятное значение в базе роняет запрос, а
не подменяется умолчанием: настройка безопасности, которую никто не понял, опаснее
отсутствующей. `setSetting(ctx, key, value)` требует `settings.write` и пишет в журнал.

## Тесты

Интеграционные тесты поднимают PostgreSQL 17 в testcontainers, применяют миграции из
`drizzle/` и работают с настоящей базой: триггеры, частичные индексы, CHECK и представление —
это и есть то, что проверяется.

```ts
import { startTestDatabase, testActor, failureCode } from './helpers/db';

// Vitest поднимает этот вызов выше импортов. Без него `$env/dynamic/private`
// остаётся слепком `.env`, снятым при старте Vitest, и сервисы пойдут в базу
// разработчика вместо контейнера.
vi.mock('$env/dynamic/private', () => ({ env: process.env }));
```

`startTestDatabase()` возвращает `{ db, raw, reset, stop }`: `db` — тот же handle, что получают
сервисы через `getDb()`, `raw` — отдельное соединение для сырого SQL, `reset()` очищает данные
и заново заливает каталог прав и по пользователю на роль. Ошибку PostgreSQL из обёртки
Drizzle достаёт `failureCode(promise)`.
