# Модель данных и контракты

Документ описывает устройство ядра: где лежит схема базы, как её менять, какими схемами
описаны команды и ответы и по каким правилам сервисы вызываются из транспортов.

Набор полей — гипотеза до получения технического задания заказчика. Имена нейтральные,
смысл каждого столбца объяснён комментарием рядом с ним; переименование полей после
уточнения требований — ожидаемое событие, а не авария.

## Схема базы

`src/lib/server/db/schema/` — по файлу на предметную область, `index.ts` реэкспортирует всё.

| Файл              | Что внутри                                                                           |
| ----------------- | ------------------------------------------------------------------------------------ |
| `shared.ts`       | Повторяющиеся столбцы: `createdAt`/`updatedAt`, внешняя ссылка и её уникальность     |
| `auth.ts`         | `permissions`, `roles`, `role_permissions`, `users`                                  |
| `settings.ts`     | `app_settings`                                                                       |
| `audit.ts`        | `audit_events`                                                                       |
| `directory.ts`    | `organizations`, `sites`, `people`, `affiliations`, `consents`, программы и продукты |
| `interactions.ts` | Маршруты и стадии, взаимодействия, записи стадий, паузы, блокировки, комментарии     |
| `documents.ts`    | `document_templates`, `documents`                                                    |
| `api.ts`          | `api_keys`                                                                           |

Соглашения:

- идентификаторы — `uuid` с `gen_random_uuid()`; ключи справочника прав и ролей — текстовые
  коды, потому что на них ссылается код;
- имена в TypeScript camelCase, в PostgreSQL snake_case (`casing: 'snake_case'`);
- моменты времени — `timestamptz`, календарные (учебные и договорные) даты — `date`;
- `created_at` и `updated_at` есть у каждой сущности. Их нет у `audit_events` и
  `interaction_changes`: это события, у них уже есть `occurred_at` и `changed_at`, а менять
  их нельзя;
- перечисления объявлены значениями из контрактов (`pgEnum('...', ORGANIZATION_KINDS)`), чтобы
  список вариантов не разъехался между формой и таблицей.

### Внешние идентификаторы

У организаций, площадок, программ, продуктов и взаимодействий есть пара
`external_source` + `external_id` с частичной уникальностью
`(external_source, external_id) WHERE external_source IS NOT NULL`. Это основа
идемпотентного импорта: повторная загрузка той же выгрузки обновляет запись, а не плодит
дубли. Записи без внешней ссылки друг другу не мешают.

### Ограничения, которые держат инварианты

| Где             | Что                                                                                                    |
| --------------- | ------------------------------------------------------------------------------------------------------ |
| `organizations` | CHECK: уровень образования заполнен ровно у учебных заведений                                          |
| `organizations` | Частичная уникальность ИНН `WHERE inn IS NOT NULL`                                                     |
| `affiliations`  | Составной внешний ключ `(site_id, organization_id) → sites(id, organization_id)`                       |
| `stage_entries` | Частичная уникальность `(interaction_id) WHERE left_at IS NULL`                                        |
| `stage_pauses`  | Частичная уникальность `(stage_entry_id) WHERE ended_at IS NULL`, CHECK `ended_at > started_at`        |
| `documents`     | Частичная уникальность `(supersedes_id) WHERE supersedes_id IS NOT NULL`, CHECK «не заменяет сам себя» |
| `consents`      | CHECK `withdrawn_at >= given_at` и «автор отзыва только вместе с отзывом»                              |
| `audit_events`  | Триггер `BEFORE UPDATE OR DELETE` → исключение                                                         |

Составной внешний ключ у `affiliations` заменяет триггер: при `site_id IS NULL` правило
MATCH SIMPLE ничего не требует, а при заполненной площадке она обязана принадлежать той же
организации. Ради него у `sites` есть избыточный на первый взгляд уникальный ключ
`(id, organization_id)` — сослаться можно только на уникальный набор столбцов. Удаление
оставлено NO ACTION: проверка откладывается до конца оператора, поэтому каскад от
организации проходит, а точечное удаление площадки, на которую ссылается роль, отвергается.

### Персональные данные и редакции документов

`people.retention_until` (дата) и `people.anonymized_at` отвечают на вопрос «до какого дня данные
хранятся и когда их уничтожили»; `consents` — на вопрос «на каком основании они лежат». Основание
задано перечислением `consent_basis` (`consent`, `contract`, `legal`): это ссылка на норму, а не
заметка. Даты получения и отзыва согласия — календарные (`date`), потому что согласие подписывают
днём, и точность до секунды в нём ничего не значит.

`documents.supersedes_id` — ссылка на редакцию, которую этот файл заменил. Файл неизменяем, поэтому
история документа — цепочка записей, а не версии одной строки. Частичный уникальный индекс
`documents_supersedes_key` держит правило «одну редакцию заменяют один раз»: иначе у документа
вырастает две «следующих» редакции и на вопрос «какая действует» ответа нет. Удаление ссылки —
`set null`: поштучно документы не удаляются вовсе, а каскад от взаимодействия сносит всю цепочку.
Подробности — в [`documents.md`](documents.md#редакции).

### Представление `stage_entry_status`

Срок стадии с учётом пауз. Создаётся custom-миграцией, в схеме объявлено через
`pgView(...).existing()` — Drizzle знает его форму и умеет из него выбирать, но не пытается
им управлять.

Окно записи — от входа на стадию до `left_at`, а у открытой записи до `now()`.
`paused_seconds` — суммарная длина пересечения пауз с окном (открытая пауза считается до
конца окна), и ровно на неё сдвигается `due_at`. Закрытая запись перестаёт «ехать»: её окно
больше не растёт. Норматив берётся из `stage_snapshot`, а не из таблицы `stages`: маршрут
могли переиздать, а срок уже пройденной стадии обязан остаться прежним.

Протухание считается не здесь: оно про тишину вокруг взаимодействия, а не про часы на
стадии, и опирается на `interactions.last_activity_at`, который обновляют сервисы.

### Цикл изменения схемы

1. правим файлы в `schema/`;
2. `DATABASE_URL=... pnpm run db:generate` — drizzle-kit кладёт SQL в `drizzle/`;
3. читаем сгенерированный SQL глазами;
4. что drizzle-kit не выражает (триггеры, представления), добавляем отдельной custom-миграцией:
   `pnpm exec drizzle-kit generate --custom --name=<имя>`;
5. `pnpm run db:migrate`, затем `pnpm run test:integration`;
6. коммитим и схему, и миграцию.

Каталог прав и ролей SQL-миграциями не описан — его приводит к коду
`seedRolesAndPermissions(tx)` из `$lib/server/rbac/seed`, и зовёт её `scripts/migrate.ts` сразу
после применения миграций, на каждой установке и на каждом старте контейнера. Отсюда правило:
право, добавленное в `$lib/server/rbac/permissions`, приезжает к ролям вместе с релизом, руками
делать ничего не надо. Её же зовут тесты, а ручной прогон на работающей установке — это
`node scripts/seed/index.ts --roles-only` ([`seeds.md`](seeds.md)).

## Контракты

`src/lib/contracts/**` — схемы Zod 4 команд и запросов плюс типы представлений (DTO).
Серверных импортов здесь нет: одна и та же схема валидирует форму в браузере, тело запроса
к API и строку импорта. Сообщения об ошибках — по-русски, они показываются человеку.

Строки таблиц наружу не отдаются. Тип ответа объявлен в контрактах (`OrganizationView`,
`PersonView`, `AffiliationView`, `AuditEventView`, …), сервис приводит строку к нему явно —
иначе любое изменение схемы молча меняло бы контракт с интерфейсом и с API.

Проверка ИНН — `src/lib/validation/inn.ts`: чистая функция с контрольными суммами ФНС,
которой пользуются схемы.

## Как звать сервисы

Каждый сервис принимает `(ctx: ActorContext, input)`. Контекст собирает транспорт:

```ts
import { actorFromEvent } from '$lib/server/actor';

export const actions = {
	default: async (event) => {
		const ctx = actorFromEvent(event);
		const form = await superValidate(event.request, zod4(createOrganizationSchema));
		// …
	}
};
```

Фоновая работа — `systemActor(requestId)`. Такой контекст проходит любую проверку прав
(у него нет пользователя, а запускает его код, который решение уже принял), поэтому
создавать его из обработчика запроса нельзя.

`ActorContext` несёт `requestId`, источник (`ui` / `api` / `system`), пользователя, ключ API,
адрес, `user-agent` и область доступа. Сервис не смотрит в `locals`, не читает заголовки и не
решает, кто перед ним: тогда одно и то же действие ведёт себя одинаково из браузера, из API и
из скрипта.

### Транзакции

```ts
await withTransaction(ctx, async (tx) => {
	const interaction = await createInteraction(tx, …);
	await recordAuditEvent(ctx, { type: 'interactions.created', outcome: 'success' }, tx);
});
```

Транзакцию открывает сервис, отвечающий за операцию целиком; вложенные вызовы получают `tx`
параметром и новой транзакции не начинают. `withTransaction` кладёт `app.request_id` в
настройки сеанса, поэтому медленный или упавший запрос в логе PostgreSQL связывается с
записью журнала.

Открытая транзакция держит соединение целиком, а запись, сделанная рядом с ней отдельным
соединением (отказ журнала, след просмотра контактов), требует второго свободного — поэтому
пул задан явно (`POOL_MAX` в `$lib/server/db`, 24) и обязан вмещать вдвое больше соединений,
чем бывает одновременных транзакций: пул ровно на их число запирается насмерть. По той же
причине область следа, открытая внутри транзакции, получает её исполнителя третьим параметром
(`withPiiTrace(ctx, read, tx)`), а приём заявки держит одну область на весь запрос — снаружи
транзакции.

### Права и область доступа

Право — про действие, область — про строки.

```ts
requirePermission(ctx, 'organizations.write');

const where = and(scopeFilter(ctx, organizations.id), eq(organizations.kind, 'operator'));
```

Каталог прав и роли по умолчанию — `$lib/server/rbac/permissions`. Выборки обязаны применять
`scopeFilter` всегда, даже пока все роли получают полный доступ: правило, которое соблюдают
не везде, — это не правило. При пустой области условие превращается в `false`, а не в
синтаксически невозможный `in ()`.

Права роли читаются из базы `loadRolePermissions(roleId)` с кэшем на процесс; после любого
изменения ролей — `invalidateRoleCache()`.

### Ошибки и их перевод в HTTP

Сервисы бросают ошибки из `$lib/server/errors`, ничего не зная про HTTP. Переводит их
транспорт:

| Класс             | `code`       | Ответ API | Что делает форма                              |
| ----------------- | ------------ | --------- | --------------------------------------------- |
| `ValidationError` | `validation` | 400       | показывает `issues` рядом с полями            |
| `ForbiddenError`  | `forbidden`  | 403       | сообщение «недостаточно прав»                 |
| `NotFoundError`   | `not_found`  | 404       | страница «не найдено»                         |
| `ConflictError`   | `conflict`   | 409       | сообщение о том, что состояние уже изменилось |

Запись вне области доступа отдаётся как `NotFoundError`, а не как `ForbiddenError`: иначе
перебором идентификаторов можно узнать, что существует за пределами своей области.

### Контакты людей

`toPersonView(ctx, person)` — единственный способ отдать человека наружу. Без права
`people.read_pii` почта и телефон маскируются (`i***@vuz.ru`, `+7 *** *** 45 67`), а
`contactsMasked` говорит интерфейсу показывать «скрыто», а не «не указано». Он же отмечает
раскрытие контактов в следе просмотра — одно событие `people.pii_viewed` на чтение, см.
[`directory.md`](directory.md#след-просмотра-контактов). Сериализатор
обязателен и во вложенных ответах, и в выгрузках, и в сгенерированных документах: маскирование
в компоненте рано или поздно забудут в том месте, про которое никто не вспомнил.

### Журнал действий

Событие берётся из словаря `AUDIT_EVENT_TYPES` (`$lib/contracts/audit`) — произвольную строку
записать нельзя. В `details` допустимы только ссылки на записи (ключ заканчивается на `Id`),
`changedFields` и единственный список идентификаторов `personIds` (след просмотра контактов);
ключи `email`, `phone`, `password`, `lastName`, `firstName`, `middleName` и любые другие
отвергаются. Причина простая: персональные данные, попавшие в неизменяемый
журнал, нельзя будет удалить по требованию субъекта, не сломав сам журнал.

`recordAuditEvent(ctx, event, tx?)` с `outcome: 'success'` и переданным `tx` пишет внутри
транзакции: не случилось действие — не должно остаться и записи о нём. `failure` и `denied`
всегда пишутся отдельным соединением, потому что транзакция вокруг них обычно откатывается,
а знать о попытке нужно именно тогда.

Выгрузка (`exportAuditEvents`) требует права `audit.export`, ограничена 50 000 записей за раз
и сама попадает в журнал. CSV отдаётся с BOM — иначе Excel читает кириллицу как мусор.

### Настройки

`getSetting(key)` подставляет значение по умолчанию при отсутствии строки; значения по
умолчанию живут только в `$lib/server/settings`. Непонятное значение в базе роняет запрос, а
не подменяется умолчанием: настройка безопасности, которую никто не понял, опаснее
отсутствующей. `setSetting(ctx, key, value)` требует `settings.write` и пишет в журнал.

## Тесты

Интеграционные тесты поднимают PostgreSQL 17 в testcontainers, применяют миграции из
`drizzle/` и работают с настоящей базой: триггеры, частичные индексы, CHECK и представление —
это и есть то, что проверяется.

```ts
import { startTestDatabase, testActor, failureCode } from './helpers/db';

// Vitest поднимает этот вызов выше импортов. Без него `$env/dynamic/private`
// остаётся слепком `.env`, снятым при старте Vitest, и сервисы пойдут в базу
// разработчика вместо контейнера.
vi.mock('$env/dynamic/private', () => ({ env: process.env }));
```

`startTestDatabase()` возвращает `{ db, raw, reset, stop }`: `db` — тот же handle, что получают
сервисы через `getDb()`, `raw` — отдельное соединение для сырого SQL, `reset()` очищает данные
и заново заливает каталог прав и по пользователю на роль. Ошибку PostgreSQL из обёртки
Drizzle достаёт `failureCode(promise)`.
