**От заявки до подтверждённого результата — весь процесс под контролем.**

**LCT CRM** — система, в которой оператор образовательных программ ведёт весь цикл работы с вузами, колледжами
и школами: от первого контакта до подписанного соглашения, обучения и контроля исполнения. Каждое взаимодействие
идёт по настраиваемому маршруту стадий, и по каждому видно, **что происходит, что мешает, кто должен действовать
и что можно сделать прямо сейчас**. Рядом — данные об обучении: загрузки статистики с проверкой строк, показатели
по программам и объяснимый рейтинг востребованности.

Решение команды **Wine Coding Team** для хакатона «Лидеры цифровой трансформации 2026», задача
**«Система контроля взаимодействия с учебными заведениями»** от ИТ Школы Ростелекома.

## Идея

Цель развития — связать заявку с сайта, работу сотрудников, обучение и проверяемый отчёт в один путь.
Текущий прототип уже даёт карточки взаимодействий, движок стадий, документы, статистику и основу обмена.
Общий изменяемый процесс, Keycloak и полный двусторонний обмен относятся к следующему этапу;
ниже описаны работающие возможности, а запланированное отмечено в дорожной карте.

Оператор федеральных образовательных проектов одновременно ведёт десятки партнёрств с учебными заведениями.
У каждого — свой этап, свои документы, свои сроки и свои люди, а данные об обучении приходят из нескольких
источников и меняются в течение года. Пока это живёт в таблицах и переписке, никто не может ответить одним
взглядом: где мы застряли, кого ждём и какие программы действительно востребованы.

LCT CRM собирает это в одну систему координат.

|                               | Что это значит                                                                                                                                                                                                                                                                                     |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Три стороны**               | Учебное заведение, компания-заказчик подготовки и оператор — равноправные участники взаимодействия. У организации есть площадки (филиалы, кампусы), у людей — роли в организациях с периодом действия.                                                                                             |
| **Воронка стадий**            | Взаимодействие идёт по маршруту из 14 стадий: поиск контактов → сверка программ → встреча → документы → соглашение → передача материалов → внедрение → обучение преподавателей → занятия → контроль исполнения. Маршрут — конфигурация, а не код: версии, чек-листы, нормативы, права на переходы. |
| **Контроль каждой стадии**    | Норматив по дням, пауза «ждём контрагента», помехи с причиной, ответственный, результат и подтверждение. Просрочка вычисляется по календарю за вычетом пауз.                                                                                                                                       |
| **Данные об обучении**        | Статистика хранится снимками с происхождением: источник, период, область покрытия, режим (полный / дополнение / исправление). Показатели считаются только по подтверждённым снимкам; ноль и «нет данных» различаются.                                                                              |
| **Документы внутри процесса** | Соглашение собирается по шаблону в DOCX и PDF прямо из карточки; загруженные файлы неизменяемы, отметки «согласован / утверждён / введён в действие» хранятся отдельно.                                                                                                                            |
| **Открытость**                | REST API с OpenAPI 3.1 и Swagger UI, ключи доступа с правами человека, лимиты частоты, идемпотентность изменяющих запросов.                                                                                                                                                                        |

## Что умеет

### Сводка: что требует внимания сегодня

Счётчики портфеля, распределение активных взаимодействий по группам стадий, список «требуют действия»
(сначала просроченные, затем с помехами и с близким сроком), «ждём вуз» и лента активности.

<p align="center"><img src="docs/media/home.png" alt="Сводка" width="960"></p>

### Карточка взаимодействия: четыре вопроса

Лента стадий, а под ней — **что происходит**, **что мешает**, **кто должен действовать**, **что могу сейчас**.
Кнопка перехода недоступна, пока не закрыты обязательные пункты чек-листа, не снята пауза или не записан
результат, и объясняет каждую причину словами. Правила живут в одной функции, которой пользуются и интерфейс,
и API, и сама команда перехода — поэтому они не расходятся.

<p align="center"><img src="docs/media/interaction-card.png" alt="Карточка взаимодействия" width="960"></p>

Вкладки карточки: стадия (чек-лист, результат, подтверждение), документы, помехи, правки плана, история
переходов с причинами, комментарии.

<p align="center"><img src="docs/media/interaction-history.png" alt="История переходов" width="960"></p>

### Список с фильтрами: просроченные, на паузе, с помехами

Таблицы с состоянием в адресной строке (фильтры и сортировку можно отправить ссылкой), выбором колонок,
клавиатурной навигацией и постраничной выборкой на сервере.

<p align="center"><img src="docs/media/interactions-overdue.png" alt="Просроченные взаимодействия" width="960"></p>

### Доска: где стоит работа целиком

Те же взаимодействия колонками по стадиям маршрута — сразу видно, на какой стадии скопились дела и
сколько из них просрочено. Карточку двигают перетаскиванием или меню на ней, но решает не доска:
переход считает тот же движок, что и в карточке взаимодействия, поэтому невозможный отказывает
словами, а карточка остаётся на месте. Возврат и пропуск, как и везде, требуют объяснения.
Представление стоит в адресе — доской делятся ссылкой вместе с фильтрами.

<p align="center"><img src="docs/media/interactions-board.png" alt="Доска взаимодействий по стадиям" width="960"></p>

### Маршрут стадий как конфигурация

Стадии с категорией, нормативом, чек-листом и требованиями к результату; переходы вперёд, назад и с пропуском,
каждый со своим правом. Опубликованная версия неизменяема — по ней уже идут взаимодействия, — изменения
делаются новой версией.

<p align="center"><img src="docs/media/settings-route.png" alt="Экран маршрута стадий" width="960"></p>

### Документы: соглашение в два формата за секунды

Шаблон заполняется данными взаимодействия, DOCX собирается на сервере, PDF — через Gotenberg. Сборка,
загрузка и скачивание попадают в журнал; файлы отдаются только через проверку прав и области доступа.

<p align="center"><img src="docs/media/documents.png" alt="Раздел документов" width="960"></p>

Исправленный документ — не правка прежней записи, а новая **редакция** со ссылкой на заменённую:
файл неизменяем, цепочка видна целиком, а отметки «согласован / утверждён / введён в действие»
остаются на том файле, который согласовывали, и на новой редакции ставятся заново. Списки по
умолчанию показывают действующую редакцию; заменённая открывается по ссылке с пометкой, чем её
заменили.

### Данные об обучении: загрузка → проверка → показатели → рейтинг

Мастер из трёх шагов: файл XLSX или CSV с периодом и режимом, сопоставление колонок с подсказками,
построчная проверка с понятными ошибками («организация не найдена в справочнике») и подтверждение снимка.

<p align="center"><img src="docs/media/import.gif" alt="Загрузка статистики с сопоставлением колонок" width="960"></p>

Показатели считаются по программам и организациям за выбранный период. Рейтинг программ объясним:
рядом с баллом — из чего он сложился.

<p align="center"><img src="docs/media/data-ranking.png" alt="Рейтинг программ с объяснением" width="960"></p>

Дашборд собирает портфель одного отчётного периода в один экран: шесть плиток, верхушка рейтинга с
разложением балла, разбивка по уровням программ, распределение по вузам и происхождение — из каких
загрузок сложились числа. Записанный ноль и отсутствие данных здесь разные ответы, и это видно
словами. Тот же период выгружается книгой XLSX в четыре листа: числа приезжают числами, пустая
ячейка значит «нет данных», а текст, начинающийся со знака равенства, обезврежен — название вуза из
чужой выгрузки не выполнится формулой у того, кто открыл файл.

<p align="center"><img src="docs/media/data-dashboard.png" alt="Дашборд данных: плитки, рейтинг с объяснением, разбивка по уровням" width="960"></p>

### Справочники

Организации с площадками, контакты с ролями, программы с версиями, продукты. Дедупликация юрлиц по ИНН,
архив вместо удаления, единый образец для всех разделов.

<p align="center"><img src="docs/media/organizations.png" alt="Справочник организаций" width="960"></p>

### Персональные данные: основание, срок и след

Данные человека лежат в системе не «потому что их завели», а на основании: согласие субъекта,
исполнение договора или требование закона — с датой получения и датой отзыва. Рядом срок хранения:
по нему список отбирает записи, у которых он истёк. Обезличивание — плановое уничтожение: имя,
контакты и заметки стираются, сама запись остаётся, потому что на неё ссылаются взаимодействия, а
удалить строку значит переписать историю. Показ немаскированных контактов — отдельное событие
журнала: одна запись на чтение, со списком идентификаторов и без единого значения.

### Журнал действий

Неизменяемый журнал: кто, что, когда, с какого адреса и над чем. Записи защищены триггером базы от правки
и удаления, отказы по правам тоже фиксируются. Фильтры и экспорт в CSV и JSON.

<p align="center"><img src="docs/media/audit.png" alt="Журнал действий" width="960"></p>

### Публичный API

`/api/v1` с OpenAPI 3.1 из тех же Zod-схем, что проверяют запросы. Ключ действует правами и областью доступа
выпустившего его пользователя, показывается один раз, в базе хранится только хеш. Лимиты частоты в заголовках,
`Idempotency-Key` для изменяющих запросов, единый формат ошибок с `requestId`, который есть и в журнале.

<p align="center"><img src="docs/media/api-docs.png" alt="Swagger UI" width="960"></p>

### Интеграции: вебхуки, обмен с CMS и системой обучения

**Вебхуки.** Подписка выбирает события журнала точными кодами или целыми разделами; доставка идёт
`POST`-ом с подписью HMAC-SHA256 по строке «момент отправки + тело», поэтому перехваченный запрос не
повторить завтра. Неудача уходит в очередь повторов — шесть попыток, от «сразу» до «через два
часа», — и одно событие доходит до подписки ровно один раз.

**Обмен в четыре стороны.** Заявка с сайта превращается во взаимодействие (`POST /api/v1/applications`),
снимок её статуса уходит обратно в CMS после каждого изменения, учебная группа заводится в системе
обучения кнопкой с карточки, а результат потока приходит оттуда сам и подтверждает стадию — не
двигая взаимодействие: переход остаётся решением сотрудника. Сообщения едут в общем конверте с
версией схемы и идентификатором события, исходящие подписаны HMAC, повторяются только временные
отказы, а повтор не создаёт дубля — ни у нас, ни у получателя. Обе стороны обмена видны одним
списком в разделе «Внешние системы»: что пришло, что ушло, сколько было попыток и что ответили.

**Система обучения.** Клиент веб-сервисов Moodle забирает курсы, записанных слушателей и итоговые
оценки и складывает их в обычный снимок данных — тот же, что получается из файла, и с тем же
происхождением. Снимок останавливается на «проверен»: ввести числа в показатели — решение человека.

Настоящие CMS и LMS заказчика наружу не смотрят, поэтому на стенде рядом подняты два имитатора —
`mock-cms` и `mock-lms`. Они говорят ровно на объявленном контракте и умеют ломаться по команде
(отказ, задержка, обрыв связи), поэтому повторы и восстановление после сбоя показываются вживую. Что
они отвечают, ничего не доказывает о системах заказчика: доказывается другое — что CRM говорит на
контракте и не теряет сообщений.

## Демо за пять минут

Сценарий «разобраться с задержкой и довести до результата» — от просроченного взаимодействия до подписанного
соглашения. Тот же проход выполняется автоматически в `e2e/demo-pass.test.ts`.

<p align="center"><img src="docs/media/demo-pass.gif" alt="Демо-проход: просрочка → чек-лист → переход → соглашение" width="960"></p>

1. Откройте [стенд](https://crm.volkv.com) или локальный http://localhost:3000 и нажмите **«Войти как менеджер»**.
2. В «Взаимодействиях» включите фильтр **«Просроченные»**. Откройте «СЗПУ: подготовка по прикладной
   информатике, 2026/2027» — оно стоит на первой стадии дольше норматива.
3. Карточка объясняет, что мешает: не закрыты обязательные пункты чек-листа. Кнопка перехода недоступна.
4. Закройте оба пункта на вкладке «Стадия» — кнопка «Перейти: Коммуникация и сверка программ» оживает.
   Нажмите: лента стадий и история обновятся.
5. На вкладке «Документы» заполните поля соглашения и нажмите «Сгенерировать соглашение» — DOCX и PDF готовы.
6. Войдите администратором и откройте «Журнал»: переход и сборка документа уже там, с автором и временем.

## Быстрый старт

Нужны Docker 25+ с плагином Compose. Для разработки — Node.js 24 (`.nvmrc`) и pnpm 10 (`corepack enable`).

```bash
git clone https://github.com/volkv/lct-2026.git && cd lct-2026
docker compose up --build
```

Поднимаются приложение, PostgreSQL 17, Redis 8, Keycloak, Gotenberg, MinIO, Mailpit и два имитатора
систем заказчика. Миграции применяются автоматически, демо-данные заливаются при первом старте.

| Адрес                          | Что там                                |
| ------------------------------ | -------------------------------------- |
| http://localhost:3000          | приложение                             |
| http://localhost:3000/api/docs | Swagger UI                             |
| http://localhost:58080/admin   | Keycloak — каталог учётных записей     |
| http://localhost:8025          | Mailpit — вся исходящая почта          |
| http://localhost:59001         | MinIO — файлы документов               |
| http://localhost:58081         | `mock-cms` — имитатор CMS сайта        |
| http://localhost:58082         | `mock-lms` — имитатор системы обучения |

Имитаторы показывают своё состояние страницей: что они приняли, что отправили и чем им ответили.
Адреса и секрет обмена приложение берёт из `EXCHANGE_*` (`.env.example`), а ключ доступа, которым
имитаторы представляются CRM, выпускает сид по `EXCHANGE_API_KEY`; переменной нет — имитаторы честно
отвечают, что обмен на стенде не настроен.

Локальный стек — демонстрационный стенд: на странице входа перечислены учётные записи демонстрации.
Пустая база без них: `DEMO_MODE=false docker compose up --build`.
Остановить и удалить данные: `docker compose down -v`.

### Вход

Почту и пароль спрашивает не система, а общий каталог учётных записей — Keycloak, realm `lct`
(OIDC Authorization Code + PKCE). Кнопка «Войти» уводит туда, каталог проверяет пароль и второй
фактор, а система получает от него проверенную учётную запись и роль. Своих паролей в базе нет.

Роль приходит из каталога при каждом входе: `crm-admin` → администратор, `crm-lead` → руководитель,
`crm-user` → менеджер. Учётная запись без единой роли CRM получает понятный отказ и в системе не
заводится. Кто за что отвечает и что при этом видит — [`docs/access-matrix.md`](docs/access-matrix.md);
устройство входа — [`docs/auth.md`](docs/auth.md).

Консоль Keycloak локального стека — http://localhost:58080/admin, учётная запись из
`KEYCLOAK_ADMIN` / `KEYCLOAK_ADMIN_PASSWORD`.

### Демо-учётные записи

| Имя входа | Роль          | Что ведёт                                                                                 |
| --------- | ------------- | ----------------------------------------------------------------------------------------- |
| `admin`   | Администратор | доступ, каталоги, процесс, интеграции, настройки; видит всё                               |
| `lead`    | Руководитель  | свою область и работу подчинённых, назначает ответственных за вузы, журнал по своим людям |
| `manager` | Менеджер      | свои вузы: взаимодействия, переходы, документы, контакты, отчёты по своей области         |

Пароль у всех трёх общий — `SEED_DEMO_PASSWORD` (значение для локальной работы — в `.env.example`);
его читает импорт realm, а не сервер. В базе приложения эти же люди заведены с почтами
`<имя входа>@demo.lct-crm.local`: при первом входе запись найдётся по подтверждённой почте, и
человек войдёт со своим портфелем, а не двойником. Демо-данные синтетические: названия организаций и
людей не соответствуют реальным.

Границу держат права, а не спрятанные кнопки: демонстрационная сессия не получает `users.manage`,
`api_keys.manage`, `integrations.manage_endpoints` и `people.anonymize`, какой бы ролью в неё ни
вошли, — на эти экраны она получает 403 и из `curl` тоже. Открытый стенд общий, и посетитель не
должен ни оставлять после себя учётную запись или ключ, которые переживут его визит, ни стирать
чужие данные насовсем. Всё остальное — правка процесса, журнал обмена, настройки стенда, выгрузка
журнала — демонстрации доступно: иначе показывать нечего.

### Полный доступ локально

Экраны управления пользователями и ключами показывает штатный администратор — обычная учётная запись
оператора, не демонстрационная. В realm её нет: заводят её в консоли Keycloak, как и любого
настоящего сотрудника.

1. открыть http://localhost:58080/admin, realm `lct`, раздел «Users»;
2. завести запись, указать подтверждённую почту `admin@staff.lct-crm.local` и задать пароль;
3. на вкладке «Role mapping» выдать роль realm `crm-admin`.

Почта выбрана не случайно: с этим адресом сид уже завёл в базе приложения строку «Администратор
стенда», и первый вход свяжет её с каталогом вместо того, чтобы завести двойника. Любая другая
подтверждённая почта тоже работает — тогда запись появится в системе при первом входе.

## Безопасность

Меры выбраны по методическому документу ФСТЭК о защите информации в приложениях и требованиям 152-ФЗ.
Класс защищённости — гипотеза до технического задания; ниже то, что уже работает.

- **Вход — через общий каталог учётных записей.** OIDC Authorization Code + PKCE (`S256`),
  конфиденциальный клиент: код на токены меняет сервер. Своих паролей в базе нет вовсе. Id-токен
  проверяется по ключам realm целиком — подпись, `iss`, `aud`, `nonce`, сроки; одноразовые значения
  захода живут в Redis не дольше десяти минут и читаются с удалением. Пароль, его политика и второй
  фактор — забота каталога, включая защиту от перебора.
- **Роль приходит из каталога.** `crm-admin` / `crm-lead` / `crm-user` отображаются на роли системы
  при каждом входе; отозвали роль — следующий вход отклонён, а учётная запись выключена вместе со
  своими сессиями. Ключи обмена с внешними системами выпускаются на машинного субъекта, которому
  вход закрыт при любых утверждениях токена, а доступ открыт только к эндпоинтам обмена.

- **Сессии.** Серверные, в Redis, с индексом по пользователю; бездействие 30 минут, абсолютный срок
  12 часов; смена роли, руководителя или выключение записи гасят их немедленно. «Выйти» гасит и
  сессию каталога, а не только нашу.
- **Область доступа на каждую выборку.** Менеджер видит свои вузы, руководитель — свои и своих
  подчинённых, администратор — всё. Считается подзапросом по действующим назначениям, поэтому смена
  ответственного меняет доступ в ту же секунду и во всех каналах сразу: списки, карточки, скачивание
  файлов, выгрузки, дашборд, подсказки и публичный API.
- **Права на каждый запрос.** Каталог прав и ролей, проверка на сервере в каждом загрузчике, действии и
  эндпоинте; навигация не показывает недоступное, но защита не в навигации.
- **Журнал по составу РСБ.1.** Append-only на уровне базы (триггер), без значений персональных данных —
  только идентификаторы и имена полей; отказы по правам и аномалии анонимных запросов тоже пишутся.
- **Персональные данные.** Единый сериализатор контактов маскирует телефон и почту в списках и API
  по правам; человек вне области не виден в справочнике и отвечает «не найдено» по прямой ссылке —
  включая согласия, срок хранения и обезличивание.
- **API.** Ключи с хешем в базе, лимиты частоты по ключу и по адресу, идемпотентность, ошибки без лишних
  подробностей, валидация по тем же схемам, из которых собран OpenAPI.
- **Файлы.** Проверка содержимого загружаемых файлов, потолок размера, скачивание только через проверку прав.
- **HTTP.** CSP и security-заголовки, антикэш чувствительных ответов, CSRF-защита форм, страницы ошибок
  с `requestId`, который совпадает с записью журнала.

## Качество

```bash
pnpm run check:all
```

Один гейт локально и в CI: аудит зависимостей → lint → типы → unit-тесты → интеграционные тесты
(PostgreSQL и Redis поднимаются testcontainers) → сборка → e2e против собранного приложения → сборка образа.

| Уровень        | Сколько | Что проверяется                                                                         | Инструмент              |
| -------------- | ------- | --------------------------------------------------------------------------------------- | ----------------------- |
| Unit           | 544     | контракты, движок стадий, разбор импорта, права, навигация, форматирование              | Vitest                  |
| Интеграционные | 401     | сервисы на настоящей базе: миграции, транзакции, журнал, API, документы через Gotenberg | Vitest + testcontainers |
| End-to-end     | 105     | демо-проход, разделы, формы, вход через каталог, границы области, ширины 390 и 1280     | Playwright              |

Всего 958 автоматических тестов. Быстрый гейт для разработки — `pnpm run check:fast`.
