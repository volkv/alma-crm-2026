# Keycloak: realm `lct`

Каталог учётных записей и единственный вход в систему: OIDC Authorization Code + PKCE, своих
паролей приложение не хранит (`docs/auth.md`). Realm, роли, второй фактор и демонстрационные
учётные записи заводятся импортом. Отображение ролей realm на роли системы —
`docs/access-matrix.md`, раздел 6; развёртывание — `docs/deployment.md`, разделы «Keycloak» и
«Промышленная установка».

## Что здесь лежит

| Файл                 | Что это                                                                                                  |
| -------------------- | -------------------------------------------------------------------------------------------------------- |
| `realm-lct.json`     | Импорт realm: клиент, роли, поток входа со вторым фактором, группа `demo`, сроки и лимиты                |
| `demo-users.json`    | Три демонстрационные учётные записи стенда — файл пользователей того же realm                            |
| `initdb-keycloak.sh` | Заводит вторую базу в PostgreSQL стека — ту, в которой Keycloak живёт на стенде                          |
| `themes/alma/`       | Тема формы входа (`loginTheme: "alma"`): облик Альма CRM и быстрый вход демо-стенда поверх `keycloak.v2` |

Учётные записи вынесены из файла realm намеренно: установка у заказчика монтирует только
`realm-lct.json` (`docker-compose.production.yml`) и получает realm без единой учётной записи.
Стек и стенд монтируют оба файла под именами, по которым импорт каталога их связывает:
`lct-realm.json` и `lct-users-0.json` (`docker-compose.yml`). Под любым другим именем файла
пользователей Keycloak импортирует realm и **молча** пропускает учётные записи — проверено на
26.7.4.

Тема монтируется в `/opt/keycloak/themes/alma` во всех трёх вариантах запуска (`docker-compose.yml`,
`docker-compose.production.yml`). Шаблонов она не переопределяет — стили поверх `keycloak.v2` и
скрипт `js/alma.js`, который дополняет готовую разметку, поэтому обновление Keycloak её не ломает.
Знак в ней — копия `static/favicon.svg`. Realm, импортированный до появления темы, переключают на
неё сами: импорт существующий realm не трогает.

### Быстрый вход демо-стенда

На странице имени и пароля скрипт темы ставит под заголовком строку о системе, а если контейнеру
каталога задан `KEYCLOAK_DEMO_PASSWORD`, — ещё и блок «Демо-стенд: войти одной кнопкой»: кнопки
«Менеджер», «Руководитель», «Администратор» подставляют `manager` / `lead` / `admin` и пароль и
отправляют форму; там же назван общий пароль и сказано, что данные вымышленные и ночью
сбрасываются. Пароль приходит из `theme.properties` (`meta=alma-demo-password==${env.KEYCLOAK_DEMO_PASSWORD:}`
— тема, в отличие от файла realm, понимает именно форму `env.`) мета-тегом страницы.

Это та же переменная, по которой импорт заводит демо-записи (`demo-users.json`), поэтому кнопки
есть ровно там, где есть эти записи: локальный стек и стенд (`docker-compose.yml`,
`docker-compose.prod.yml`) её задают, промышленная установка (`docker-compose.production.yml`)
перекрывает окружение каталога без неё — мета-тег пуст, блока нет, форма обычная. Отдельной темы
и правки realm для этого не нужно. Пароль, сменённый позже в консоли каталога, переменная не
знает: после такой смены её правят в `.env` и пересоздают контейнер (`docs/deployment.md`,
«Keycloak»). Пробел и `==` в демо-пароле недопустимы — они разломали бы список мета-тегов шаблона.

Тема кэшируется в режиме `start` (стенд, установка): правка файлов темы доходит до формы после
перезапуска контейнера каталога (`docker compose … up -d --force-recreate keycloak`); в
`start-dev` кэша нет.

## Что в realm

**Клиент `lct-crm`** — confidential: код на токены меняет сервер, PKCE `S256` обязателен
(`pkce.code.challenge.method`), неявный поток и обмен пароля на токен выключены. Разрешённые
адреса возврата — `http://localhost:5173/*` (`vite dev`), `http://localhost:4173/*` … `4177/*`
(сборка и параллельные прогоны e2e: `E2E_PORT` берётся из этого списка, потому что адрес возврата,
которого в realm нет, каталог разворачивает) и `${CRM_ORIGIN}/*` (приложение стека или стенда).
Адреса выхода заданы как `+` — «те же, что и адреса возврата».

**Роли realm** — `crm-admin`, `crm-lead`, `crm-user`. Отображение на роли системы и правила
(старшая роль при нескольких, отказ при отсутствии, связывание по подтверждённой почте) —
`docs/access-matrix.md`, раздел 6. Роли `service` в realm нет: машинный субъект не входит.

**Идентификаторы записей заданы в файле** (`id`) и не меняются. Это не украшение: `id`
пользователя Keycloak — это `sub` его токенов, а `sub` — тот ключ, которым приложение связывает
запись каталога со своей (`users.external_subject`). Без `id` в файле Keycloak выдаёт новый UUID
на каждом импорте, то есть на каждом пересоздании контейнера, и те же люди приезжают неузнанными:
вход отклоняется с «ваша почта уже числится за другой учётной записью системы», а связать их
заново может только администратор кнопкой «Отвязать» в `/settings/users` — под которую тоже надо
сначала войти. Значения произвольны, постоянство — нет; сценарий целиком описан в `docs/auth.md`,
абзац «Каталог перезавели».

**Демонстрационные учётные записи** (`demo-users.json`) — `admin`, `lead`, `manager` с почтами
`<роль>@demo.lct-crm.local` и общим паролем `lct-demo-2026` (умолчание подстановки; политика realm
`length(12) and notUsername` ему отвечает). Пароль публичный: его показывает и страница входа
стенда, и `README.md` — стенд открыт для зрителей, и пароль, который надо у кого-то спрашивать,
закрыл бы показ, а не защитил его (границу держат права демонстрации, `docs/auth.md`). Почты совпадают с теми, которыми эти же люди заведены в базе
приложения (`scripts/seed/users.ts`): при первом входе запись найдётся по почте и человек войдёт
со своим прежним портфелем, а не двойником. Поэтому `emailVerified` у них `true` — связывание
принимает только подтверждённую почту. Все три состоят в группе `demo` — это их исключение из
второго фактора, раздел ниже. Импорт файла пользователей не выдаёт им ролей по умолчанию
(`default-roles-lct`), поэтому консоль учётной записи (`/realms/lct/account`) им закрыта: зритель
не сменит общий пароль и не привяжет к общей записи свой код.

**Второй фактор.** Поток входа в браузере — свой, `browser-otp` (`browserFlow`): после имени и
пароля выполняется одна из трёх условных веток, и в каждой — форма одноразового кода (TOTP,
6 цифр, 30 секунд, `HmacSHA1`: Яндекс Ключ, Google Authenticator, FreeOTP и любое другое
приложение TOTP).

| Ветка                    | Когда срабатывает                                               | Что требует                                            |
| ------------------------ | --------------------------------------------------------------- | ------------------------------------------------------ |
| `browser-otp crm-admin`  | роль `crm-admin` и человек не в группе `demo`                   | код обязателен; не настроен — настройка прямо на входе |
| `browser-otp crm-lead`   | роль `crm-lead`, без `crm-admin`, не в группе `demo`            | то же                                                  |
| `browser-otp configured` | прочие, кто настроил код сам (`crm-user`), и не в группе `demo` | код                                                    |

Штатный администратор или руководитель при первом входе попадает на страницу «Настройка
одноразового пароля» (обязательное действие `CONFIGURE_TOTP` Keycloak ставит сам, потому что
форма кода в его ветке обязательна): QR-код, код из приложения — и только потом вход. Дальше —
пароль и код на каждом входе. Человеку с обеими ролями код спрашивается один раз: ветка
руководителя исключает `crm-admin`.

**Исключение — группа `demo`.** Её признак `otp-exempt=true` снимает все три ветки
(`Condition - user attribute` с `include_group_attributes` и отрицанием). Это ровно
демонстрационные записи стенда: пароль у них общий и публичный, их набирают зрители показа, и
код, привязанный к чужому телефону, закрыл бы показ, а не защитил его (границу демонстрации держат
права, `docs/auth.md`, «Демо-режим»). Исключение снимает и третью ветку: код, который кто-то
всё-таки привяжет к общей записи, её не запирает. Поставить признак себе человек не может —
произвольные атрибуты в профиль пользователя realm не пускает, а членство в группе меняет только
администратор каталога. В промышленной установке группа пуста, и чек-лист удаляет её вовсе
(`docs/deployment.md`, «Промышленная установка»).

Проверено входом через поднятый каталог 26.7.4 на обоих вариантах импорта: демонстрационные записи
входят по паролю; заведённые администратором `crm-admin`, `crm-lead` и обе роли сразу получают
настройку кода, а со второго входа — форму кода, неверный код не пропускает; `crm-user` без
настроенного кода входит по паролю, с настроенным — с кодом. Структуру потока держит
`tests/unit/auth/realm-config.test.ts`.

**Роль в токене.** В access-токен `realm_access.roles` кладёт область `roles`, которая у клиента
стоит по умолчанию. В id-токен её кладёт отображение `realm-roles-id-token`, объявленное на самом
клиенте: без него приложению пришлось бы ходить за ролью отдельным запросом на каждый вход.

**Сроки и лимиты.** Access-токен живёт 5 минут, сессия — 8 часов, бездействие — 30 минут.
Защита от перебора включена (`bruteForceProtected`), но настроена под общий стенд: 30 неудач подряд
закрывают учётную запись на минуту, и дольше минуты пауза не растёт (`failureFactor: 30`,
`maxFailureWaitSeconds: 60`). Умолчания Keycloak — 10 неудач и пауза до 15 минут — на стенде
означают, что три зрителя, по очереди опечатавшиеся в общем пароле, закрывают вход всем остальным
на четверть часа. Блокировка при этом остаётся временной и ненулевой: подбор упирается в неё же,
а чужая опечатка не закрывает вход насовсем (принятое ограничение — `docs/security.md`).

## Подстановки окружения

Значения вида `${VAR:умолчание}` Keycloak разворачивает **при импорте**, из окружения своего
контейнера. Это единственный способ задать realm разные значения на машине разработчика и на
стенде, не держа двух файлов.

| Переменная               | Что задаёт                                                     | В локальном стеке                           |
| ------------------------ | -------------------------------------------------------------- | ------------------------------------------- |
| `CRM_ORIGIN`             | Адрес приложения в списке адресов возврата                     | `http://localhost:3000`                     |
| `OIDC_CLIENT_SECRET`     | Секрет клиента `lct-crm`                                       | `lct-crm-dev-secret`                        |
| `KEYCLOAK_DEMO_PASSWORD` | Общий пароль трёх демонстрационных записей (`demo-users.json`) | `SEED_DEMO_PASSWORD`, иначе `lct-demo-2026` |

Грабля, проверенная руками: работает только `${VAR:умолчание}`. Форма `${env.VAR:умолчание}`,
которая встречается в примерах, **молча** подставляет умолчание — переменную окружения она не
находит, и пароль оказывается не тем, которого ждали.

Умолчания в файле — для локального стека: пароль демонстрации и так написан в `README.md` продукта
и показан на странице входа стенда. На стенде обе переменные задают в `.env` **до первого запуска**:
импорт отрабатывает один раз, на пустой базе, и позже подстановка ничего не меняет
(`docs/deployment.md`, раздел «Keycloak», — там же как поменять пароль потом).

## Как править realm

Локально realm задаётся файлами целиком: у базы Keycloak в `docker-compose.yml` нет тома, поэтому
пересозданный контейнер поднимается ровно тем, что записано здесь. Тома нет намеренно — иначе
правка этого файла перестала бы применяться **молча**: стратегия импорта `IGNORE_EXISTING`
пропускает realm, который уже есть. Связь с записями приложения пересоздание не рвёт: `id`
демонстрационных записей заданы в `demo-users.json` и от импорта к импорту не меняются.

Поток входа меняется только новым импортом: частичный импорт Keycloak (`partialImport`) потоков
не переносит. Стенд с базой Keycloak в PostgreSQL получает правку потока пересозданием этой базы —
`docs/deployment.md`, «Что делать, если realm переимпортировали».

```bash
docker compose up -d --force-recreate keycloak   # перечитать файл после правки
docker compose logs keycloak | grep -i import    # «Realm 'lct' imported» — импорт прошёл
```

Накликанное в консоли (http://localhost:58080/admin, учётная запись из `KEYCLOAK_ADMIN`) живёт до
пересоздания контейнера. Чтобы правка осталась, её переносят в этот файл руками.

## Как снять то, что накликали

Полный экспорт работающего realm — 60 КБ, из которых наше меньше страницы: всё остальное —
встроенные клиенты, потоки входа, области и сгенерированные идентификаторы. Файл в репозитории
поэтому не сырой экспорт, а минимум, который читается глазами: Keycloak дополняет отсутствующие
поля умолчаниями сам.

Посмотреть, что получилось у работающего сервера, и перенести нужное сюда руками:

```bash
TOKEN=$(curl -s http://localhost:58080/realms/master/protocol/openid-connect/token \
  -d grant_type=password -d client_id=admin-cli -d username=admin -d password=admin \
  | python3 -c 'import json,sys; print(json.load(sys.stdin)["access_token"])')

curl -s -H "Authorization: Bearer $TOKEN" \
  'http://localhost:58080/admin/realms/lct/partial-export?exportClients=true&exportGroupsAndRoles=true' \
  | python3 -m json.tool > /tmp/lct-realm-full.json
```

Учётных записей в таком экспорте нет намеренно — пароли наружу Keycloak не отдаёт. Три
демонстрационные записи ведутся в `demo-users.json` руками.

## Чего в realm нет

- **Клиента с Direct Access Grants.** Обмен пароля на токен обходит и PKCE, и страницу входа;
  приложению он не нужен, и на стенде его быть не должно.
- **Сотрудников и штатного администратора.** В файлах только три демонстрационные записи.
  Настоящие учётные записи заводит администратор каталога в консоли Keycloak; `crm-admin` и
  `crm-lead` среди них настраивают код на первом же входе.
- **Второго фактора помимо TOTP.** WebAuthn и коды восстановления в потоке не включены: потерянный
  телефон штатного сотрудника — это сброс кода администратором каталога («Учётные данные» →
  удалить OTP), после которого следующий вход снова начинается с настройки.
